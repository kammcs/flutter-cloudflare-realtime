# Changelog

## Unreleased

The first public release, prepared for 0.1.0 (roadmap M8). An unofficial Flutter client for the Cloudflare Realtime SFU, on `flutter_webrtc`, for Android, iOS, macOS, Windows and the web.

- **Rooms** (`CloudflareRealtime.join`, `Room`, `LocalParticipant`, `RemoteParticipant`) on top of an app-provided `Signaling` interface, with `InMemorySignaling` (in `testing.dart`) for tests and demos. Participants are diffed, and only what is subscribed is pulled.
- **Publishing** the camera, microphone and screen, with mute, camera switching that behaves the same on every platform, and device selection with fallback.
- **Simulcast** (three layers by default) with per-view layer selection, a manual override and opt-in layer pausing; VP8 by default, H.264, VP9 or AV1 per room or publication.
- **Active speaker**, **connection quality** per participant and **typed stats**.
- **Automatic reconnection:** the room replaces a failed or expired SFU session, republishes under the same names and pulls again, with backoff.
- **Screen share** on desktops (a source picker), the web (the browser's picker), Android (MediaProjection under the package's foreground service) and iOS (a Broadcast Upload Extension from the package's templates).
- **Calls on phones:** one audio-route API, a foreground service on Android, interruptions, the proximity sensor, and system calls through Android Telecom and CallKit/PushKit.
- **The screen stays on during video calls** on Android, iOS, macOS, Windows and the web (`RoomOptions.keepScreenAwake`).
- **DataChannels**, reliable and unreliable, that follow participants across sessions.
- **The broker client** (`HttpBrokerClient`, in `broker.dart`) for the broker contract; reference brokers (a Cloudflare Worker and a Supabase Edge Function) live in the repository, not in the package.
- **Safe logging:** the package's log lines and its exceptions' `toString()` carry an error's type and code, never its text; `CloudflareRealtime.logger` (a `CloudflareRealtimeLogger` receiving `CloudflareRealtimeLogRecord`s) sends them, with the full error, to the app's own logging.
- **Release preparation:**
  - The SDK constraint is widened from Dart 3.13 / Flutter 3.47 to **Dart 3.11 / Flutter 3.41**, checked with resolved and downgraded dependencies, and an Android build, on Flutter 3.41.0. Internal constructors no longer use private named parameters (Dart 3.12).
  - The Android plugin builds with the Android templates of older Flutter releases (AGP 8 with the Kotlin Gradle plugin) as well as with AGP 9's built-in Kotlin: it applies the Kotlin Gradle plugin only when built-in Kotlin is off, and sets the JVM target on the compile tasks.
  - README rewritten for pub.dev, with platform setup guides in `doc/` (Android, iOS, macOS, Windows, web), `pubspec.yaml` metadata (`platforms`, `documentation`), a `.pubignore`, and the `public_member_api_docs` lint. `docs/api-review.md` lists the public API and the review's decisions.
  - **The API was cleaned up in one breaking pass** before 0.1.0; [doc/migrating-to-0.1.md](https://github.com/kammcs/flutter-cloudflare-realtime/blob/main/doc/migrating-to-0.1.md) has the old → new table. Observable state is a getter for the value now plus a replaying `…Changes` stream everywhere (`room.participants` / `participantsChanges`, `publication.isMuted` / `mutedChanges`); settings classes end in `Options` (`BrokerOptions`, `ActiveSpeakerOptions`, …); room events are named `Participant…`, `Track…`, `LocalTrack…` or `Room…`; value types, options and events are `final`, and `BrokerException` and `SfuSessionException` are `sealed` for exhaustive `switch`es. `Room.setAudioOutputDevice` throws an `AudioOutputException` (with an `AudioOutputFailure` reason) when the platform refuses the device, instead of the platform's error. The plumbing (`BrokerClient`, `HttpBrokerClient`, the wire models, `SfuSession`) moved to `package:cloudflare_realtime/broker.dart`, and the test seams (`MediaBackend`, `VideoRenderer`, the factories, `InMemorySignaling`) to `package:cloudflare_realtime/testing.dart`.

### Development history

- **Security: the package logs safely by default** (found in an integration review; `docs/design.md` §4.9). Its log lines printed errors in full, for example `cloudflare_realtime: prewarm failed: MissingPluginException(...)`, and an error's text can echo a broker's response body (the app's own data), a URL or a platform message into the device log, which on Android is readable over adb and is often collected by crash reporters. Apps that log carefully couldn't control the package's lines.
  - **One logging seam:** every Dart log line is a `CloudflareRealtimeLogRecord` (`level`, a fixed `message`, the error's `errorType` and `errorCode`; the `error` and `stackTrace` in separate fields) passed to `CloudflareRealtime.logger`, a `CloudflareRealtimeLogger`. The default, `CloudflareRealtime.defaultLogger`, prints `cloudflare_realtime: <message> (<type>, code: <code>)` with `debugPrint`; `CloudflareRealtime.debugLogFullErrors = true` adds the error's text and stack while debugging. Codes come from `PlatformException.code`, a broker error's HTTP status and `errorCode`, the SFU's `errorCode`, `SystemCallException.code`, `AudioOutputException.reason` and a peer connection failure's kind, capped at 64 characters. The 41 log calls (prewarm, call audio, system calls, the screen wake lock, devices, screen share, negotiation timeouts, the platform call timing) go through it; a logger that throws falls back to the default.
  - **Exceptions' `toString()` is log-safe:** `BrokerException` and the SFU's per-track, per-request and per-channel exceptions no longer include `errorDescription`; `MediaException` and `AudioOutputException` show their cause's type, not its text; `SystemCallException` shows its code, not the platform's message. The fields keep the data (`doc/migrating-to-0.1.md`, Exceptions).
  - **Native logs carry no messages:** Android logs an exception's class name instead of its message (13 lines), a system call event's name and call ID instead of its map, and Telecom's disconnect code instead of the whole `DisconnectCause`; iOS logs an `NSError`'s domain and code instead of its description (6 lines), and no longer logs the value of an unknown `ended` reason from a VoIP push. Push payloads, PushKit tokens, caller handles and names, session tokens and SDP were and are never logged.
- **Reference brokers: optional DataChannel rules, and stricter key spellings** (proposed in an integration review; `docs/design.md` §5, Optional DataChannel rules and Key spellings; `broker/README.md`, Optional: DataChannel rules). The SFU forwards a published DataChannel to every subscriber that names it, and the broker checked only that subscriptions stay in the room, so an app that reserves channel names for certain participants had to wrap the handler, read the body again and authenticate twice.
  - **`BrokerConfig.authorizeDataChannels(caller, roomId, sessionId, route, entries)`** (new, optional, unset by default) runs on every `datachannels/*` route (`establish`, `new`, `update`, `close`) after rules 1 to 4 pass, just before forwarding. `entries` (`DataChannelEntry`: `location`, `dataChannelName`, `sessionId`, `canReply`, `id`) are frozen copies taken from the same parsed value the broker forwards, so there is no second parse. `true` forwards; anything else is `403 forbidden`; a throw is `500 internal_error`, its text in neither the response nor `onError`. With the hook set, an entry field of the wrong type is a `400`. Both reference brokers wire it from a new `data_channels.ts`, unset.
  - **Look-alike keys:** `dataChannelName`, `canReply` and `id` join the keys that must be spelled exactly (`400` otherwise), and the check now folds keys the way Go's `encoding/json` does, so `ſessionId` (U+017F) is refused like `SessionId`; before, it reached the SFU without the same-room check, which matters if the SFU's decoder folds keys that way.

- **Fewer video renderer calls, and no blink when a layout change re-creates a view** (a consuming app on macOS 27 saw `videoRendererSetSrcObject` block its UI for 520–830 ms each after mute and camera toggles; `docs/design.md` §4.3, Fewer renderer calls; `doc/macos.md`, Video views). On iOS and macOS `flutter_webrtc` answers the call on the main thread and waits there for libwebrtc's worker thread to add or remove the renderer, so each call costs whatever that thread is busy with (0–48 ms each here with an idle worker thread; the app's 0.5–0.8 s weren't reproduced). The package now makes only the calls a new track needs, measured with the new `renderer_timing_test.dart`:
  - **A view that Flutter re-creates for the same track takes over the renderer** of the view it replaces (kept 500 ms), with no native call and no placeholder in between: a gallery ↔ stage switch without `GlobalKey`s went from 4 `videoRendererSetSrcObject`, 2 creations and 2 releases to none. Views on screen together still have a renderer each.
  - **`FlutterWebrtcVideoRenderer` sends nothing that changes nothing** (the stream it shows, or `null` when it shows none); a release after a detach waits only for what is left of its 250 ms (the renderer crash's mitigation is kept), and a renderer that showed nothing is released without a detach. Unpublishing a camera took 3 calls, now 2.
  - **A view given another source** moves its renderer to the new track in one call instead of a detach and an attach.
  - **No stale frame:** a view shows video only once its renderer has its current track.
  - Unchanged, and necessary: a camera turned off and on costs one call each way on the self-view; a publisher's mute costs remote views nothing.

- **Platform call timing, a debug aid for a frozen UI; a chosen Mac microphone without the device list; `prewarm()`'s limits** (a consuming app on macOS 27 still saw its UI freeze for up to 5.2 s in its first microphone publish; `docs/design.md` §4.2, Finding the blocking call, and §4.5; `doc/macos.md`, Finding what freezes the UI).
  - **`CloudflareRealtime.debugPlatformCallTiming`** (new; `PlatformCallTimingOptions`, `null` by default): times every platform call sent through Flutter's messenger on the chosen channels (`flutter_webrtc`'s by default, every channel with `channels: null`), the app's own `flutter_webrtc` calls included, and the event loop's gaps, and names the calls sent just before or during each gap; it prints them with `debugPrint`, and `debugPlatformCallTimingEvents` has them as typed events (`PlatformCallAnsweredEvent`, `EventLoopGapEvent`, with `PlatformCall` records). It records method names, argument keys and times, never argument values or replies. Calls are named only when the app creates `PlatformCallTimingBinding` first thing in `main` (or wraps its own binding's messenger with `PlatformCallTimingBinding.wrapMessenger`): Flutter's messenger can't be replaced later outside tests; without it, gaps only. Free while off. `join_timing_test.dart` uses it, and the new `first_publish_timing_test.dart` times a first call with camera and microphone against a second device (a browser).
  - **What it found** in a macOS ↔ Chrome repro (the default microphone, the camera, cold starts, 12 runs): the first microphone publish itself froze nothing. The UI froze in `join` (the first peer connection, 2.7–5.7 s), for the first device list when the camera started before or with the microphone (2.0–4.2 s; 0.1 s once the microphone publish had started), and for the camera's `getUserMedia` (0.8–1.0 s). All three are `flutter_webrtc`'s main-thread calls (flutter-webrtc #2217; listing before or after the camera's capture only moves the camera's cost).
  - **Fixed: a chosen Mac microphone no longer lists the devices first.** `publishMicrophone(device:)` (or `setPreferredDevice`) on macOS selects the microphone by its ID, as the default already was; the list was read inside the first microphone publish (2.1 s and 3.1 s with "MacBook Pro Microphone"; none in 2 runs after). A microphone that is gone fails its selection and falls back through the list as before. Still freezing for a microphone other than the system default: the module's rebuild when the package selects it again after the first audio send (3.6–12.3 s), `flutter_webrtc`'s `selectAudioInput` on the main thread.
  - **`prewarm()` is kept, with its limits documented:** it moves the first peer connection's freeze to a moment the app chooses, it doesn't remove it (2.6–3.7 s here; a consuming app measured 5.3 s and 8.9 s right after sign-in), and joins aren't faster (that app measured no gain; here the join's own 3–6 s moved, the publishes took as long). Use it only where a freeze is acceptable, such as behind a launch screen.

- **macOS: no device list during a microphone join, and `CloudflareRealtime.prewarm()` for the first peer connection** (reported from a consuming app on macOS 27: a macOS ↔ Chrome first join still froze its UI for up to about 10 s, twice; `docs/design.md` §4.2 macOS: a slow first join, §4.5 Capture before listing on macOS; `doc/macos.md`). `join_timing_test.dart` now times every `flutter_webrtc` call and names the calls behind each event-loop gap: the two freezes were the first `initialize` + `createPeerConnection` (4.1–6.0 s) and the first `getSources` (4.8–6.9 s), both run on the main thread by the plugin.
  - **A microphone on macOS with no device chosen is captured from the system default (`default`) without listing the devices**, and isn't listed after the capture either: the `getSources` freeze is gone from a microphone join (5 runs: longest gap 3.8–5.7 s, only the peer connection's). The list is read when something needs it (a chosen device, a failed capture, which then falls back through the list as before, a camera, or the app reading or watching the devices). `MediaDeviceList` now enumerates when first used rather than when created.
  - **`CloudflareRealtime.prewarm()`** (new, opt-in, macOS only; does nothing elsewhere) creates the first peer connection at a moment the app chooses and keeps it idle until the next join has its own (closing it first left 2.4–3.1 s in the join). With it, the join froze for nothing (5 runs: no gap over 250 ms; join and publish 17.4–18.4 s against 24–25 s); the prewarm itself still freezes the UI for 4.2–5.1 s. A join waits for a running prewarm before `sessions/new`, so the SFU's session clock never runs during it.
  - **Not fixed by the package:** the 4–6 s of the first peer connection (only moved), the device list's 5–9 s when a camera or a chosen microphone needs it, 2–3 s for the next join after leaving a room (unless the app prewarms again), and 8.3 s after the first publish with a chosen non-default microphone, while the input re-selection waits on the module's rebuild (1 run). They are `flutter_webrtc`'s main-thread calls (flutter-webrtc #2217; the context is in design.md §4.2).
- **Android's ring screen shows the caller's picture, else a monogram** (asked for by a consuming app; `docs/design.md` §4.8, The caller's picture; `doc/android.md`). `SystemCalls.reportIncomingCall` takes `callerImage`, a local `file:` or `content:` URI (the package never downloads; `http(s)` is ignored with a log line). Android decodes it off the main thread, downsampled to the ring screen's 120 dp circle, waiting at most 1 s before the call rings; it is also the caller's icon in the call's notification. Without one, or when it can't be read, the ring screen and the notification show a monogram: up to two initials (graphemes, so emoji and CJK names come out whole) on a colour derived from the name, from the overridable array `cloudflare_realtime_monogram_colors`. iOS ignores the picture: CallKit shows only Contacts photos. The plugin now has JVM unit tests (`android/src/test`) for the monogram.
- **Upgrade note (Android):** if a build after updating the package reports an unresolved reference to one of its Kotlin classes (for example `CallService`), run `flutter clean`: a stale Kotlin incremental cache, seen after the update that added `IncomingCallActivity` (`doc/android.md`, After updating the package).

- **Security: Android system calls no longer show the app over the lock screen, and no other app can answer a call** (found in an integration review; `docs/design.md` §4.8, The ring activity and the lock screen; `doc/android.md`). An incoming ring on a locked Android phone showed the app's launch activity over the lock screen: the package opened that activity from the ring's full-screen intent and its Answer, and set `setShowWhenLocked` / `setTurnScreenOn` on it until the last call ended, so for a typical app the whole app was usable without unlocking (reproduced on a Pixel 10 with Android 16 and on a PIN-locked emulator). And any app could answer a call by intent: the launch activity is exported, and the plugin answered on any intent with its Answer action and a known call ID (on a Pixel 10, `adb shell am start` with that action and the ID answered a ringing call). Fixed: the full-screen intent, the ringing notification's tap and Answer now open the package's own `IncomingCallActivity` (not exported, its own task, out of Recents, plain Android views, no Flutter engine needed), the only screen shown over the lock screen, and only while its call exists. Answer answers the call there, then asks for the unlock (`requestDismissKeyguard`) and opens the app with its plain launch intent only once the keyguard is gone; a cancelled unlock leaves the answered call on that screen (Hang up, Open app) with the app still locked away. Decline ends the call and never unlocks. The plugin no longer sets lock-screen flags on the app's activity or acts on its intents, and the ongoing call's notification opens the app with its plain launch intent (the system asks for the unlock first). Apps change nothing; the ring screen's theme and texts can be overridden. `system_call_test.dart` checks that a forged Answer to the launch activity, in-app and (with its driver) from adb's shell, leaves the call ringing and that the ring activity can't be started from outside.

- **A publish can no longer hang forever** (reported from an app on an iPhone, iOS 27.2: 1 of 14 CallKit answers hung in the microphone publish after the audio session's activation, before `tracks/new`; `docs/design.md` §4.2 Bounded negotiation steps, §4.3 Bounded publish, §4.5 Bounded capture, §4.8). The cause isn't found yet (the leading suspect is WebRTC-SDK's `AVAudioEngine` module blocking its worker thread while CallKit hands over the session); every step is bounded instead. **Capture:** `CameraSource` / `MicrophoneSource` take `captureTimeout` (default 30 s, `DeviceMediaSource.defaultCaptureTimeout`; `null` waits), set for room publishes by the new `RoomOptions.captureTimeout`; a `getUserMedia` that runs over fails the source with `MediaCaptureException` (its `cause` a `TimeoutException`), and a track that arrives later is stopped. Device enumerations stop waiting after `MediaDeviceList.enumerationTimeout` (10 s; a Mac's first one takes up to about 9 s) and fail soft: no error, the platform picks the device. **Negotiation:** the new `SfuSessionOptions.negotiationTimeout` (default 60 s on every platform, leaving room for macOS's slow first `setRemoteDescription`; `null` turns it off) bounds each peer-connection step of an exchange (`addTransceiver`, `createOffer`, `setLocalDescription`, …) and creating the peer connection; one that runs over fails the session with the new `PeerConnectionFailureKind.negotiationTimeout` (the operation throws `SfuSessionFailedException`), so the queue moves on and the room re-sessions and pushes the publish once more; a step that timed out stops holding back `getStats()` and the macOS input selection (`NativeNegotiation.releasingOn`). Each timeout logs the step that stuck (`cloudflare_realtime: setLocalDescription did not complete within 60000 ms`), for the device repro.

- **macOS: a crash after a screen share stopped, a frozen app during the first join and during shares** (found in a consuming app on macOS 27; `docs/design.md` §4.2, §4.3, §4.5 and §10, `doc/macos.md`).
  - **Crash:** `flutter_webrtc`'s Darwin video renderer queues a main-queue block per frame that dereferences the renderer without a nil check, so releasing a renderer while frames still arrive could crash the app (`EXC_BAD_ACCESS` at `0x40` in `-[FlutterRTCVideoRenderer renderFrame:]_block_invoke_2`; macOS and iOS). `FlutterWebrtcVideoRenderer.dispose` now detaches the stream, waits for the plugin, lets the last frames' blocks run (250 ms), then releases it. Reproduced with the new `example/integration_test/screen_share_stress_test.dart`: with the old release it crashed at the first stop in 3 of 3 runs that kept the main thread busy (and once in 109 iterations without); with the fix, not in 212 iterations (132 of them with the busy main thread).
  - **Frozen during the first join:** on a Mac, the first audio publish starts Apple's voice processing, which held libwebrtc's worker thread for 3–27 s in the measured joins, and the Room's `getStats()` polls waited for it on the main thread (the Dart UI thread on macOS), freezing the app. Native `getStats()` calls, and the macOS microphone selections, now wait until no description is being applied: the event loop's longest gap during that step fell from 13–15 s to under 0.5 s. The join itself is no faster: the three slow steps (module start, AVFoundation's device list, voice processing) are WebRTC-SDK's, `flutter_webrtc`'s and Apple's, documented with the numbers in `doc/macos.md`.
  - **Frozen during a share:** while a desktop share ran, the source watcher called `updateSources` every 3 s, which on macOS lists every window and renders every thumbnail on the main thread (2–7 s each on a loaded Mac). It now re-scans only while the operating system reports no geometry for the shared source (so a closed window still ends the share). In a 200 s share: 127 re-scans before (up to 3.0 s each; up to 7.4 s under heavy load), none after. A freeze of about 105 s, as reported, wasn't reproduced in 200 s shares or nearly 400 short ones.

- **iOS: a launch hook for system calls** (`docs/design.md` §4.8, Launch; `doc/ios.md`). `CloudflareRealtimePlugin.handleLaunch()` (`import cloudflare_realtime`, Swift Package Manager or CocoaPods) restores the CallKit provider and the PushKit registry from `application(_:didFinishLaunchingWithOptions:)`, as Apple asks for VoIP pushes, instead of only when a Flutter engine registers the plugin, which in a UIScene app, with an engine started later or in add-to-app can come after the launch. Idempotent, needs no engine (events wait for Dart), and does nothing until the app has configured system calls or registered for VoIP pushes. Defensive: in a field test on an iPhone (iOS 27.2) iOS launched a killed app with its scene connected, and CallKit had the call 0.77 s after the push. The example's `AppDelegate` calls it. RunnerTests cover the hook before any registration, calling it twice plus registrations (one provider, one registry), no persisted state, and a push at launch reaching the first engine that listens.
- **iOS: a VoIP push for a call that already ended stays ended** (found in a field report; `docs/design.md` §4.8, Pushes for calls that ended). When the app ended a ringing call itself (its own ring timeout, `end(unanswered)`) and the server's cancel push came later, the package didn't know the ID and reported a stand-in call that flashed and could add a Recents entry; the call's own push after a local end would ring again. The package now remembers every call that ends (the last 64, whoever ended it, with any reason), and a push for one of them, ring or cancel, never rings and raises no event: it is reported under the call's own UUID, as iOS requires. CallKit refuses that while it remembers the call, so a quick or duplicate push is silent; but on the Simulator it forgets within 2 s (at once after an end action), and then the report is a call ended at once, which can still flash for an instant. So the field report's late cancel (~8 s) can't be made silent by the package; `doc/ios.md` tells servers not to cancel on the device that ended the call. RunnerTests cover a cancel right after and 3 s after the app's own `unanswered`, a ring push after a `local` end, and that every end is remembered.
- **System calls: a ringing call the system ends is no longer reported as declined on Android** (found in an integration review; `docs/design.md` §4.8, Who ended a ringing call). An app that tells its server "declined" on `SystemCallEndReason.declined` could mark a call declined that the user never saw. On Android, Telecom disconnecting a ringing call (to make room for an emergency call or a phone call the user places, or a companion app ending it) arrived as `LOCAL` below Android 14 and was reported as `declined`; it is now `failed`, as Android 14+ already reported it (Telecom's own cause, `UNKNOWN`). Telecom's reject (a headset, a car or a watch declining) stays `declined`, and so do the package's own Decline and `SystemCall.end()`. On iOS, CallKit reports the user's Decline and its own end of a ringing call (another call taking over, or the Simulator, which has no call UI, about 0.9 s after the report) as the same `CXEndCallAction`, with nothing that says who asked, so both stay `declined`. This is now documented, not guessed with a timing rule. No API change: the docs of `declined` and `failed` say what each means on each platform, and `failed` now says it covers the system ending a call. Tests: a RunnerTest records CallKit's own end on the Simulator. `system_call_test.dart` ends a ringing call from Telecom's side with a companion `InCallService` in the example (debug builds; the driver allows its `MANAGE_ONGOING_CALLS` app op). On the Pixel 10 its reject was `declined` and its disconnect was `failed`. A Dart test checks that a system-ended ringing call keeps the native reason. `Room.attachSystemCall`'s `endWhenLeft` now ends a call that still rings unanswered `failed` instead of `SystemCall.end()`'s default `declined` (a room leaving on an error isn't a decline); an answered call still ends `local`.
- **Display and window geometry for screen-share sources** (desktop; `docs/design.md` §10, Display and window geometry). `ScreenSource.geometry` is a new `ScreenGeometry` (`bounds`, `scaleFactor`, `isPrimary`) on macOS and Windows, `null` elsewhere or when the OS can't say; `ScreenShareSource.sourceGeometry` / `sourceGeometryChanges` follow the shared display or window while sharing (polled every `geometryWatchInterval`, 500 ms). Bounds are in each OS's own desktop coordinates: Core Graphics points on macOS (origin at the primary display's top-left, y down), physical virtual-screen pixels on Windows; displays left of or above the primary are negative. Read through `dart:ffi` (Core Graphics; user32, shcore and dwmapi), mapping `flutter_webrtc`'s source IDs: on macOS a `CGDirectDisplayID` or `CGWindowID`, on Windows an `HWND` or libwebrtc's `EnumDisplayDevices` index. `DesktopCapturerBackend` gained `geometryOf(source)` (breaking for custom implementations; fakes can answer `null`). Verified on macOS by `example/integration_test/screen_geometry_test.dart` (in the App Sandbox, without an entitlement) against Flutter's display list and the app's own window, and outside the sandbox against `NSScreen` and the window server; **Windows is unverified on a device** (unit tests with fakes, and the real bindings run on the CI's Windows host).
- **iOS: VoIP cancel pushes stop a ring** (found in an integration review; `docs/design.md` §4.8, `doc/ios.md`). A second VoIP push for a call that should stop ringing (the caller hung up, another device answered) was reported again and refused by CallKit as a duplicate, with no event, so the call kept ringing; and when that push launched a killed app, it rang as a new call. A push with the reserved key `ended` (a `SystemCallEndReason` name: `remoteEnded`, `answeredElsewhere`, `declinedElsewhere`, `unanswered`, `failed`; anything else is taken as `remoteEnded`) now ends the call `id` with that reason and the `ended` event. For a call the package doesn't have, it reports a stand-in and ends it at once, with no event, since iOS requires a report for every VoIP push. A call this device already took ends only for `remoteEnded` or `failed`. The last 64 cancelled IDs are remembered, so the call's own push arriving after its cancel doesn't ring. `ended` isn't part of `SystemCall.payload`. Android has no VoIP pushes: the docs show the FCM handler ending the call with `SystemCall.end(reason)`. RunnerTests cover the parsing and each case on the Simulator; the device check needs APNs.

- **Fixed: a network change didn't cut short a re-session attempt stuck on the old network** (found in the checkpoint's real Ethernet drop on a Mac; `docs/design.md` §8.1, A network change during an attempt). The attempt's `sessions/new`, started while offline, hung until the broker timeout (15 s), so media came back 6.9 s after the link while the signaling rejoined in 4 ms. A network change now abandons an attempt that is still waiting for its new session or for that session to connect, and starts the next one at once: `RoomReconnectAttemptEvent.restarted` (new, default `false`), no backoff wait, no error event. A session that arrives late is closed with nothing on it (forgotten in the broker client, peer connection closed), and a late failure is ignored. Attempts moving tracks or announcing aren't abandoned, since their requests could land after the next attempt's; a change then makes the next attempt, if needed, skip its backoff wait (the Open item from the diagnostics entry below). Abandoned attempts count against the backoff's limits. `leave()` no longer waits for a hung `sessions/new`. The example logs `attempt N (…): network changed, attempt N-1 abandoned, no backoff`.

- **Fixed: the announced simulcast size could be landscape for a portrait iPhone video** (`docs/design.md` §6.3). An iPhone's `media-source` keeps the sensor's landscape size (1280×720) while its layers are sent rotated (720×1280); while no layer qualified for the size (`a` and `b` paused, `c` limited by `bandwidth`), the room fell back to the `media-source` and announced 1280×720. The fallback now takes its orientation from the lowest sending layer (only the orientation, so the quality scaler's size still never counts). `publish_quality_test` now checks the announcement's aspect against the layers being encoded throughout the test.

- **Fixed: the announced simulcast size missed libwebrtc's CPU adaptation** (found in a Mac ↔ Pixel `cross_device_test`; `docs/design.md` §6.3). Once a session has pulled a video, the SFU renumbers the pushed codec in its answer but leaves the RTX `apt` at the offered number, which libwebrtc rejects. - **Screen share on iOS** (`docs/design.md` §10, roadmap M9):
  - `ScreenShareSource.start()` and `LocalParticipant.publishScreen()` work on iOS, without a source: the system's broadcast picker is the picker, and the call completes once the user taps **Start Broadcast**. The capture runs in a Broadcast Upload Extension in the app, which the package ships as templates (`ios/broadcast_extension/`); the README's "iOS screen share setup" walks through adding the target, the App Group and the `Info.plist` keys.
  - The setup is checked before each share: if anything is missing, the share doesn't start and reports a `ScreenShareSetupException` with `problems` (`BroadcastSetupProblem`) and `guidance`.
  - The picker can't report a cancel, so a broadcast not started within `ScreenShareOptions.broadcastStartTimeout` (60 s) makes `start()` return `false`, as a cancelled picker does elsewhere. A broadcast stopped from the status bar or Control Center ends the share with `ScreenShareEndReason.userStopped`.
  - `ScreenShareOptions.broadcastScale` (0.5) sets how much the extension scales the screen down; `frameRate` caps its frames. Screen audio (`captureAudio`) isn't supported on iOS and is ignored.
  - `MediaBackend.broadcastExtension` (a new `BroadcastExtensionBackend`) is the seam for it. Custom `MediaBackend`s must implement it (return `null` where none is needed).
  - Example: a `BroadcastExtension` target built from the templates, and **Share screen** on iOS; `screen_share_test.dart` and the screen mode of `cross_device_test.dart` run on an iPhone (with a person to tap "Start Broadcast").
- **Screen share on Android** (`docs/design.md` §10, roadmap M9):
  - `ScreenShareSource.start()` and `LocalParticipant.publishScreen()` work on Android, without a source: the system's consent dialog is the picker. A cancelled dialog returns `false` (`publishScreen` throws a `MediaCaptureException`), like a cancelled browser picker.
  - The package's Android plugin runs the share under its own foreground service of type `mediaProjection`, started after consent and before the capture, as Android 14+ requires. Its manifest declares the service and the `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PROJECTION` and `POST_NOTIFICATIONS` permissions, which merge into the app. The notification has a **Stop sharing** action; the package asks for the notification permission once per launch on Android 13+, and the share works without it.
  - A share stopped from the system (the status-bar chip) or from the notification ends with `ScreenShareEndReason.userStopped`, and the room unpublishes it.
  - `ScreenShareSource.usesSystemPicker`: `true` on the web and Android, where the browser or the system picks what to share. `usesBrowserPicker` stays web-only.
  - `MediaBackend.screenCaptureService` (a new `ScreenCaptureServiceBackend`) is the seam for the consent dialog and the service. Custom `MediaBackend`s must implement it (return `null` where none is needed).
  - Screen audio (`captureAudio`) isn't supported on Android and is ignored.
  - Example: on Android, **Share screen** goes straight to the consent dialog; `integration_test/screen_share_test.dart`.
- The same camera behaviour on every platform:
  - **The front camera opens by default.** `CameraOptions.facing` now defaults to `CameraFacing.user`, and cameras facing that way are tried first (Android lists its back camera first, so the back camera used to open). Pass `facing: null` for the platform's order.
  - **`CameraSource.switchCamera()` and `LocalParticipant.switchCamera()`:** one call that flips front ↔ back on phones and moves to the next camera elsewhere (virtual cameras last). A published camera keeps its track and sender, so subscribers see the new camera without pulling again.
  - `MediaDevice.facing` says which way a camera faces, from the platform (Android, iOS) or the label (browsers); `CameraSource.currentFacing` for the camera in use. `CameraFacing` moved to `media_types.dart` (still exported from the package).
  - `ParticipantVideoView` no longer mirrors a back camera's self-view by default.
  - On iOS, the plain cameras come first: iOS lists its virtual multi-camera devices ("Back Triple Camera") first, and `flutter_webrtc` gets no frames from them, so switching to the back camera sent nothing. Apple's built-in cameras are now ordered by the index in their ID.
  - Example: a **Switch camera** button on the call screen, and `integration_test/camera_switch_test.dart`.
- The same call audio on every phone (`docs/design.md` §4.6):
  - **Audio routes:** `Room.audioRoutes`, `currentAudioRoute` / `audioRouteChanges` and `selectAudioRoute(route)`. `AudioRoute` has an `id`, a `kind` (`speaker`, `earpiece`, `wiredHeadset`, `bluetooth`, `usb`, `other`) and a `name`. The list is the same on Android and iOS, and shows only routes the platform will honour (no earpiece while Bluetooth is connected). The current route is read back from the platform. `canSelectAudioRoute` is `false` on desktops and the web.
  - **The default follows the call:** a voice call starts on the earpiece and moves to the speaker once the call has video (sent or received). Before, iOS used the earpiece even for video, while Android always used the speaker. A connected headset comes first, and a route the user picked sticks until a new headset connects or the route goes. `RoomOptions.speakerphone` (`null` by default) can force the speaker (`true`) or the earpiece (`false`); `Room.setSpeakerphone(on)` does the same mid-call, and `speakerphone` / `speakerphoneChanges` report it.
  - **The package is now a Flutter plugin**, with a small native layer on Android (`setCommunicationDevice` on Android 12+, speakerphone and Bluetooth SCO before that) and on iOS (AVFoundation). On Android it turns off flutter_webrtc's own audio routing (AudioSwitch), which re-picked a route on every device change; flutter_webrtc's Android list of audio outputs is empty as a result.
  - **Bluetooth on Android 12+** needs the app's `BLUETOOTH_CONNECT` permission (declared and requested at runtime); without it, Bluetooth routes are missing. The example asks for it before joining.
  - **Choosing a microphone works on Android.** The Android plugin ignored the microphone named in `getUserMedia` (it only reported it back), so `MicrophoneSource.setPreferredDevice` changed nothing; the backend now selects it first.
  - Example: an audio route button on the call screen (phones), with a sheet of routes; `integration_test/audio_routing_test.dart`.

- Fixes from the first runs against the real SFU (Windows):
  - Offers and answers no longer carry stray receive-only audio and video m-lines: native `flutter_webrtc` adds them unless `createOffer`/`createAnswer` get explicit empty constraints.
  - Negotiated DataChannels open on Windows: the plugin never reports their `open` state, so the package reads it from `getStats()`. Closing a session no longer logs `dataChannelClose() peerConnection is null`.

  - `setPreferredRid` right after a pull retries while the SFU isn't forwarding the track yet (`SfuSessionOptions.layerUpdateRetryTimeout`, 10 s).
  - On Windows and Linux, at most 8 ICE server URLs reach `flutter_webrtc` (its desktop plugin overflows a fixed array beyond that).
- Fixes from the first runs against the real SFU on Android (a Pixel 10, Android 16):
  - Publishing works on Android: every push failed with "the transceiver has no mid", because the Android plugin replaces a transceiver's ID with its mid after negotiation. The package now finds its transceiver by the sender's ID, and stops a negotiated transceiver through its current entry, which the iOS and macOS plugin (whose transceiver ID is the mid) needs too.
  - Android doesn't report negotiated DataChannels as open either; the `getStats()` fallback from the Windows fix covers it (no change needed). The 8-ICE-server limit stays desktop-only.
- Fixes from the first runs against the real SFU on macOS (a MacBook Pro, macOS 27):
  - The camera captures at the requested preset on macOS and iOS: the Darwin plugin ignored `width: {ideal: 1280}` (it reads `ideal` only as a string), so the camera opened at its smallest format with a frame rate of 0, and a MacBook sent 640×480 in two simulcast layers instead of 1280×720 in three. Native platforms now get bare numbers, which every plugin reads; Android, which never read `ideal` either, captured 1280×720 whatever the preset; on a Pixel 10, 360p and 540p presets now capture 640×360 and 1024×576. Browsers still get `{ideal: n}`.
  - The loopback, DataChannel echo and reconnect integration tests, and cross-device calls with Windows and with Android, pass with no other change.
