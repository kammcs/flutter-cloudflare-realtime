## Scope: telecom, videoconferencing and screen sharing

**Decided (October 2026).** The package aims to give apps every *primitive* they need for phone-style calls, video conferences and screen sharing, through **one Dart API** that behaves the same on Android, iOS, macOS, Windows and the web (see [Same behaviour on every platform](#same-behaviour-on-every-platform)). It does not provide app structure: no UI beyond the video view and the pickers, no signaling server, no push delivery. Where a primitive needs native code, it goes in this package (it is a Flutter plugin since the audio routes work, [design.md §4.6](design.md#46-call-audio-routing-native)). Where something has to live in the host app (an iOS app extension, Info.plist keys, a foreground-service declaration), the package ships the code to copy and a setup guide, and the API reports what's missing instead of failing silently.

The gaps against that scope, as milestones. M8 (pub.dev) comes after M9–M13.

## Running the device tests (notes from the October 2026 runs)

[checkpoint.md §7](checkpoint.md#7-integration-tests-against-the-dev-server) is the runbook; these are the lessons that aren't obvious from it:

- **Phones: pass `--no-uninstall`.** Otherwise `flutter test` deletes the app after every file and the camera, microphone and Local Network permissions go with it.
- **iOS:** the first run asks for Local Network, and nothing connects until it is allowed. *The Dart VM Service was not discovered after 60 seconds* is usual: Flutter finds the app over Bonjour, which took 2.5–3 minutes per run on the Mac used. A tool or terminal without Bonjour (Local Network) access on the Mac never finds it. A run that fails with *Connection refused* on `127.0.0.1` after the phone was reconnected needed the cable unplugged and plugged back in, with the phone unlocked. The white screen during a test is normal: the tests draw nothing.
- **Use the Xcode version the project is pinned to** for Apple builds. With several installed, set `DEVELOPER_DIR` for the command instead of changing the system selection, and delete `example/build/ios` (or `build/macos`) when switching.
- **Both sides of `cross_device_test.dart` from one machine:** start both `flutter test` runs from one script in parallel (a short stagger between them), not one after the other; each side waits 5 minutes for the other.
- **Checking audio on Android from outside the app:** `adb shell dumpsys audio` (*Actual mode*, *Active communication device*) shows the call mode and output route; `adb shell dumpsys media.audio_flinger` (*Input device*) shows which microphone is capturing.
- **Ask for permissions before joining** in tests on phones: the SFU drops a session left unused while a first-run prompt waits (see M10).

## Consumer checkpoint (week 6)

**At week 6 of this work**, the first consumer (buildIt.Social) makes a go/no-go call. It continues on this package only if all three of these hold:

1. **Calls work:** a 1:1 **and** a 4-person call on **Windows, macOS and Android**.
2. **Simulcast layer switching** works.
3. **Recovery:** a call recovers from a network drop.

If any fails, that app switches to LiveKit behind its own `VideoProvider` interface, and this package continues as a side project.

**So prioritize M1–M4 plus a basic M5 and a desktop-only M6 path over polish.** The example app should be able to demonstrate all three criteria. **[checkpoint.md](checkpoint.md) is the runbook** for demonstrating them with the example app and the dev server.

## Same behaviour on every platform

A goal for the whole package ([design.md §2](design.md#2-goals-and-non-goals)): the basic camera and audio calls do the same thing on every OS, so apps don't branch on the platform.

- **Camera (done, verified on Android, macOS and iOS):**
  - the front camera opens by default (`CameraOptions.facing`);
  - the preset's resolution is honoured (it wasn't on Darwin or Android);
  - `switchCamera()` flips front ↔ back on phones and cycles through cameras elsewhere, without renegotiating;
  - the self-view is mirrored except for a back camera.
  
  `example/integration_test/camera_switch_test.dart` checks this on each device.
- **Audio (done, verified on Android, iOS and macOS):**
  - the speaker/earpiece default is the same on both phones (it was the loudspeaker on Android and the earpiece on iOS, even with video);
  - choosing a microphone works on Android (it was silently ignored there).
- **Audio routes (done, verified on a Pixel 10 and an iPhone; [design.md §4.6](design.md#46-call-audio-routing-native)):**
  - one route list on both phones (`audioRoutes`, `currentAudioRoute`, `selectAudioRoute`);
  - voice calls start on the earpiece and move to the speaker when video starts;
  - a route the user picked sticks;
  - a small native layer (the package becomes a Flutter plugin for Android and iOS), which takes Android's call audio routing over from flutter_webrtc;
  - `BLUETOOTH_CONNECT` in the example.
  
  Later: Apple's route picker as an optional widget (M14), and checks with Bluetooth and wired headsets on devices (M13).
- **CallKit (iOS) and Android Telecom (planned soon):** see M11.
- **Still to do for the camera:** the web (labels decide which way a camera faces there); see M13.
- **A publish that waits on a permission prompt:** see M10.
