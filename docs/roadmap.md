## Scope: telecom, videoconferencing and screen sharing

**Decided (October 2026).** The package aims to give apps every *primitive* they need for phone-style calls, video conferences and screen sharing, through **one Dart API** that behaves the same on Android, iOS, macOS, Windows and the web (see [Same behaviour on every platform](#same-behaviour-on-every-platform)). It does not provide app structure: no UI beyond the video view and the pickers, no signaling server, no push delivery. Where a primitive needs native code, it goes in this package (it is a Flutter plugin since the audio routes work, [design.md §4.6](design.md#46-call-audio-routing-native)). Where something has to live in the host app (an iOS app extension, Info.plist keys, a foreground-service declaration), the package ships the code to copy and a setup guide, and the API reports what's missing instead of failing silently.

The gaps against that scope, as milestones. M8 (pub.dev) comes after M9–M13.

### M14 notes: picture-in-picture and the iOS camera in the background

Researched in October 2026 (not built yet). Today an iPhone call keeps its audio in the background but its camera pauses (`LocalCameraPausedEvent(background)`, [design.md §4.7](design.md#47-calls-outside-the-foreground-background-interruptions-proximity-native)); subscribers see a frozen frame.

**Platform rules.**
- iOS forbids the camera in the plain background ("Camera usage is prohibited while in the background", `AVCaptureSession.InterruptionReason.videoDeviceNotAvailableInBackground`). The one way to keep it is a **video-call picture-in-picture window** plus **multitasking camera access**, as FaceTime does on the Home Screen.
- `AVCaptureSession.isMultitaskingCameraAccessSupported` (iOS 16+) is `true` for an app **linked against iOS 18+ with `voip` in `UIBackgroundModes`**, for an iPad with Stage Manager on an external display, or for an app with the `com.apple.developer.avfoundation.multitasking-camera-access` entitlement. The app then sets `isMultitaskingCameraAccessEnabled = true` on the capture session (default `false`).
- So on **iOS 18 and later no Apple entitlement is needed**: the host app adds `voip` next to `audio` in `UIBackgroundModes` (an `Info.plist` change; no capability or provisioning change). App Review expects an app that declares `voip` to do real calling, which a calling app does (and CallKit, M11, needs it anyway).
- **iPhones on iOS 16–17** need the entitlement, which Apple grants slowly (forum reports range from weeks to over a year) and only to VoIP apps. Plan: document them as unsupported and report the camera paused there, as today.
- While PiP shows, hiding (stashing) the PiP window interrupts the camera again (`background`), and Camera.app taking the camera gives `inUseByAnotherApp`; `CallBackground.swift` already reports both.
- A video-call PiP needs an `AVSampleBufferDisplayLayer`-backed view inside `AVPictureInPictureVideoCallViewController`, `AVPictureInPictureController.ContentSource(activeVideoCallSourceView:contentViewController:)`, `canStartPictureInPictureAutomaticallyFromInline` (to start it on going Home), and the `audio` background mode. The window takes no touches; the content source is cleared when the call ends. Its content must be a native view, not a Flutter texture, so the package feeds WebRTC frames into it natively.

**flutter_webrtc 1.6.2 (MIT)** has neither PiP nor multitasking camera access. `FlutterWebRTCPlugin.sharedSingleton` exposes `trackForId:peerConnectionId:` (local and remote tracks) and the camera capturer; it already has an `AVSampleBufferDisplayLayer` renderer converting I420 frames; its `Package.swift` exports a `WebRTC` product for dependent plugins. WebRTC m150's `RTCCameraVideoCapturer` (BSD-3) shares one static `AVCaptureMultiCamSession` on multi-camera iPhones, configured on `RTCDispatcher`'s capture queue. Prior art: Stream's MIT fork of flutter_webrtc re-applies the multitasking flag to each new capture session (portable with a notice); Stream's video SDK (proprietary) and LiveKit's SDK are concepts only.

**Design.**
- **Dart (off by default):** `RoomOptions.pictureInPicture` (`PictureInPictureOptions?`: `startAutomatically`, `keepCameraRunning`, `showLocalWhenAlone`); `Room.canPictureInPicture`, `canKeepCameraInBackground`, `pictureInPictureActive` / `pictureInPictureChanges`, `startPictureInPicture()`, `stopPictureInPicture()`, `pinPictureInPicture(participantId)`; `PictureInPictureStartedEvent` / `PictureInPictureStoppedEvent`, `RoomErrorEvent('pictureInPicture', …)`. The window shows the pinned participant, else the active speaker, else the first remote camera, else the local camera, and asks for a low simulcast layer (`LayerDemandReporter`).
- **Native (this package's iOS plugin):** link WebRTC through flutter_webrtc (its `WebRTC` product with Swift Package Manager; `s.dependency 'flutter_webrtc'` in the podspec); reach flutter_webrtc's plugin through the Objective-C runtime (its headers include C++); `MultitaskingCamera` sets the flag on each capture session as it starts (on WebRTC's capture queue); `PictureInPictureVideoView`, an `RTCVideoRenderer` on an `AVSampleBufferDisplayLayer` that converts and downscales frames (to about 640 px) and renders only while PiP is active; `PictureInPicture`, the controller (the Flutter root view as the source view) and its method and event channels.
- **The host app** adds `voip` to `UIBackgroundModes`. The README's iOS background section documents it.
- **Android PiP** (the activity's PiP mode) fits the same Dart API; Android already keeps the camera through the call's foreground service.

**Steps.** (1) The build plumbing first, the riskiest part: depend on flutter_webrtc's WebRTC from our `Package.swift` and podspec, and prove both Swift Package Manager and CocoaPods builds. (2) `MultitaskingCamera.swift`. (3) Track lookup. (4) `PictureInPictureVideoView.swift` (MIT notice if flutter_webrtc's conversion code is ported). (5) `PictureInPicture.swift` and the channels. (6) The Dart API, events and room wiring, with unit tests on a fake backend. (7) Native tests (frame conversion, track lookup) in `RunnerTests`. (8) Devices: extend `background_test.dart` and the cross-device run so that a Pixel's received frames keep rising for 20 s while the iPhone is on the Home Screen. (9) The example app: `voip` in its `Info.plist`, the option on. (10) design.md §4.7 (it says the package doesn't reconfigure flutter_webrtc's session; that changes), the README.

**Checks by hand (iPhone with a Pixel):** going Home shows PiP and the Pixel keeps getting live camera; stashing the window pauses and then resumes the camera; opening Camera.app reports `inUseByAnotherApp`; returning to the app closes PiP with live video in the app; locking the screen; with "Start PiP Automatically" off in Settings, no PiP and a paused camera.

**Risks.** CocoaPods may not expose WebRTC to our Swift code (fallback: an unpinned `WebRTC-SDK` dependency); Swift Package Manager relies on the Flutter tool rewriting the `flutter_webrtc` path. Setting the flag on a session that is already running may stall it briefly; whether `AVCaptureMultiCamSession` honours it is unverified. flutter_webrtc's selectors aren't public API (re-test on every upgrade). H.264 encoding in the background is unverified (VP8, the default, is software). Frame conversion costs CPU and heat, which can trigger system-pressure pauses. On iOS 16–17 iPhones subscribers still see a frozen frame.

**Sources.** Apple's documentation for `isMultitaskingCameraAccessSupported`, `isMultitaskingCameraAccessEnabled`, the multitasking-camera-access entitlement, "Adopting Picture in Picture for video calls", "Accessing the camera while multitasking on iPad", `videoDeviceNotAvailableInBackground` and `AVPictureInPictureController`; WWDC22 session 110429; Apple developer forum threads 720109, 698187 and 772526; GetStream/webrtc-flutter PR #88; flutter-webrtc issue #1193; webrtc-sdk/webrtc `m150_release` `RTCCameraVideoCapturer.m`.

## Running the device tests (notes from the October 2026 runs)

[checkpoint.md §7](checkpoint.md#7-integration-tests-against-the-dev-server) is the runbook; these are the lessons that aren't obvious from it:

- **Phones: pass `--no-uninstall`.** Otherwise `flutter test` deletes the app after every file and the camera, microphone and Local Network permissions go with it.
- **iOS:** the first run asks for Local Network, and nothing connects until it is allowed. *The Dart VM Service was not discovered after 60 seconds* is usual: Flutter finds the app over Bonjour, which took 2.5–3 minutes per run on the Mac used. A tool or terminal without Bonjour (Local Network) access on the Mac never finds it. A run that fails with *Connection refused* on `127.0.0.1` after the phone was reconnected needed the cable unplugged and plugged back in, with the phone unlocked. The white screen during a test is normal: the tests draw nothing.
- **Use the Xcode version the project is pinned to** for Apple builds. With several installed, set `DEVELOPER_DIR` for the command instead of changing the system selection, and delete `example/build/ios` (or `build/macos`) when switching.
- **Both sides of `cross_device_test.dart` from one machine:** start both `flutter test` runs from one script in parallel (a short stagger between them), not one after the other; each side waits 5 minutes for the other.
- **Checking audio on Android from outside the app:** `adb shell dumpsys audio` (*Actual mode*, *Active communication device*) shows the call mode and output route; `adb shell dumpsys media.audio_flinger` (*Input device*) shows which microphone is capturing.
- **Ask for permissions before joining** in tests on phones. Since M10 part A a late first publish survives (the room connects its session at join), but a first-run prompt still adds its wait to the test's timeouts.

## Consumer checkpoint (week 6)

**At week 6 of this work**, the first consumer (buildIt.Social) makes a go/no-go call. It continues on this package only if all three of these hold:

1. **Calls work:** a 1:1 **and** a 4-person call on **Windows, macOS and Android**.
2. **Simulcast layer switching** works.
3. **Recovery:** a call recovers from a network drop.

If any fails, that app switches to LiveKit behind its own `VideoProvider` interface, and this package continues as a side project.

**So prioritize M1–M4 plus a basic M5 and a desktop-only M6 path over polish.** The example app should be able to demonstrate all three criteria. **[checkpoint.md](checkpoint.md) is the runbook** for demonstrating them with the example app and the dev server.

## Same behaviour on every platform

A goal for the whole package ([design.md §2](design.md#2-goals-and-non-goals)): the basic camera and audio calls do the same thing on every OS, so apps don't branch on the platform.

- **Camera (done, verified on Android, macOS and iOS):**
  - the front camera opens by default (`CameraOptions.facing`);
  - the preset's resolution is honoured (it wasn't on Darwin or Android);
  - `switchCamera()` flips front ↔ back on phones and cycles through cameras elsewhere, without renegotiating;
  - the self-view is mirrored except for a back camera.
  
  `example/integration_test/camera_switch_test.dart` checks this on each device.
- **Audio (done, verified on Android, iOS and macOS):**
  - the speaker/earpiece default is the same on both phones (it was the loudspeaker on Android and the earpiece on iOS, even with video);
  - choosing a microphone works on Android (it was silently ignored there).
- **Audio routes (done, verified on a Pixel 10 and an iPhone; [design.md §4.6](design.md#46-call-audio-routing-native)):**
  - one route list on both phones (`audioRoutes`, `currentAudioRoute`, `selectAudioRoute`);
  - voice calls start on the earpiece and move to the speaker when video starts;
  - a route the user picked sticks;
  - a small native layer (the package becomes a Flutter plugin for Android and iOS), which takes Android's call audio routing over from flutter_webrtc;
  - `BLUETOOTH_CONNECT` in the example.
  
  Later: Apple's route picker as an optional widget (M14), and checks with Bluetooth and wired headsets on devices (M13).
- **CallKit (iOS) and Android Telecom (M11, Dart layer and Android done):** one `SystemCalls` API; desktops and the web keep the calls in Dart with the same events. See [design.md §4.8](design.md#48-system-calls-callkit-and-android-telecom-native).
- **Still to do for the camera:** the web (labels decide which way a camera faces there); see M13.
- **A publish that waits on a permission prompt:** see M10.
