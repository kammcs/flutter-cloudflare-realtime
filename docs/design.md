# Design: `cloudflare_realtime`

This package is a Flutter client for the [Cloudflare Realtime SFU](https://developers.cloudflare.com/realtime/sfu/). It is built on [`flutter_webrtc`](https://pub.dev/packages/flutter_webrtc) and targets **Android, iOS, macOS, Windows and Web**.

- **Status:** pre-release (October 2026). Implemented and unit-tested: the broker client and reference brokers (§4.1, §5), the SFU session with DataChannels (§4.2, §9), rooms (§4.3), signaling (§4.4), media and screen capture on desktop, web, Android and iOS (§4.5, §10), simulcast layer selection (§6), publisher-side layer pausing (opt-in), the captured-size announcement and the codec option (M12 part B, §6.2, §6.3), active speaker, typed stats and connection quality (§7, §7.1), reconnection (§8), call audio and background behaviour on phones (§4.6, §4.7), and system calls (CallKit and Telecom, §4.8). Verified against the real SFU on Windows, Android, macOS and iOS, and on the web in Chrome, Firefox and Safari 27 (in Safari, screen share and the output choice need a user gesture, which the tests can't give). The week-6 checkpoint ([checkpoint.md §6](checkpoint.md#6-results)) is complete and passes: Windows ↔ macOS, Windows ↔ Android and macOS ↔ Android calls, a 4-person call (Windows, macOS, a Pixel 10 and an iPhone), layer switching, and real network drops on Windows, macOS and Android. System calls (M11) are verified on Android and iOS, by test and by hand; VoIP pushes with APNs and headset buttons are still to check. iOS screen share (M9) is verified on an iPhone, iPhone → Mac included. Linux isn't supported. The pub.dev release (M8) waits until the first consumer has validated the package; [roadmap.md](roadmap.md#open-gaps) lists what's still open.
- **Companion docs:**
  - [cloudflare-sfu.md](cloudflare-sfu.md): what the SFU API provides.
  - [roadmap.md](roadmap.md): build order and milestones.

## 1. Why this package exists

The Cloudflare SFU is plain WebRTC media forwarding, controlled by an HTTPS sessions/tracks API. Cloudflare ships no Flutter client for it:

- **RealtimeKit's Flutter SDKs** (`realtimekit_core`, `realtimekit_ui`) were discontinued on pub.dev in August 2026. They only ever supported Android and iOS.
- The reference client is **partytracks**, a TypeScript/RxJS library. It is licensed ISC, and it lives in [`cloudflare/partykit`](https://github.com/cloudflare/partykit/tree/main/packages/partytracks). **It is the blueprint for this package.** When code is ported from it, keep its notice in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).
- A second reference is **Cloudflare Meet** (formerly Orange Meets), a full meeting app: <https://github.com/cloudflare/meet>.

**The SFU has no concept of rooms or presence.** Cloudflare calls a room "application state". This package provides the client side of rooms, and **the app brings its own signaling** through an interface (§4.4).

## 2. Goals and non-goals

**Goals:**
- Publish camera, microphone and screen tracks, and subscribe to other participants' tracks.
- Rooms on top of a pluggable signaling/presence transport.
- **Simulcast publishing and per-subscriber layer selection. Simulcast is mandatory:** without it, SFU egress is about 3× higher (see §6).
- Active-speaker detection.
- **Automatic reconnection**, including network changes and mobile background/foreground.
- Screen share on every platform `flutter_webrtc` supports.
- DataChannels (reliable and unreliable) for app messages, such as reactions or remote-control input.
- **Every primitive for phone-style calls, video conferences and screen sharing** (decided October 2026): CallKit and Android Telecom, calls that keep running in the background, connection quality, screen share on phones, and the rest listed in the [roadmap](roadmap.md#scope-telecom-videoconferencing-and-screen-sharing) (M9–M15). Primitives only: the app builds its own structure on them.
- **The same call behaves the same on every platform.** The basic camera and audio operations are one API with one behaviour: which camera opens (the front one), at what resolution, switching cameras, mirroring the self-view, muting, and choosing the microphone and speaker. The package absorbs `flutter_webrtc`'s per-platform differences (§4.5) so apps don't branch on the OS. Where a platform can't do something, the API says so (for example `canSelectAudioOutput`) instead of behaving differently.
- The Cloudflare **App Secret never reaches the client.** Every SFU API call goes through a server-side broker (§5).

**Non-goals** (the app's job, or later work):
- **A signaling or room server.** The app supplies a `Signaling` implementation.
- **Remote-control input injection** (`SendInput`, `CGEventPost`). The package only carries the bytes over DataChannels.
- Recording, transcription, egress to RTMP.
- End-to-end encryption. Possible later through `flutter_webrtc`'s frame cryptor.
- Heavy UI. At most a thin video-view helper and a desktop source-picker model; no meeting UI.

## 3. First consumer and API shape

The first consumer is the buildIt.Social app. It wraps this package behind its own `VideoProvider` interface, so that `livekit_client` can be swapped in if needed.

To keep that swap cheap, **use LiveKit-like concepts where they fit**: `Room`, `LocalParticipant`/`RemoteParticipant`, track publications, `connectionState`, `activeSpeakers`. Don't copy LiveKit code or API verbatim.

## 4. Architecture

```
┌────────────────────────── app ──────────────────────────┐
│  Signaling impl (e.g. Supabase Realtime presence)       │
└──────────────┬──────────────────────────────────────────┘
               │ participants: {id, sessionId, tracks}
┌──────────────▼───────────── cloudflare_realtime ────────┐
│ Room ── participants, active speaker, layer selection   │
│   │                                                     │
│ SfuSession ── 1 RTCPeerConnection ↔ 1 SFU session       │
│   │   op queue: push / pull / update / close / renego   │
│ BrokerClient ── typed HTTP client for the broker        │
│ Media ── camera / mic / screen capture, device lists    │
└──────────────┬──────────────────────────────────────────┘
               │ HTTPS (app auth headers)
        ┌──────▼──────┐   Bearer <App Secret>   ┌──────────────────┐
        │   Broker    ├────────────────────────►│ Cloudflare SFU   │
        │ (app server)│                         │ rtc.live.cf.com  │
        └─────────────┘                         └──────────────────┘
```

### 4.1 `BrokerClient`

A typed client for the broker contract (§5), in `lib/src/broker/`. Implemented (M1).

- **`BrokerOptions`** takes:
  - the broker's base URL,
  - an async `headers` provider. The app uses it to attach its own auth, such as `Authorization: Bearer <user JWT>`. It is called before every request, so it can refresh a token;
  - optionally an injected `http.Client` and a per-request timeout (default 15 s).
- **`BrokerClient`** is an abstract interface, one method per endpoint in §5, so session code can be tested against a fake. **`HttpBrokerClient`** implements it with `package:http`. One instance serves one room.
- **Typed models** mirror the SFU's OpenAPI schema: `TracksRequest`/`TracksResponse`, `TrackObject.local`/`.remote` (with `SimulcastOptions`), `CloseTracksRequest`, `DataChannelObject`, `SessionState`, and so on.
- **Libraries.** `BrokerOptions` and the exceptions are in the main library; `BrokerClient`, `HttpBrokerClient`, `BrokerHeaders` and the models are in `package:cloudflare_realtime/broker.dart`, for custom clients (§11, Libraries).
- **Errors.** A failed call throws a `BrokerException` carrying the status, `errorCode` and `errorDescription`. It is sealed, so a `switch` over its subtypes is exhaustive: `BrokerUnauthorizedException` (401), `BrokerForbiddenException` (403), `SessionGoneException` (410, or `errorCode: session_error` at any status; the Room re-sessions on it, §8), `BrokerNetworkException` (and its `BrokerTimeoutException`), `BrokerProtocolException` (an unparseable 2xx) and `BrokerResponseException` (any other error response, with the SFU's status and body).
  - A 2xx response with a request-level `errorCode` is **returned**, not thrown, so per-track results aren't lost; check `hasError` on the response and on each track or DataChannel result.
  - The client never logs. Exception messages never contain SDP, header values or tokens.
- **ICE servers.** `getIceServers()` returns maps ready for `flutter_webrtc`'s `iceServers`, **one map per URL** with a string `urls`: `flutter_webrtc`'s Windows implementation keeps only the last entry of a `urls` array. The desktop plugin (Windows, Linux) also copies the entries into a fixed array of 8 with no bounds check, so on those platforms the peer connection factory keeps at most 8 (dropping port-53 and duplicate URLs first, then the tail). Cloudflare's TURN service returns up to 9 URLs; the reference brokers already drop the two on port 53.
- The client doesn't serialize calls. The session layer's op queue does (§4.2).

### 4.2 `SfuSession`

One `RTCPeerConnection` maps to one SFU session. A participant normally has **one session** that carries everything they push and pull. Implemented (M2) in `lib/src/session/`, ported from partytracks' `PartyTracks.ts` and `Peer.utils.ts`.

**API** (`SfuSession`, its publications and subscriptions, `SfuConnectionState` and `PublishOptions` are in `package:cloudflare_realtime/broker.dart`; the options, track states, failures and exceptions the room API shares are in the main library):

```dart
final session = await SfuSession.connect(broker: broker, options: SfuSessionOptions(...));
session.sessionId;                      // share through signaling
session.connectionState;                // initial/connecting/connected/disconnected/failed/closed
session.connectionStateChanges;         // Stream<SfuConnectionState>, replays the current value
session.failures;                       // Stream<SfuSessionFailure>: at most one, replayed to late listeners
session.failure;                        // SfuSessionGone | SfuPeerConnectionFailed | null
await session.establishConnection();    // connect now, before any push (M10): the SFU keeps the session
session.hasNegotiated;                  // an SDP exchange has completed

final pub = await session.publish(track, options: PublishOptions(trackName?, sendEncodings?, codecPreferences?));
await pub.whenSending();                // RTP is flowing: now advertise pub.trackName + pub.sessionId
await pub.replaceTrack(otherCamera);    // no renegotiation; null mutes (transceiver and mid stay)
await pub.setEncodings([...]);          // no renegotiation (bitrates, active layers)

// Or follow a media source's track stream (null while muted, a new track on device change):
final cam = await session.publishTrackStream(source.broadcastTrackChanges.map((t) => t?.track), kind: 'video');

final sub = await session.subscribe(remoteSessionId: id, trackName: name, preferredRid: 'b');
sub.track; sub.trackChanges;            // MediaStreamTrack? / Stream<MediaStreamTrack>
await sub.setPreferredRid('c');         // tracks/update

await session.getStats();               // List<StatsReport>, outside the queue (M4)
await pub.unpublish(); await sub.unsubscribe();   // tracks/close
await session.republish(pub); await session.resubscribe(sub, remoteSessionId: newId);  // on a new session
await session.close();
```

`LocalTrackPublication` and `RemoteTrackSubscription` have a `state` (`SfuTrackState`: `pending`, `active`, `interrupted`, `failed`, `closed`), a replaying `stateChanges` stream, `error`, `session` and `mid`. A failed operation throws a `BrokerException` (passed through) or a sealed `SfuSessionException`: `SfuSessionClosedException`, `SfuSessionFailedException`, `SfuInterruptedException` (unpublished, closed or moved before it completed), `SfuTrackException` / `SfuDataChannelException` (the SFU rejected one item), `SfuRequestException` (it rejected the request) or `SfuProtocolException` (its answer was unusable).

- **Connect.** Two chains run at once: `sessions/new`, and `generate-ice-servers` (skipped when `SfuSessionOptions.iceServers` is set) followed by creating the peer connection with `bundlePolicy: max-bundle`. **Deviation (M10):** partytracks (`forkJoin`) creates the peer connection only after both requests; here it doesn't wait for `sessions/new`, because flutter_webrtc's first `createPeerConnection` took 5–10 s on a loaded Mac, and the SFU's expiry clock for an unconnected session (below) starts at `sessions/new`. Both chains always finish (`Future.wait` on a record), so when one fails, whatever the other created is released: the session is forgotten (`BrokerClient.forgetSession`), the peer connection closed, and the first error thrown. A `sessions/new` with a request-level `errorCode` does the same. Nothing is negotiated until the first push, pull or `establishConnection()`.
- **macOS: a slow first join, and a frozen app while it runs** (measured after M13 on a MacBook Pro, macOS 27, `flutter_webrtc` 1.6.2+hotfix.3 with WebRTC-SDK 150.7871.01, cold app starts, `example/integration_test` against the real SFU; a field report from another Mac had the same shape: 29 s with steps of 6.3, 7.3 and 14.5 s). Almost all of a 25–38 s first join is the audio stack starting, in three steps (the first two once per process, the third whenever the module starts recording again):
  1. The first `createPeerConnection` initializes WebRTC-SDK's audio device module (its `AudioEngineDevice`) on libwebrtc's worker thread: up to 6.0 s. `flutter_webrtc`'s `initialize` (the factory, sent before the first call) adds 0.5–1.7 s just before it. Closing the last peer connection undoes part of it: a peer connection created after that blocked again for 2.4–3.1 s.
  2. The media layer's first device list (`getSources`) makes AVFoundation build its list of capture devices, which queries every Core Audio device: up to 9.0 s. **No longer on a microphone join's path** (October 2026, below).
  3. The first audio send (`setRemoteDescription` of the first microphone push) starts recording, and the module turns on Apple's voice processing (`AVAudioInputNode setVoiceProcessingEnabled`), whose I/O unit builds an aggregate device of the input and output: 3.0–14.9 s with the system default input (here "BlackHole 16ch", a virtual 16-channel device) in 9 traced runs, and about 27 s in a later one (the whole publish; its other steps take milliseconds), 5.3–23.3 s with the MacBook Pro Microphone chosen. Choosing an input other than the default then cost another 9–11 s before the first packet: the module saw the device list change, went back to the default, and the package's re-selection (§4.5) switched it again, each rebuild running the voice processing again.

  `getUserMedia` itself took under 30 ms, and the network steps (`sessions/new`, `tracks/new`, ICE) well under a second; the iOS Simulator, an Android emulator and Chrome on the same Mac join in a few seconds, as none of them uses Apple's voice-processing unit here. The times vary a lot with the Mac's load and Core Audio's state: on a quiet run the three steps took 0.03, 0.3 and 3–5 s. `bypassVoiceProcessing` (`WebRTC.initialize`) didn't help: the module still enables voice processing (it only bypasses it). Starting the module's recording before the join (`NativeAudioManagement.startLocalRecording`) made it worse: it ran before the peer connection, which then waited 25.8 s for it on the worker thread, long enough for the SFU to expire the unconnected session. Steps 1 and 3 are WebRTC-SDK's and Apple's, and step 2 `flutter_webrtc`'s (its `getSources` lists cameras through AVFoundation even when only microphones are wanted); the package can't make them faster.

  **What the package does: keep the app responsive meanwhile.** `flutter_webrtc`'s Darwin plugin answers method calls on the main thread, which on macOS is also the Dart UI thread (reported as [flutter-webrtc #2217](https://github.com/flutter-webrtc/flutter-webrtc/issues/2217)), and libwebrtc's proxies make many of them wait for the worker thread. Applying a description doesn't block it (the plugin answers asynchronously), but a `getStats()` sent during the 15 s of step 3 did: a sampled run had the main thread waiting in `peerConnectionGetStats` for the whole of it (the Room's stats and the publication's `whenSending()` poll), so timers, rendering, signaling and a hang-up all stopped. The `MacInputReselector`'s re-selections (§4.5) did the same through `selectAudioInput`. So the peer-connection wrapper counts the native `createOffer`, `createAnswer`, `setLocalDescription` and `setRemoteDescription` calls in flight in the process (`NativeNegotiation`, internal; the audio device module is one per process), and `getStats()` (the connection's, a sender's and the DataChannel check's) and the macOS input selections wait until none is running. Measured with the event loop's longest gaps during step 3: 13.4–14.7 s before; after, under 0.5 s in 3 runs with the default input (one with a 27 s step 3) and none in 3 runs with the MacBook Pro Microphone. The module's own rebuilds after a device-list change can still block it, which nothing announces. Not changed: the join's order (the peer connection is still created while `sessions/new` runs).

  **Steps 1 and 2: what still froze the app** (October 2026, from a consuming app's report: a macOS ↔ Chrome first join froze its UI for up to about 10 s, twice). `example/integration_test/join_timing_test.dart` now times every `flutter_webrtc` method call and names the calls behind each event-loop gap. Measured on the same MacBook Pro (macOS 27, default input "BlackHole 16ch", cold app starts, against the real SFU, a microphone join and publish), in 4 runs: `initialize` 0.6–1.7 s and the first `createPeerConnection` 3.5–4.9 s back to back (one freeze of 4.1–6.0 s), then `getSources` 4.8–6.9 s (a `getStats` queued behind it); the longest gap 4.9–6.9 s, the join and publish 24.2–25.4 s. Every other call answered in under 0.25 s, and `setRemoteDescription`'s 12.7–13.4 s (step 3) blocked nothing.
  - **Step 2, removed: a Mac's microphone is captured before the devices are listed** (§4.5, Capture before listing on macOS). Nothing in a microphone publish needs the list when no device is chosen, so the `getSources` is gone from the join (5 runs: no gap from it; the longest gap 3.8–5.7 s, step 1). The join isn't faster: `setRemoteDescription` grew to 16–19 s and the join and publish stayed at 24.5–25.0 s, as if the Core Audio scan moved to the worker thread, where it blocks nothing. A camera publish still lists the devices (and `getUserMedia` lists the cameras through AVFoundation itself), so a camera join still has it.
  - **Step 1, moved: `CloudflareRealtime.prewarm()`** (opt-in). The plugin creates the factory and the peer connection on the main thread, and the package can't send a platform call from elsewhere, so the 4–6 s can only happen at another time. `prewarm()` creates one idle peer connection (no ICE servers, no transceivers) at a moment the app chooses, and keeps it until the next join's session has created its own (`PeerConnectionWarmup`, internal): closing it first left the join's `createPeerConnection` at 2.4–3.1 s (2 runs). Held, the join's took milliseconds: in 5 runs the prewarm froze the app for 4.2–5.1 s and the join for nothing (no gap over 250 ms from joining; the join 0.4–0.6 s, join and publish 17.4–18.4 s). Nothing is recorded: unlike the earlier `startLocalRecording` attempt (above), the module only initializes, and the voice processing still starts with the first publish. `SfuSession.connect` waits for a prewarm still creating its peer connection before `sessions/new` (bounded by `negotiationTimeout`), so the SFU's clock for an unconnected session never runs during it; the join is the same as before when `prewarm()` isn't called. Only on macOS: elsewhere it does nothing (a phone's first peer connection is fast, and creating one early could touch the audio session before CallKit or Telecom expects it). A room left and joined again has the 2–3 s again, unless the app prewarms after leaving. A re-session (§8.1) creates its new session before closing the old one, so it doesn't. **Its limits (decided October 2026: kept, documented):** it moves the freeze and doesn't remove it. A consuming app on macOS 27 measured the prewarm itself freezing its UI for 5.3 s and 8.9 s when it ran right after sign-in (0.6–2.1 s of jank at that moment without it), and no gain on its joins (the SFU session took 0.7–1.0 s either way; what still froze was its first microphone publish, below), so it ships with the prewarm off. It is kept, opt-in, for apps that can hide a freeze (behind a launch or splash screen); its dartdoc, `doc/macos.md` and the CHANGELOG say so.
  - **Still freezing: a chosen microphone other than the default** (with "MacBook Pro Microphone"). The list is no longer read first (October 2026: a Mac's chosen microphone is selected by its ID, §4.5; it took 6.0 s in the first run and 2.1 s later), but after the first audio send the `MacInputReselector`'s re-selection (§4.5) blocks the main thread: 8.3 s in the first run, 3.6–12.3 s in 4 runs with the platform call timing (below). `selectAudioInput` (`setInputDevice:`) waits on the worker thread while the module rebuilds its voice processing for the switch back from the default it fell back to (the 9–11 s of step 3's last sentence). The re-selections queued during `setRemoteDescription` all go out as it completes; the first one blocks for the rebuild, the others then answer at once, and the `getStats` polls sent with them wait behind it. The re-selection waits for no description to be applied, but nothing announces the rebuild it triggers; without it, the call would capture from the default (§4.5).
  - **For flutter-webrtc #2217** (not posted; context for the issue): what remains is the plugin's, on the main thread. `initialize` (`RTCPeerConnectionFactory` creation, and `inputDevices` / `setInputDevice:` on the audio device module), `createPeerConnection` (`peerConnectionWithConfiguration:`, which waits for the worker thread's `AudioEngineDevice` init) and `getSources` (`AVCaptureDeviceDiscoverySession` and the module's `inputDevices` / `outputDevices`) all run synchronously in the method-call handler on the main thread, which on macOS is Flutter's UI thread, for 0.25–1.7, 2.3–7.7 and 2.0–9.0 s on a cold start; so do the camera's `getUserMedia` (`AVCaptureDeviceDiscoverySession`, the capture session's start: 0.8–1.0 s, and 3.6–4.1 s when it is the process's first camera discovery) and `selectAudioInput` while the module rebuilds (3.6–12.3 s for a microphone other than the default, after the first audio send). So do the video renderer's calls: `videoRendererSetSrcObject` (and `videoRendererDispose` and `streamDispose` when they detach a renderer) runs `-[FlutterRTCVideoRenderer setVideoTrack:]` on the main thread, whose `-[RTCVideoTrack removeRenderer:]` / `addRenderer:` make a blocking call to the worker thread: 0–48 ms each with an idle worker thread (§4.3, Fewer renderer calls), 520–830 ms each in a consuming app's call after mute and camera toggles. Answering them from a background queue (as the description calls already answer asynchronously; for the renderer, setting the track off the main thread and answering after) would remove the freezes; `getSources` could also skip the cameras when only audio devices are wanted. Measured with `CloudflareRealtime.debugPlatformCallTiming` (below).

  **Finding the blocking call: platform call timing** (October 2026). The same consuming app's macOS ↔ Chrome first joins (3 runs each way, at `0bf167a`) still took 5–29 s with UI gaps up to 5.2 s, in the first microphone publish (the camera's start didn't freeze), where the package's own runs had no gap left: so something the app does, or a call the example doesn't make, blocks there. To find it in the app, the package now has a debug aid, `CloudflareRealtime.debugPlatformCallTiming` (`PlatformCallTimingOptions`, `null` by default) with `debugPlatformCallTimingEvents` (`PlatformCallAnsweredEvent`, `EventLoopGapEvent`; `lib/src/diagnostics/`), built from what `join_timing_test` did:
  - **Calls:** every message sent on the chosen channels (`flutter_webrtc`'s `FlutterWebRTC.Method` by default, `null` for all) is timed from its sending to its answer, with its method name and its map argument's keys; never argument values (SDP, tokens) or replies. **Where it hooks in:** Flutter creates the default `BinaryMessenger` once, with the binding (`ServicesBinding.createBinaryMessenger`), every `MethodChannel` without its own messenger sends through it, and it can't be swapped afterwards outside tests (only `TestDefaultBinaryMessengerBinding` can); `flutter_webrtc`'s channel is a private `static const` with no hook. So the app creates `PlatformCallTimingBinding` (a `WidgetsFlutterBinding` whose messenger reports to the timing) first thing in `main`, or wraps its own binding's messenger with `PlatformCallTimingBinding.wrapMessenger`; tests forward the test messenger's messages through `wrapMessenger` (`example/integration_test/support/call_timing.dart`). Wrapping only the package's own call sites was the alternative: no binding needed, but blind to the app's direct `flutter_webrtc` calls, the likeliest suspects here. Without the binding the timing reports gaps only, and logs that.
  - **Gaps:** a 20 ms periodic timer measures the Dart event loop's lateness; a gap over `gapThreshold` (250 ms) is reported with the calls **sent** from 40 ms before it began until it ended (a call that blocks the platform thread is sent just before its gap and answers as it ends) and the calls **pending** from earlier. On macOS, iOS and Android the platform thread is the UI thread, so a gap is a frozen app; a gap with no call came from the app's own Dart code or native work no call started (the renderer's frame callbacks, timers).
  - **Off by default and then free:** no timer runs, and the wrapped messenger only checks one static before passing a message on. It logs with `debugPrint` (`log: false` turns that off; the gaps, and calls over `slowCallThreshold`, 100 ms). Unit tests: `test/diagnostics/platform_call_timing_test.dart`.

  **What it found in a macOS ↔ Chrome first call** (October 2026; `example/integration_test/first_publish_timing_test.dart`: the same MacBook Pro, macOS 27, default input "BlackHole 16ch", the FaceTime HD camera; Chrome 154, headless with fake devices, as the other side, through the dev server; cold app starts with a call screen showing both cameras; the camera and the microphone published together, microphone first or camera first, with Chrome in the room first or joining after; load averages 5–25):
  - **The first microphone publish itself froze nothing.** With the system default microphone, no gap over 250 ms came from it in any run: joined to microphone sending took 12.4–15.4 s, nearly all `setRemoteDescription` (10–14 s, the voice processing, off the main thread).
  - **What froze, in every run:** `initialize` + `createPeerConnection` inside `join` (step 1: 2.7–5.7 s in 9 runs, 7.7 s under a load average of 20); the first device list (`getSources`) when the camera started before or with the microphone, 2.0–4.2 s in 7 runs; and the camera's own `getUserMedia`, 0.8–1.0 s. When the microphone went first, the camera's list took 0.1 s and only its `getUserMedia` froze: the first audio send's voice processing does the slow Core Audio and AVFoundation scan on the worker thread, and later lists are fast.
  - **The camera's list stays** (as §4.5 decided): a probe on a cold start (a peer connection, then the camera alone) had `getUserMedia` first take 3.6–4.1 s with `getSources` after it at 0.1 s, and the other way round 3.2–4.0 s then 0.45–1.05 s. Whichever asks AVFoundation for the cameras first pays the scan, so capturing a camera before listing would move that freeze into `getUserMedia`, not remove it.
  - **A chosen microphone: the package's list is gone from the publish** (fixed; §4.5, Capture before listing on macOS). A microphone the app passes by ID (`publishMicrophone(device:)` with a choice it saved) was listed first: 2.1 s and 3.1 s of `getSources` inside the first microphone publish with "MacBook Pro Microphone" (2 runs). It is now selected by its ID without the list: no list in the publish (2 runs). What remains for a microphone other than the system default is the re-selection after the first audio send (below): 3.6–12.3 s in those 4 runs, all of it inside the publish (joined to microphone sending 20.4–31.6 s). That fits the consuming app's report (UI gaps of up to 5.2 s inside its first microphone publish, joins up to 29 s) if it publishes a microphone other than the default; it is still to be confirmed there with the timing on. An app that lists the devices itself (a device picker) pays the list where it does it: 1.9–4.3 s in 3 runs that listed just before the publish.
  - **`prewarm()` at app start** (3 runs, the camera and the microphone together): the prewarm froze 2.6–3.7 s, the join then took 0.4–1.4 s with no gap, the longest gap from joining fell from 3.3–5.7 s to 1.0–2.2 s (the camera's list and capture), and joining to both sending took 11.9–14.5 s against 17.4–21.2 s: the join's peer connection moved earlier; the publishes took as long (10.6–14.1 s against 12.4–15.4 s).
  - **Three runs started warm** (the join 0.6–0.8 s, no gap but the camera's capture, joining to both sending under 6 s), each right after a run with the MacBook Pro Microphone; they are left out above. Core Audio's state matters as much as the load (step 3's note).
  - When several calls are sent together (the camera's `getSources` with a `getStats` and a `getSignalingState`), they all answer as the gap ends and the timing alone can't say which one blocked; a run with the call alone (the probe above) or `sample` of the main thread does.

  **Time limits on these steps must allow for it:** a limit of 15 s per negotiation step would have failed 5 of the 15 measured macOS first joins (`setRemoteDescription` at 15.1, 15.3, 15.6 and 23.3 s with the MacBook Pro Microphone chosen, and about 27 s with the default input). The other steps stayed well under it: the first `createPeerConnection` 6.0 s, `getUserMedia` 30 ms, `setLocalDescription` 0.7 s. So the per-step limit (Bounded negotiation steps, below) is 60 s on every platform.
- **The SFU expires a session whose peer connection never connected.** Observed against the real SFU: about ten seconds after `sessions/new` (gaps of 9–13 s sometimes survived, 10 s sometimes didn't), the next call on an unconnected session fails with 410 `session_error` "Session appears to be disconnected". Nothing connects until the first SDP exchange, so a first push that waits on a camera or microphone prompt, Android's screen-capture consent, the iOS broadcast picker, or a slow first `getUserMedia` fails. **`establishConnection()`** (M10) connects the session early: it sets up the DataChannel transport (`datachannels/establish` without an offer, then answering the SFU's offer through `renegotiate`, as the first DataChannel operation does; §9), which gives the peer connection one `application` m-line and no media. ICE and DTLS then connect and the session stays. It runs on the queue, does nothing once `hasNegotiated` is true, and completes when the exchange is done (not when ICE connects). A 410 fails the session as any call does; other errors leave it usable, and the next DataChannel operation tries to establish again. That retry can't always work: against the real SFU, a second `datachannels/establish` on a session whose first one had reached the SFU answered 400 `decoding_error` ("Failed to decode body as JSON"), so such a session gets no DataChannels until it is replaced. Later pushes, pulls and DataChannels share the transport; the session's close logic then never needs `force` (the `application` m-line stays live). The Room calls it (§8.1, Publishing late); direct `SfuSession` users call it themselves right after `connect`.
- **Push** (publish local tracks):
  1. Add a `sendonly` transceiver per track (with simulcast encodings for video) and apply codec preferences.
  2. `createOffer`, then `setLocalDescription`.
  3. `POST tracks/new` with the offer, and `tracks: [{location: "local", mid, trackName}]`.
  4. `setRemoteDescription(answer)`, after the RTX repair below.

  Track names are UUIDs (partytracks uses `crypto.randomUUID()`) unless the caller names the track; names are unique per session.

  **Offers and answers pass empty constraints** (`{}`). Without an argument, native `flutter_webrtc` (Android, Darwin, Windows, Linux) sends `OfferToReceiveAudio/Video: true`, and libwebrtc then adds a `recvonly` audio and a `recvonly` video transceiver to the first offer. The SFU answers those undeclared m-lines, so every session carried two stray transceivers, and on Windows they hid the close problem below. Browsers add nothing for `createOffer()`, so `{}` matches the web and partytracks (found against the real SFU, after M7).

  **Mute and device changes.** partytracks keeps sending a black or silent placeholder track while muted; `flutter_webrtc` can't make those, so the media layer's `broadcastTrack` is null while muted. `replaceTrack(null)` therefore stops sending without renegotiating: the transceiver and `mid` stay, and unmuting is another `replaceTrack`. Replacements are applied in order and settle on the latest track. `publishTrackStream(tracks, kind:)` follows such a stream (partytracks' `push(track$)`): it pushes whatever the stream holds when the push goes out (possibly nothing: the transceiver is then created from `kind`), and applies every later value. The session code takes plain `MediaStreamTrack`s and doesn't import the media layer. **Deviation:** partytracks adds the transceiver when `push` is called; here it is added inside the queued operation, so an unrelated offer in flight never carries an undeclared m-line.

  partytracks emits a pushed track's metadata only once the sender reports `bytesSent > 0`, so peers don't pull too early. Here `publish` completes when the SFU accepts the track, and `whenSending()` ports the wait (stats polled from 1 ms, ×1.1, capped at 100 ms). **Decision (M3):** the Room does *not* wait for `whenSending()`; it advertises a track as soon as the SFU accepts it, because a publication muted from the start sends no RTP and would never be announced. Subscribers instead retry pulls that fail before the first packets (§4.3).
- **Encodings and codecs.**
  - Video defaults to `SimulcastPresets.h720`: rids `a` (full, 1.2 Mbps), `b` (`scaleResolutionDownBy: 2`, 400 kbps), `c` (4, 150 kbps). `h1080` and `h360` exist too; M4 tunes the numbers. `sendEncodings: []` publishes one default encoding. Audio has none.
  - Codec preferences are MIME types; set, they **restrict** the transceiver to those codecs plus rtx/red/ulpfec/flexfec, so the SFU can't pick another. The default is `['video/VP8']` on every platform (§6, Codec; `SfuSessionDefaults.videoCodecPreferences` overrides it). A platform that rejects `setCodecPreferences` keeps its default order.
- **SDP from the SFU is repaired before it is applied.** Once a session has pulled a video, the SFU numbers codecs in its SDP the way that pulled m-line does (VP8 as 96), including in its answer to a later video push that offered VP8 under another number (100 on Apple platforms with libwebrtc M150). But it leaves that m-line's RTX entry as offered (`a=fmtp:101 apt=100`), naming a payload type the m-line no longer has. libwebrtc can't map the RTX codec, finds no codec to send with, and rejects the whole description: "Failed to set remote video description send parameters for m-section with mid=...". The SFU repeats the broken m-line in its later offers and close answers. So every SFU answer and offer goes through `repairRtxAssociations` (`sdp_repair.dart`) first. A dangling `apt` is pointed at the payload type the m-line now uses for the codec the local description gave that number (same format parameters preferred). If the m-line has no such codec, or that codec already has an RTX entry, the dangling RTX entry is removed. Valid SDP is passed through unchanged. The repair reads the local description first; when the SFU's offer is the session's first SDP (`datachannels/establish`), there is none, and Android's plugin throws for it (a `NullPointerException` in `getLocalDescription`) instead of answering null, which broke DataChannels on a fresh Android session until the wrapper turned that into null (found running `datachannel_echo_test.dart` for M10). Seen pushing an iPhone screen share after the microphone with a camera already pulled, and reproduced on macOS; a push before any pull, or with no pulled video, never hit it. Android's numbering didn't trigger it in the runs so far.
- **Pull** (subscribe to remote tracks):
  1. `POST tracks/new` with `tracks: [{location: "remote", sessionId, trackName, simulcast?}]`. `simulcast` is sent only with a `preferredRid`; `ridNotAvailable` then defaults to `asciibetical`, and `priorityOrdering` is left to the SFU default (`none`) unless given (§6).
  2. If the response has `requiresImmediateRenegotiation`, then `setRemoteDescription(offer)`, `createAnswer`, `setLocalDescription`, and `PUT renegotiate` with the answer.
  3. Map the returned `mid` to the transceiver, which gives you the remote track. Results are matched by `trackName` + `sessionId`, as in partytracks. The transceiver is looked up after renegotiation, waiting up to 5 s for its `track` event (partytracks' `resolveTransceiver`). If it never shows up, the pull fails as a per-track error and its `mid` is closed at the SFU (`tracks/close` with `force: true`: there is no transceiver to stop), so a retried pull, which gets a new `mid`, doesn't leave another pulled track open on the session.
  4. A pull of a track the SFU can't serve yet (the publisher's session isn't connected, or hasn't sent media for it) is answered `200` with a per-track error (`not_found_track_error`) and no `mid` or renegotiation (§8.1, Publishing late). Such a pull adds nothing to the session; the Room retries it with `RoomOptions.pullRetry`. Seen in the checkpoint's real-drop run: a phone re-sessioned and announced its new session before its media path was up, and the subscriber's pulls of its tracks failed this way, twelve `tracks/new` in seven seconds with no `renegotiate`, until the phone's media path came up; the next pulls renegotiated.
- **Update:** `PUT tracks/update` with the pulled track's `mid` and its full `simulcast` object (keeping the orderings). Updates are batched too, and the last `rid` per subscription in a batch wins. On a subscription that isn't active, the rid is only remembered for the next pull. partytracks fires updates outside its queue; here they are queued.
  - **The SFU rejects a layer change until it forwards the track.** Right after a pull, `tracks/update` answers `update_track_error` "The track is not configured for simulcast, no updates applicable." until media reaches the subscriber (a few hundred milliseconds against the real SFU; waiting for `inbound-rtp` bytes made it pass every time). The Room changes layers as soon as a pull lands, so `setPreferredRid` retries that one error with backoff (100 ms doubling to 1 s) for up to `SfuSessionOptions.layerUpdateRetryTimeout` (10 s), outside the queue. A newer `setPreferredRid` on the same subscription supersedes a pending retry. Once accepted, the received resolution follows only at a keyframe of the new layer: 8–13 s in most of the first Windows ↔ Android runs (sometimes 1–4 s), regular enough to look like an SFU-side timer (`docs/checkpoint.md`, criterion 2 notes). On a Pixel 10 loopback (M12) switches up came on a 6.2–6.5 s cadence, and some never came within 20 s (the SFU kept forwarding a lower layer; §6.2). Nothing in the client waits for it. A track published without simulcast gets the same answer for good; the Room never asks for a layer there (§6.1), and a direct caller gets the error after the timeout.
- **Close:** stop the transceivers, `createOffer`, `setLocalDescription`, `PUT tracks/close` with the `mid`s and the offer (`force: false`), then apply the answer, or renegotiate if the response asks for it. `close_track_error` counts as closed. The publication or subscription is closed locally even if the request fails. On a failed or closed session, only local state changes (partytracks also skips negotiation on a dead connection). Local `MediaStreamTrack`s are never stopped: capture belongs to the app.
  - **Closing the session's last live m-lines** (every m-line of the current local description that isn't rejected, including a DataChannel `application` m-line) can't be negotiated: with `max-bundle`, libwebrtc refuses an offer whose m-lines are all rejected ("max-bundle configured but session description has no BUNDLE group"), and with `balanced` the offer goes through but the transport closes and the SFU drops the session (410 on the next call). Both seen against the real SFU on Windows. So that close uses `force: true` with no SDP, and **parks** the transceivers instead of stopping them: a parked sender gets `replaceTrack(null)`, the SFU stops forwarding, and the idle m-lines keep the transport up. Later pushes and pulls work on the same session (tested: re-pull, re-push, and a negotiated close next to a parked m-line). Stopping the transceivers without negotiating crashed the Windows app on the next SFU offer, so they are left as they are. Parked transceivers live until the session closes.
- **All operations run through one serialized queue** (`OpQueue`, a port of `FIFOScheduler`). The SFU requires each SDP exchange to finish before the next mutation on the same session.
  - Pushes, pulls, updates and closes that arrive in the same event-loop turn are each batched into one request (`BatchDispatcher`, a port of `BulkRequestDispatcher`: a zero-duration timer, at most 32 items per batch). A push batch and a pull batch in the same turn become two requests, run one after the other (one `tracks/new` is all local or all remote).
  - A failing operation fails only its own items; the queue moves on.
  - **The queue heals the signaling state.** A push or close that fails after `setLocalDescription(offer)` (broker error, request-level `errorCode`, no answer) would leave `have-local-offer`; a failure after applying an SFU offer leaves `have-remote-offer`. Either would make the next exchange fail. So after any failed operation, and before each one, the queue checks the signaling state and rolls back (`{type: rollback}` through `setLocalDescription` or `setRemoteDescription`) to `stable`. If the rollback fails or isn't supported on a platform, the session fails with `PeerConnectionFailureKind.signalingStuck`, so the Room replaces it (§8) instead of it staying wedged. partytracks doesn't do this; it relies on re-creating the whole session.
  - **Bounded negotiation steps** (hardening, October 2026). Every peer-connection call an operation awaits inside the queue can hang on a stuck platform, and the queue would then wait forever, with every later push, pull and close behind it. Seen once on an iPhone (iOS 27.2): 1 of 14 CallKit answers hung in the microphone publish, after `didActivate` and before `tracks/new` (§4.8, iOS status and findings). So the session wraps its peer connection in `NegotiationGuard` (`negotiation_guard.dart`): `signalingState`, `rollback`, `addTransceiver`, `createOffer`, `createAnswer`, `setLocalDescription`, `setRemoteDescription`, `localDescription`, `createDataChannel`, and a transceiver's `mid`, `replaceTrack`, `setCodecPreferences` and `stop` each get `SfuSessionOptions.negotiationTimeout` (**60 s** by default, on every platform; `null` turns it off; `transceiverForMid` gets it on top of its own wait). A step that runs over fails the session with `PeerConnectionFailureKind.negotiationTimeout` and throws `SfuSessionFailedException` from the operation, logging which step it was (`cloudflare_realtime: setLocalDescription did not complete within 60000 ms`). Failing the session rather than one batch is deliberate: the step may still complete later and leave the peer connection in an unknown state, as with `signalingStuck`. The Room then re-sessions (§8) and pushes a publish that was waiting once more on the new session (`_onSessionWithRetry`, §8.1), so the room stays usable. What completes late stays on the old peer connection, which the re-session closes; a late DataChannel is closed at once. Creating the peer connection in `connect` has the same bound (a late one is closed), so the recovery itself can't hang, and `close()` stops waiting for a platform close after it. The 60 s leaves room for macOS's slow first join (above: the first audio push's `setRemoteDescription` took 3–23 s, once about 27 s, while Apple's voice processing started; 15 s would have failed about 1 in 3 first joins there), and is still well inside an app's own join timeout. **With `NativeNegotiation`** (above): a native SDP call the guard gave up on would otherwise count as running until it completes, maybe never, and `getStats()` and the macOS input selection wait for none to run. So the guard runs each step under `NativeNegotiation.releasingOn`, and a step that times out stops counting at the timeout; its late completion doesn't count twice (`test/util/native_negotiation_test.dart`, and the guard's test). Not bounded: `getStats` and `hasSentMedia` (slow on a loaded machine, and outside the exchange) and `setEncodings`. Unit tests: `test/session/negotiation_timeout_test.dart`, `test/room/room_publish_timeout_test.dart`.
  - Cleanup runs inside the queue before an operation's futures complete: the transceivers of failed pushes (a whole-request failure, a per-track error or a missing `mid`) are stopped, so later offers leave them out (or reject them with port 0), and the publication drops them; a `republish` adds a fresh transceiver.
  - A `tracks/close` response that carries an SFU offer instead of an answer rolls back our close offer, then answers theirs.
- **Per-track errors:** an error on one track (or a missing result) fails only that publish, pull, update or close, with an `SfuTrackException` carrying the SFU's `errorCode`. The rest of the batch succeeds. A request-level `errorCode` in a 2xx fails the whole batch with an `SfuRequestException`; broker exceptions pass through unchanged.
- **Failures and replacement.** The session doesn't reconnect; the Room does (§8). It reports one `SfuSessionFailure` and then refuses operations (`SfuSessionFailedException`):
  - `SfuSessionGone` when a broker call throws `SessionGoneException`. **Except for requests that name other sessions** (pulls, and DataChannel subscribes with `location: remote`): there the 410 or `session_error` may be about the *publisher's* expired session, but `HttpBrokerClient` can only attribute it to the session in the path, ours. So the session first confirms itself with `GET sessions/{ownId}` (hardening, after M5):
    - gone (`SessionGoneException`) or refused (`403`: the broker no longer lets us use it): the session fails as above;
    - alive, or the check itself fails (network, timeout, 5xx; that proves nothing either way): only the batch's items fail, as per-item errors (`SfuTrackException` / `SfuDataChannelException` with the SFU's `errorCode`, `session_error` for a bare 410), and the Room's pull retries handle them (§4.3). A real outage still shows on the peer connection. Every item in the batch fails, since the error doesn't say which session it meant; the retries are jittered, so the healthy pulls land in other batches.

    Pushes, updates, closes, renegotiation and `datachannels/establish` name only our session and fail it at once, as before. `HttpBrokerClient` keeps the session token on a `SessionGoneException` (the confirmation needs it); `forgetSession` drops it when the session is closed.
  - `SfuPeerConnectionFailed` when the connection state becomes `failed`, the ICE state `failed`, the connection closes unexpectedly, or ICE stays `disconnected` longer than `iceDisconnectedTimeout` (7 s, as in partytracks; null disables it).

  Its publications and subscriptions become `interrupted` and detach from it; they survive the session. The Room's re-session connects a new session and calls `republish` (same `trackName`, current track and encodings) and `resubscribe` (optionally with the publisher's new `sessionId`); `trackChanges` then emits the new remote track. `close()` also leaves them `interrupted`, fails queued operations with `SfuSessionClosedException`, and calls `BrokerClient.forgetSession`. partytracks instead re-creates the session inside `session$` and re-pushes automatically; here that policy is the Room's (§8).
  - **`debugSimulateFailure()`** (tests and demos only) fails the session with `PeerConnectionFailureKind.simulated` and closes its peer connection, so the whole recovery path runs as after a real drop. `Room.debugSimulateConnectionFailure()` calls it.
- **Peer-connection abstraction.** `SfuSession` talks to an internal `PeerConnection`/`PeerTransceiver` interface (including `getStats()`, M4): `FlutterWebrtcPeerConnection` wraps `flutter_webrtc`, and tests use a scripted fake with opaque SDP (`test/support/`). Native `flutter_webrtc` transceivers cache their `mid` from creation, so the wrapper re-reads it through `getTransceivers()`, finding its entry there by the **sender's ID**. The `transceiverId` isn't stable across plugins: Android reports a random ID until the transceiver has a `mid` and the `mid` afterwards, and Darwin always reports the `mid` (empty before negotiation); only the C++ desktop plugin keeps one ID. Matching on `transceiverId` failed every push on Android ("the transceiver has no mid", found against the real SFU on a Pixel). `stop()` goes through the same lookup, because Darwin finds a transceiver to stop only by its current `mid`. On Windows and Linux, at most 8 ICE server entries reach the plugin (§4.1, ICE servers); Android, Darwin and the web get the list unchanged (checked with TURN on Android: 9 URLs, no problem). The interface also creates negotiated DataChannels (`PeerDataChannel`, §9); the DataChannel layer reaches the session's queue, broker and peer connection through an internal `SfuSessionPort`. The internal `connectSfuSession(createPeerConnection: ...)` injects a fake; M3 tests can use it with `test/support/session_harness.dart`.
- **Not done here:** rendering a remote track needs a `MediaStream` for `RTCVideoRenderer`; the Room wraps it (§4.3). Pushes aren't retried one by one (partytracks retries each push/pull with backoff, on the same session): a re-session republishes everything (§8), the Room retries pulls, and the Room retries a publish once on its new session when the session failed under it (§8.1, Publishing late).

### 4.3 `Room`

`Room` ties a session to signaling. Implemented (M3) in `lib/src/room/`, with the video view in `lib/src/rendering/`. The concepts follow LiveKit (§3); the code and API names are our own.

- **Join.** `CloudflareRealtime.join(roomId, signaling:, participantId:, metadata:, options:)` creates an `HttpBrokerClient` for the room (every request carries `X-Realtime-Room`), connects an `SfuSession`, then joins signaling with `{participantId, sessionId, tracks: {}, metadata}` while it connects the session early (`RoomOptions.connectEarly`, default on; §8.1, Publishing late). If connecting or signaling fails, what was opened is closed and the error thrown; an early connect that fails doesn't fail the join (a gone session is re-sessioned, anything else is a `RoomErrorEvent('connectEarly')`). The broker-client and session factories (and the track wrapper, below) are injectable, so tests run on the M2 fakes (`test/support/room_harness.dart`).
- **Announcing.** The local state (`LocalParticipant.state`) is `{participantId, sessionId, tracks: {trackName → {kind, source, muted, simulcast}}, metadata}`. It is re-announced whenever the local participant publishes, unpublishes, mutes, unmutes or changes metadata. Updates go through a coalescing runner: they never overlap, and a burst becomes at most one more update. A failed `Signaling.update` is reported as a `RoomErrorEvent` and retried on the next change.
- **Publishing** (`LocalParticipant`): `publishCamera`, `publishMicrophone` and `publishScreen` each create a media source (the Room owns and disposes it; camera and microphone share one `MediaDeviceList`), start broadcasting, and push `source.broadcastTrackChanges` with `publishTrackStream`. `publishMediaSource` publishes an app-owned source, which the Room never disposes.
  - **Advertise on accept.** A track is announced as soon as the SFU accepts the push, not after `whenSending()` (§4.2): a muted track never sends. The initial pull can then race the first packets, so subscribers retry (below).
  - **Track names** are `<source>-<uuid>`, fixed for the publication's lifetime, so a re-session's `republish` keeps the name (§8).
  - **Mute** is the media layer's broadcasting switch (§4.5): `mute()` = `stopBroadcasting()`, so the sender gets `replaceTrack(null)` and, for camera and screen, the capture is released. The track stays published and is announced with `muted: true`. `publishCamera(muted: true)` / `publishMicrophone(muted: true)` publish without capturing.
  - **Simulcast hint.** `publishCamera` announces its layers as `TrackInfo.simulcast` (rids, the capture size and scale factors), from the encodings (default `SimulcastPresets.h720`) and the size the camera captures as the encoder gets it (M12, §6.3; before M12, the `CameraOptions` preset). A single encoding announces none.
  - **Layer demand and pausing** (M12, §6.2): the local state also carries `layerDemand`, the layer this client pulls of each remote simulcast video, and (with `LayerPausingOptions.on`) the room pauses the layers of its own video that no one pulls (`LocalMediaPublication.pausedLayers`).
  - **Codec** (M12, §6): `RoomOptions.videoCodec`, or `codec:` on a publish.
  - **Screen share** (M6 desktop and web, M9 Android and iOS; §10) is one layer tuned for text by default: `ScreenSharePresets.detail` (up to 15 fps and 2.5 Mbps), captured at 15 fps (`ScreenShareOptions.frameRate`), with no simulcast hint. `ScreenSharePresets.motion` (30 fps, 4 Mbps) and `ScreenSharePresets.simulcast` (a thumbnail layer) are the options; §12, question 2 has the reasoning. It is VP8 like every video track (§4.2, §6). With `captureAudio`, the audio is published too, as a `screenAudio` track.
    - **Ending.** When the share ends outside the app (`ScreenShareEndReason.userStopped`: the browser's "Stop sharing", Android's stop control or notification, or iOS's broadcast stop; `sourceClosed`: the shared window or display went away), the room unpublishes it and its audio, re-announces the local state, and emits `LocalTrackUnpublishedEvent` with that `endReason` (`null` when the app unpublished). A share that ends while it is still being pushed is caught too and unpublished right after. Muting ends the capture but keeps the track published; unmuting shares the same source again.
    - **No frames.** While a share captures, the room reads `getStats()` once a second and reports `LocalTrackStalledEvent` once per capture when neither the track's video `media-source` (`frames`) nor the publication's `outbound-rtp` (`framesEncoded`) has counted a frame for `RoomOptions.screenShareStallTimeout` (8 s, counted only while the room is connected; `null` turns it off). On macOS its error is a `ScreenCapturePermissionException` (the missing Screen Recording permission, §10); elsewhere a `MediaCaptureException` (a minimized window, for example). The share stays published; the app decides. Platforms without those stats never report it.
  - Capture failures throw the source's `MediaException` (a cancelled browser picker throws `MediaCaptureException`), and the source is disposed. Nothing is announced then.
  - **Bounded publish** (hardening, October 2026). No publish waits forever: `publishCamera` and `publishMicrophone` capture within `RoomOptions.captureTimeout` (**30 s**, passed to the source's `captureTimeout`; §4.5, Bounded capture), else they throw `MediaCaptureException` with a `TimeoutException` as `cause`; the negotiation that follows is bounded step by step (§4.2, Bounded negotiation steps), and a stuck step re-sessions and pushes again once. Either way the room stays joined and a later publish can succeed. A screen share isn't bounded: its pickers and consent wait on the user.
- **Diffing** (`participant_diff.dart`, internal, unit-tested): successive `Signaling.participants` lists are diffed by `participantId` into joined, left and updated participants, and per participant into added, removed and changed tracks (a changed `muted` or `simulcast`; a changed kind or source counts as removed plus added), a session change and a metadata change (deep). **Participants without a `sessionId` are ignored** as if absent, so losing a session is a leave. Entries with the local `participantId` or `sessionId` are dropped. `Room.participants` emits once per signaling change.
- **Pull only what's subscribed.** Each remote track is a `RemoteTrackPublication`, pulled while it is wanted:
  - `RoomOptions.autoSubscribe` (default: audio yes, video no),
  - `subscribe()` / `unsubscribe()` (an explicit switch), or
  - a `RemoteTrackLease` from `retain()`; `ParticipantVideoView` holds one while mounted, so several views of a track share one pull.

  Video is pulled with `preferredRid` only when the publisher advertises simulcast layers (or the app picked a layer), with the `ridNotAvailable`/`priorityOrdering` of `RoomOptions.layerSelection`. The layer comes from the views' sizes (§6.1); before any view reports, it is `RoomOptions.defaultVideoLayer` (default `b`). `setPreferredLayer(SimulcastLayer.high/medium/low)` overrides it with `a`/`b`/`c`, or picks by rank among the advertised rids.
  - **Lease grace (M4).** A released lease keeps the pull for `RoomOptions.leaseReleaseGrace` (500 ms), so a view that is unmounted and mounted again (a layout change, a rebuild with a new key) doesn't close and re-pull. `Duration.zero` releases at once.
- **Following publishers.**
  - A track that disappears from the publisher's state is closed (`tracks/close`) and removed; a participant that leaves has all its pulls closed.
  - **Session change** (they reconnected): every wanted track is pulled from the new session. A pull that is live on the old session is closed first and pulled afresh, because a live `RemoteTrackSubscription` can't be moved (`resubscribe` requires it to be off its session); a failed or interrupted one is moved with `resubscribe(remoteSessionId: new)`. **Deviation:** the task sketch said "resubscribe every active subscription"; the session API only allows that for detached subscriptions.
  - **Retries.** A failed pull is retried with `RoomOptions.pullRetry` (full-jitter backoff; default 250 ms to 4 s, 8 attempts), and again at once whenever the publisher's state for it changes (unmute, new session). Failures are reported as `TrackSubscriptionFailedEvent` with `willRetry`.
- **Rendering.** A pulled track is wrapped in a `MediaStream` (`createLocalMediaStream('local')` plus `addTrack`) so `RTCVideoRenderer.srcObject` can show it: `RemoteTrackPublication.track` is a `RenderableTrack?` (track + stream), with the replaying `trackChanges`. The label `local` matters: native `flutter_webrtc` uses it as the stream's `ownerTag`, and renderers look up `local`-tagged streams among the local streams, where this one lives. Each replaced or unsubscribed wrapper is disposed.
  - **Disposing the wrapper is safe for the remote track** (checked in the `flutter_webrtc` 1.6.2+hotfix.3 sources, M4). `streamDispose` never stops or disposes a track: Android removes the tracks from the Java stream and drops their IDs from `localTracks` and the capturer map (a pulled track is in neither); Darwin drops the stream from `localStreams`; Windows removes the tracks from the stream and erases their IDs from `local_tracks_`. The receiver keeps the track alive, so a later re-pull or re-render works. On the web, `dispose()` does nothing.
  - **Don't remove the track first.** `mediaStreamRemoveTrack` looks the track up among local tracks only on Android and Darwin, so it fails for a pulled track (Darwin even answers the call twice). Unwrapping therefore only calls `dispose()`; a unit test pins that.
  - **One Darwin side effect.** `streamDispose` also detaches the first renderer showing each of the stream's video track IDs. A new pull has a new receiver and so a new track ID, but if a pulled track ever reappears under a new Dart object with the same ID, the room keeps the existing wrapper instead of disposing it, so the renderer isn't blanked.
- **Releasing a native renderer (macOS and iOS crash, after M13).** `flutter_webrtc`'s Darwin `FlutterRTCVideoRenderer` queues a block on the main queue for every frame; the block takes the renderer from a weak reference and reads an instance variable through it without a nil check (`strongSelf->_isFirstFrameRendered`, `FlutterRTCVideoRenderer.m` line 246 in 1.6.2+hotfix.3). Fixed upstream on `main` by [flutter-webrtc #2190](https://github.com/flutter-webrtc/flutter-webrtc/pull/2190), not yet in a release; the package's wait can go once a release includes it. If the renderer is released (`videoRendererDispose`) after a frame was delivered but before its block ran, the block dereferences nil and the app crashes (`EXC_BAD_ACCESS` at `0x40`, in `-[FlutterRTCVideoRenderer renderFrame:]_block_invoke_2`). Reported from a macOS app shortly after stopping or changing a screen share, about 1 run in 6; reproduced with `example/integration_test/screen_share_stress_test.dart` (a screen share rendered locally and pulled by a second room, stopped while frames flow, and every second time switched to a window and back): with the old release it crashed after 29 iterations in one run and not in 80 in another, and at the first stop in 3 of 3 runs where the test kept the main thread busy in 40 ms bursts while the views went (as on a loaded Mac); with the fix, no crash in 80 iterations, nor in 60, 52 and 20 with the busy main thread. So `FlutterWebrtcVideoRenderer.dispose` first detaches its stream and waits for the plugin's answer (`setSrcObject(stream: null)`: after it no frame reaches the renderer), then waits 250 ms so the blocks of the last frames run, then releases it. A crash is still possible if the main thread is blocked for longer than that with blocks queued; the fix belongs upstream (a nil check in the block). Since October 2026 (below) a renderer that shows nothing skips the detach, and the wait counts from its last detach: a renderer detached 250 ms or more ago (a muted camera) is released at once, one detached just before still waits out the rest.
- **Fewer renderer calls (October 2026).** A consuming app on macOS 27 (macOS ↔ Chrome) saw `videoRendererSetSrcObject` block the main thread for 520–830 ms each after mute and camera toggles. **Why it blocks:** the Darwin plugin answers it on the main thread (Flutter's UI thread on macOS), and `-[FlutterRTCVideoRenderer setVideoTrack:]` calls `removeRenderer:` on the old `RTCVideoTrack` and `addRenderer:` on the new one; in the bundled WebRTC-SDK (`RTCVideoTrack.mm`, disassembled) each checks `_workerThread->IsCurrent()` and otherwise makes a blocking call to libwebrtc's worker thread, so a call costs whatever the worker thread is doing at that moment. `videoRendererDispose` and `streamDispose` detach the same way when the renderer still holds a track (`render.videoTrack = nil`; `streamDispose` finds the renderer showing each of the stream's video tracks). **Measured** with `example/integration_test/renderer_timing_test.dart` (two rooms in one process, Alice's camera as her self-view and as Bob's view of it, in tiles laid out like the example's, every `flutter_webrtc` call timed with the platform call timing, §4.2) on a MacBook Pro (macOS 27, loaded: load average 12–20 from Photos' media analysis): every `videoRendererSetSrcObject` took 0–48 ms, and no event-loop gap reached 250 ms (2 runs at `main`, 2 with the changes). The worker thread was idle there (the FaceTime camera gave no frames and the microphone sent no audio in these runs, so the camera was "OBSBOT Virtual Camera" and Apple's voice processing never ran): the 0.5–0.8 s are the wait for a busy worker thread (voice processing that restarts on a microphone mute or unmute, §4.2 and §4.5, is the likeliest), which wasn't reproduced. What the package did per action, before → after (`setSrc` = `videoRendererSetSrcObject`, per action with both views on screen):

  | Action | Before | After |
  |---|---|---|
  | microphone mute / unmute | 0 | 0 |
  | camera mute / unmute (`releaseCapture`) | 1 / 1 (self-view detach / attach; Bob's view keeps its track) | 1 / 1 |
  | gallery ↔ stage, tiles with `GlobalKey`s | 0 | 0 |
  | gallery ↔ stage, no keys (views re-created) | 4 `setSrc`, 2 created, 2 released | 0 |
  | camera unpublish | 3 `setSrc` (one a repeat), 2 released | 2, 2 released |
  | camera republish | 2 `setSrc`, 2 created | 2, 2 created |

  What remains is one attach per new track per view and one detach per track that goes, each necessary; they block for as long as the worker thread is busy, which only `flutter_webrtc` can change (§4.2, For flutter-webrtc #2217). The changes:
  - **`FlutterWebrtcVideoRenderer` makes no call that changes nothing:** setting the stream it shows, or `null` when it shows none, sends nothing (unit tests pin it), and a detach is awaited.
  - **Hand-over (`_RendererHandOver`, internal).** A view that goes while its renderer shows a stream leaves the renderer, still attached, for 500 ms; a view of the same stream (the same `MediaStream` object) created meanwhile takes it over with no native call, and after 500 ms it is released. The view parks it in `deactivate` and the new one takes it in `initState`, so in a layout change, where Flutter deactivates the old view before it builds the new one, the video shows in the new view's first frame: no blink, where a re-created view used to show its placeholder until the new renderer's first frame. A view that only moves (a `GlobalKey`) takes it back in `activate`; if a new view took it in that frame, the moved view gets a renderer of its own. A renderer whose calls are still running when its view goes is left once they finish. Renderers are never shared between two views on screen: on the web a renderer's fit and mirroring are its own (one `<video>` element looked up by ID). The remote view's pull survives the swap too (the lease's release waits `RoomOptions.leaseReleaseGrace`, §6.1).
  - **A view given a new source** (another publication or local source) moves its renderer to the new track with one call (the stream replays in a later microtask; the detach happens only if the new source shows nothing by then), instead of a detach and an attach.
  - **No stale frame:** a view shows video only while its renderer was given the view's current stream; until then, its placeholder.
  - Considered and not done: keeping a muted camera's stopped track attached until the next one (the source disposes its stream, and on Darwin `streamDispose` detaches it anyway, the same removal; elsewhere the renderer would hold a stopped track); reusing the native renderer across an unpublish and republish (`createVideoRenderer` and `videoRendererDispose` took 0–82 ms, and the detach and attach remain either way).
- **`ParticipantVideoView`**: `.remote(publication, subscribe: true)` or `.local(mediaSource)`, with `fit` (`VideoViewFit.cover`/`contain`), `mirror` (default: local cameras, except a back camera, where text in front of it would read reversed), a `placeholder` (shown while not pulled, muted or not capturing), and `filterQuality`. Native calls sit behind `VideoRenderer` (`FlutterWebrtcVideoRenderer` by default; `rendererFactory` or the static `defaultRendererFactory` swap in a fake for widget tests), and the renderer is created only once there is video. The renderer is bound once per track: a rebuild (a new widget for the same source or publication, other settings) or a publisher's mute never sets its stream again; only a new track does (widget tests pin it). A view that Flutter *re-creates* got a new renderer and blinked (since October 2026 it takes over the renderer of the view it replaces, above), so apps should keep the widgets above it the same shape: the example's speaking highlight, a `Container.foregroundDecoration` set only while speaking, re-created every tile's view on each speaking change (the self-view blinking every few seconds on a Pixel 10, found in the Windows ↔ Pixel checkpoint); it is now always present, and tiles carry `GlobalKey`s so a layout change moves them. **Layer selection** (M4): a remote video view wraps itself in `SimulcastLayerReporter` keyed by `RemoteTrackPublication.id` (`participantId/trackName`, stable across the publisher's sessions) and reports to `Room.layerReporter` by default (§6.1), with `visible`. `automaticLayers: false` opts out; `layerReporter` reports elsewhere.
- **Connection state** (`RoomConnectionState`), from the session: `initial` with nothing negotiated yet, and `connected` → `connected`; `initial` once something was negotiated (the early connect at join, before the peer connection reports anything) → `connecting`, with the trigger's connect timeout armed; `connecting` → `connecting`; `disconnected` → `reconnecting`. A failure emits `RoomSessionFailedEvent` (`Room.failure`) and starts a re-session (§8): `reconnecting` until the new peer connection is connected (or nothing is negotiated on it; §8.1 step 6), then `connected`, or, when it gives up, `disconnected`. With `ReconnectOptions.enabled: false` a failure goes straight to `disconnected`. The room stays in signaling either way, so `Room.reconnect()` can recover in place.
- **`leave()`**: stops listening, leaves signaling (so others stop pulling), unpublishes every local track in one `tracks/close`, closes the session, disposes the sources and device list the Room created, releases remote wrappers, disposes the broker client, ends `disconnected` and completes its streams. Idempotent; failures along the way are ignored.
- **Events** (`Room.events`, sealed `RoomEvent`, every subtype `final`): participant joined/left/updated and connection quality changed (§7.1), track published/unpublished/muted/subscribed/subscription-failed, local track published/unpublished (with a screen share's `endReason`) and stalled (a screen share, M6), and for the room: connection-state changed, session failed, reconnecting/reconnect-attempt/reconnected/reconnect-failed (§8), audio interrupted/resumed and camera paused/resumed (§4.7), and non-fatal `RoomErrorEvent`s. **Naming (M8 API cleanup):** every subtype ends in `Event` and starts with what it is about: `Participant…` (a remote participant; `ParticipantConnectionQualityChangedEvent` also for the local one), `Track…` (a remote track), `LocalTrack…` (a local publication) or `Room…` (the room, its connection, and the device's call audio and camera).
- **`data`** (`RoomData`, §9): `publish(name, profile:)` returns the session's `LocalDataChannel`; `subscribe(participant, name, profile:, canReply:)` returns a `RemoteDataSubscription` whose `messages` carry `RoomDataMessage.participantId`. The sender is the participant that announced the channel's session in signaling (the Room remembers every session a participant announced, and a session claimed by two participants maps to none), **never the payload**. The subscription follows the publisher to a new session: a detached channel moves with `resubscribeDataChannel`, a live one is closed and subscribed afresh; `messages` carries on.
- **Layer selection and active speaker** (M4): §6.1 and §7. **Typed stats and connection quality** (M12): §7.1.
- **Re-sessioning:** §8.
- **Remote audio** (hardening, after M5). Native platforms play a pulled audio track by themselves; browsers only play media attached to a media element. So the Room feeds every pulled audio track (microphone and screen audio) to an internal `RemoteAudioSink` (`lib/src/audio/`, picked by a conditional import on `dart.library.js_interop`), keyed by `RemoteTrackPublication.id`:
  - **Web:** one hidden `<audio autoplay playsinline>` element per track (`package:web`; the JS track comes from `dart_webrtc`'s `MediaStreamTrackWeb.jsTrack`), in one hidden container. A re-pull swaps the element's `srcObject`; unsubscribing, unpublishing and `leave()` remove it.
  - **Native:** does nothing.
  - **Autoplay policy.** A `play()` refused with `NotAllowedError` marks playback blocked: `Room.isAudioPlaybackBlocked` (`bool`) and `Room.audioPlaybackBlockedChanges` (replaying stream). The app shows a prompt whose tap calls `Room.startAudio()`, which calls `play()` on every refused element synchronously inside the gesture and completes with whether audio plays. Any later successful `play()` (the page got a gesture elsewhere) retries the refused ones too, and removing the last refused track clears the flag. Always `false` on native.
  - **Output device.** `Room.setAudioOutputDevice(deviceId)` (with `canSelectAudioOutput`) uses `HTMLMediaElement.setSinkId` on the web, for current and later elements (not every browser has it), and `flutter_webrtc`'s `Helper.selectAudioOutput` on native (app-wide). A refused device keeps the previous output, as on native: the web sink keeps a device only once every element accepted it (with no element yet, a probe element checks it), and moves back the elements that did. Safari accepts a non-default device only from a user gesture (`NotAllowedError` otherwise, seen in Safari 27); before this, the refused device stuck and every later element retried it out of sight.
    - **A refusal is typed** (decided before 0.1.0): `AudioOutputException(reason, deviceId:, cause:)`, `final`, with `AudioOutputFailure.needsUserGesture` (the browser's `NotAllowedError`; a permissions policy refuses with the same name, documented on the value rather than given its own), `notFound` (`NotFoundError`; on native, a device missing from `enumerateDevices`' outputs), `permissionDenied` (`SecurityError`) or `other`, and the platform's error as `cause`. Before, the platform's error came through unchanged: a JS `DOMException` that isn't an `Exception` and has no Dart type under WebAssembly, or a `PlatformException` whose code differs per platform (`Bad Arguments` on Windows, `selectAudioOutputFailed` on Apple platforms). On the web the reason is the `DOMException`'s `name` (the rejection value checked with `isA<DOMException>()`, which works under dart2js, DDC and dart2wasm), with the error's text as a fallback; `test/audio/web_audio_output_failure_test.dart` checks it in Chrome under DDC and dart2wasm (`flutter test --platform chrome [--wasm]`), and a dart2js release build was checked by hand. Headless Chrome without a microphone permission refuses with `SecurityError` ("No permission to use requested device"), hence `permissionDenied`: the app asks for the microphone rather than for a tap. On native, `Helper.selectAudioOutput`'s error is wrapped, `notFound` when the device isn't listed; `flutter_webrtc` checks no permission for outputs there, so native never reports `permissionDenied`. `UnsupportedError` (no output selection here) is unchanged. It is not a `MediaException`: that sealed family is the capture side's (`LocalMediaSource.errors`, the screen picker), and an exhaustive `switch` over it would have to handle a case that never comes there. Like `AudioRouteUnavailableException` (phones' routes, §4.6) it stands alone.
  - **Speakerphone** (phones). Out of the box the platforms disagree: Android's `flutter_webrtc` starts a call on the loudspeaker (its preferred outputs are Bluetooth, wired, speaker, earpiece), while iOS configures WebRTC's audio session as play-and-record in voice-chat mode without "default to speaker", which plays from the earpiece, even in a video call (seen on an iPhone, iOS 27). The Room makes them agree: `RoomOptions.speakerphone` (default `true`) is applied when the room joins, and `Room.setSpeakerphone(on)` / `isSpeakerphoneOn` / `speakerphoneOnChanges` switch it; `canSetSpeakerphone` is `false` on desktops and the web, where the switch throws and `setAudioOutputDevice` chooses a device. Either way a connected wired or Bluetooth headset comes first. On iOS it sets WebRTC's base configuration (`Helper.setAppleAudioConfiguration`: video chat with `defaultToSpeaker`, or voice chat), because WebRTC applies that again whenever it starts audio and a one-off route override wouldn't last; then the route now. On Android `Helper.setSpeakerphoneOn` reorders the preferred outputs (which later headset changes follow) and `setSpeakerphoneOnButPreferBluetooth` picks a headset again when there is one. Like the platforms' switches, it is app-wide.
  - Tests swap the sink through `debugRemoteAudioSinkFactory` (internal) and check the bookkeeping. The web element code is checked in a browser by `example/integration_test/audio_routing_test.dart`: verified in Chrome 154, as JS and as Wasm (M13): one element per pulled track, playing (not paused, its clock moving), and `setSinkId` moves it to each output and back to `default`. Chrome plays it without a gesture while the page captures the microphone, so `isAudioPlaybackBlocked` stays `false` in a call that publishes audio; a receive-only page is where the autoplay prompt matters. Each `Room` adds its own hidden container (all with the same `id`, `cloudflare-realtime-remote-audio`).

### 4.4 `Signaling` (app-provided)

A small interface. Roughly:

```dart
abstract interface class Signaling {
  Future<void> join(String roomId, ParticipantState self);
  Future<void> update(ParticipantState self);
  Stream<List<ParticipantState>> get participants; // excludes self
  Future<void> leave();
}
```

- `ParticipantState` is `{participantId, sessionId?, tracks: {trackName → {kind, source, muted?, simulcast?}}, metadata?}`. Its `toJson`/`fromJson` define the JSON that adapters put into presence payloads; the shape is documented on the class.
  - **`muted`** (M3, optional): `true` while the publisher sends nothing for the track; omitted when `false`, and anything but `true` reads as `false`, so older peers interoperate.
  - **`simulcast`** (M3, optional): `{"rids": ["a","b","c"], "width": 1280, "height": 720, "scaleDownBy": [1,2,4]}` (`SimulcastInfo`), the layers a video track sends, highest first. Only `rids` is required. It is a hint, so it is parsed tolerantly: malformed input reads as "no hint" rather than failing the participant. Subscribers send a `preferredRid` only for tracks that carry it, and layer selection builds the publisher's ladder from it (§6.1). Since M12 the size is the captured one, and it changes when the capture does (§6.3).
- **`layerDemand`** (M12, optional, top level): `{"<trackName>": "<rid>"}`, the layer the participant pulls of each simulcast video it pulls (§6.2). Absent means "not reported", which publishers read as "every layer"; a malformed value reads the same way.
- `participants` replays the current list to new listeners, emits `[]` while not in a room, and never includes the caller's own entry.
- **Ship an in-memory implementation** for tests and the example app: `InMemorySignaling`, where participants share an `InMemorySignalingHub` (several rooms per hub).
- **Keep backend adapters out of the core package.** For example, a Supabase Realtime presence adapter would be a separate package, such as `cloudflare_realtime_supabase`, or it lives in the app.
- **Dev signaling is an example, not core.** For multi-device testing there is a DEV ONLY local stack in [`tools/dev-server/`](../tools/dev-server/README.md). It mounts the broker core with a shared dev token, and adds a WebSocket presence endpoint whose protocol maps 1:1 to `Signaling`. Its Dart client, `WsSignaling`, lives in `example/lib/ws_signaling.dart`, and `web_socket_channel` is an example-only dependency. The core package gains no WebSocket or backend dependency from it.
- The core must not depend on any backend SDK.

### 4.5 Media

**Implemented** in `lib/src/media/`. It ports partytracks' `getDevices.ts`, `deviceManager.ts`, `resilientTrack$.ts`, `makeBroadcastTrack.ts` and `getScreenshare.ts` to Dart streams. Publishing is not part of it: M2's `SfuSession` consumes the tracks.

- **`MediaBackend`** wraps the `flutter_webrtc` APIs: `getUserMedia`, `getDisplayMedia`, `enumerateDevices`, `ondevicechange`, and `desktopCapturer` (`getSources`, `updateSources` and the `onAdded`/`onRemoved`/`onNameChanged`/`onThumbnailChanged` events).
  - Everything above it is unit-tested with fakes. `FlutterWebrtcMediaBackend` is the production implementation.
  - `desktopCapturer` is `null` on web and mobile.
- **`MediaDeviceList`** holds cameras, microphones and audio outputs.
  - It enumerates once, then again on every `devicechange`, and emits only real changes. This is partytracks' `devices$`.
  - **It enumerates when first used** (October 2026): reading `ready`, `devices` (or a kind's list) or a change stream, or calling `refresh()`, starts it; until then it ignores `devicechange`. Before, it enumerated when created. A source reads and watches the list without starting it (`MediaDeviceListInternal`, internal), and starts it at once unless it can capture without it (Capture before listing on macOS, below), so nothing else changes.
  - Camera and microphone sources can share one list.
  - Each camera carries **`MediaDevice.facing`** (`CameraFacing.user`/`environment`) where the platform says: the native plugins report it (`front`/`back`; a Mac's built-in camera is `unspecified`), and in browsers the label decides ("Front Camera", "camera2 1, facing front"). Desktop cameras have none. On Windows and Linux the label decides too: flutter_webrtc's C++ plugin makes the facing up (`front` for the second camera in its list, `back` for every other one), which put a desktop's webcam as `environment` (not mirrored in the self-view) and a virtual camera as `user` (found in the M13 Windows run).
  - The speaker is chosen with `Room.setAudioOutputDevice` (§4.3).
- **`CameraSource` and `MicrophoneSource`** (both `DeviceMediaSource`) handle device selection:
  - A **preferred device** sorts first. The priority order is: preferred, then the **system default**, then the rest, then virtual devices and the "iPhone Microphone", then devices that recently failed. A device is virtual when its label says "virtual" or, for cameras only, names a well-known virtual camera app whose labels don't say so: NVIDIA Broadcast ("Camera (NVIDIA Broadcast)", found in the M13 Windows run, where `switchCamera()` went to it before the real webcam's virtual twin), Snap Camera, XSplit VCam, ManyCam and mmhmm. Microphones of those apps keep their place, since people choose NVIDIA Broadcast's noise removal on purpose, and "obs" alone isn't matched: OBS's camera already says "virtual", and OBSBOT makes real webcams. Within each group, cameras facing `CameraOptions.facing` come first, then cameras that don't say, then the others, so a phone opens its front camera whatever order the platform lists it in (Android lists the back camera first).
  - **The system default** (`MediaDevice.isDefault`) comes before the platform's order, even when it is virtual: someone who made "SteelSeries Sonar - Microphone (SteelSeries Sonar Virtual Audio Device)" their default routes their microphone through it on purpose (found in the Windows ↔ Pixel checkpoint: the call opened another of six inputs). Only the "iPhone Microphone" stays down, even as a browser's default, for partytracks' reason.
    - **Windows:** `flutter_webrtc` doesn't say which device is the default. Its plugin lists audio devices by index from libwebrtc's `AudioDeviceWindowsCore`, which enumerates the active Core Audio endpoints in their own order (by endpoint ID, checked on Windows 11), with no default entry, and `getUserMedia` opens index 0 when no `sourceId` is given. libwebrtc would use the default communications device (`eCommunications`) if nothing set an index, but the plugin always does. So the backend asks Core Audio itself (`IMMDeviceEnumerator::GetDefaultAudioEndpoint`, communications role, else console) through `dart:ffi` (`windows_audio_defaults_ffi.dart`, no plugin and no new dependency), on every enumeration, and marks the microphone and speaker whose `deviceId` (the plugin reports the endpoint ID) matches. A default changed in Sound settings during a call is marked at the next device-list change, but the running capture doesn't move to it (the user can choose it).
    - **Browsers:** Chromium lists `default` and `communications` entries ("Default - Headset Microphone") first; they are marked. Safari and Firefox have none.
    - **Elsewhere** nothing is marked: macOS, Android and iOS don't say through `flutter_webrtc` (phones route call audio themselves, §4.6), and no OS has a default camera. Desktop cameras keep the platform's order (Windows: DirectShow's), virtual cameras last.
    - **Audio output on Windows** needs nothing: libwebrtc plays to the default communications device until `Room.setAudioOutputDevice` (`Helper.selectAudioOutput`) picks an index.
  - **Switching during a call:** `setPreferredDevice` on a published camera or microphone captures from the new device, then releases the old one, and the sender gets the new track with `replaceTrack` (no renegotiation). On Windows, libwebrtc's audio device wrapper stops, switches and restarts the recording device (verified on Windows 11: the capture session moved to the chosen microphone).
  - **Capture tries devices in that order** until one yields a track. A permission error stops the search at once (`MediaPermissionDeniedException`). If every device fails, the source reports `DevicesExhaustedException` and turns off.
  - **Bounded capture** (hardening, October 2026). A `getUserMedia` that doesn't answer within `captureTimeout` (a constructor argument of `CameraSource` and `MicrophoneSource`, **30 s** by default, `DeviceMediaSource.defaultCaptureTimeout`; `null` waits) fails the source with `MediaCaptureException` (its `cause` a `TimeoutException`). The search stops there (a platform that doesn't answer won't answer for the next device, and each would add the full timeout), and the device goes last for the next attempt. A stream that arrives after the timeout is released at once (its tracks stopped, the stream disposed), so the late capture doesn't keep the microphone or camera; the source's reconcile loop moves on, so `disable`, a retry and `dispose` work. The timeout includes a permission prompt the platform shows inside `getUserMedia` (the first capture on iOS, macOS and Android, and the browser's prompt); 30 s leaves the user time to answer it, and an app that may leave a prompt open longer asks for the permission first or passes a longer timeout or `null`. `MediaDeviceList` enumerations get `MediaDeviceList.enumerationTimeout` (10 s), since sources wait for the first enumeration before capturing. One that runs over fails soft: no error, the list is left as it was, a capture without a list lets the platform choose the device, and the refresh after that capture reads the list again (its late result is dropped). A Mac's first enumeration in a process takes up to about 9 s (AVFoundation building its capture-device list, §4.2, macOS: a slow first join), close to the limit; going over it there costs only the device choice for that first capture.
  - **Capture before listing on macOS** (October 2026; §4.2, macOS: a slow first join). A Mac's first device list in a process (`getSources`) blocks the main thread, the UI thread, for 5–9 s, and a microphone with nothing chosen doesn't need it: the audio device module lists the system default first as `default`, and selecting that by ID needs no list. So a `MicrophoneSource` on macOS with no device that failed and a device list nothing has used yet captures from its preferred device by ID (`publishMicrophone(device:)`, `setPreferredDevice`; since October 2026, after the platform call timing found the list inside a chosen microphone's first publish, §4.2) or else from `default` (`unlistedDefaultDevice`, a `MediaDevice` with an empty label), without reading the list; the backend selects either with `Helper.selectAudioInput`, as before, and the list isn't read after the capture either. Later passes keep that capture while nothing asks for the list, and a newly preferred device is captured the same way. A preferred device that is gone fails its selection (the plugin answers `selectAudioInputFailed`), and the list is read then. So is a preferred device that has become the system default: the module lists the default only as `default`, not under its own ID (seen with "BlackHole 16ch": its saved ID failed, and the capture fell back to `default` through the list). The list is read when something needs it: a capture that fails (the listed devices are then tried in priority order, `default` not twice, and `DevicesExhaustedException` lists every failure), an ended track, a camera on the same list, or the app reading or watching the devices (a device picker); `activeDevice` then shows the listed entry, with its label. Cameras, and microphones on other platforms, read the list first as before: Windows opens the first device it lists unless told which (§4.5 above), browsers give labels only through the list, phones pick cameras by facing, and a Mac's camera capture lists the cameras through AVFoundation anyway. Unit tests: `test/media/device_media_source_test.dart` (Capture before listing on macOS), `test/media/media_device_list_test.dart`, `test/room/room_test.dart` (macOS microphone).
  - **Fallback:** when the active device is unplugged (a device-list change, or the track's `onEnded` on web), the source captures from the next device.
  - **Return:** when the preferred device comes back, the source switches back to it.
  - **Deviation from partytracks:** partytracks restarts capture on *any* device-list change. Here, capture restarts only when:
    - the active device went away,
    - the preferred device became available,
    - the options changed, or
    - the track ended.
  - **Deviation from partytracks:** it persists the preference and the failed-device list in `localStorage`. Here the app persists the preference (`preferredDevice` / the `preferredDevice:` argument). A failed device is tried last only until it is unplugged or chosen again.
  - Consumers never re-subscribe. `track` emits the replacement track. When switching to a different device, the new track is captured before the old one is stopped, so there's no `null` gap. Phones allow this too: on a Pixel 10, front ↔ back took 0.4–0.6 s with both open briefly.
  - **`CameraSource.switchCamera()`** (and `LocalParticipant.switchCamera()` for the published camera) is one call on every platform: it flips front ↔ back where the cameras say which way they face, and otherwise moves to the next camera in priority order (so virtual cameras come last), wrapping around. The choice becomes the preferred device, so an app can persist it. With one camera it does nothing. In a browser before permission, devices have no IDs, so it flips `CameraOptions.facing` (the `facingMode` constraint) instead. A publication keeps its track name and sender: the subscriber sees the new camera without pulling again, and nothing is renegotiated.
  - **Options:**
    - Camera: `VideoPreset` (`h1080`, `h720`, `h540`, `h360`, `h180`; target width, height and frame rate, which cameras match as closely as they can) and `facing`, **`CameraFacing.user` by default** (`null` keeps the platform's order). `h720` scaled by ½ and ¼ gives `h360` and `h180`, which are the simulcast layers in §6.
    - Microphone: echo cancellation, noise suppression and AGC, all on by default.
    - `setOptions` recaptures.
- **The mute model.** `LocalMediaSource` has two switches, as in partytracks:
  - **enabled** means capturing. `track` is the live track, or `null`.
  - **broadcasting** means sending. `broadcastTrack` is the track while it is both enabled and broadcasting, else `null`.
  - The two are linked: `startBroadcasting` enables the source, and `disable` stops broadcasting.
  - **Mute policy.** `MutePolicy` decides what `stopBroadcasting` does. It is partytracks' `retainIdleTrack`, made explicit:
    - `keepCapture` (default for the microphone): stay capturing. Unmute is instant, and "talking while muted" is possible. The OS mic indicator stays on.
    - `releaseCapture` (default for the camera and screen): also disable, so the camera light goes off.
  - `flutter_webrtc` can't synthesize partytracks' fallback tracks (the black canvas and inaudible tone). So "not broadcasting" is a `null` `broadcastTrack`. **M2 should `replaceTrack(null)` on the sender** (or send a disabled clone) and keep the SFU track published.
  - **Failures** go to `errors` and turn the source off. The methods return whether capture is running; they don't throw for capture failures. All capture work runs through one coalescing reconcile loop per source, so concurrent calls can't race.
  - The source owns its tracks: it stops them and disposes their streams when it replaces or releases them.
- **`flutter_webrtc` realities** (checked against 1.6.2+hotfix.3, the version in `pubspec.lock`):
  - **Native `getUserMedia` ignores the W3C `deviceId: {exact: id}`.**
    - Windows and Linux read only `optional: [{sourceId: id}]`, and treat a string `deviceId` on audio as the *output* device.
    - Android and Darwin read `deviceId` as a plain string.
    - So native platforms get `optional.sourceId`, and the web gets `deviceId.exact`.
  - **Native `getUserMedia` doesn't reliably read `{ideal: n}` either.** Darwin reads `ideal` only as a string: with a number, it picks the camera's smallest format and a frame rate of 0 (a MacBook's FaceTime HD camera captured 640×480 instead of 1280×720, so it sent two simulcast layers instead of three). Android never finds `ideal` and falls back to 1280×720 at 30 fps whatever the preset. Windows and Linux read it. Every native platform reads a bare number (as a target, not a requirement), so native platforms get `width: 1280`, and the web keeps `{ideal: 1280}`.
  - **Native `enumerateDevices` drops the camera's `facing`**, which the Android and Darwin plugins report in the underlying `getSources` list. The backend reads `getSources` on native platforms (deprecated in `flutter_webrtc`, so it falls back to `enumerateDevices` and labels if it fails). Labels alone won't do on iOS, where they are localized.
  - **iOS lists its virtual multi-camera devices first** ("Back Triple Camera", "Back Dual Camera", "Back Dual Wide Camera"), and `flutter_webrtc`'s capturer gets no frames from them (an iPhone on iOS 27: 1–2 frames in 6 s, against 150–176 from "Back Camera", whichever order the switch closed and opened in). The backend orders Apple's built-in cameras by the index in their ID (`com.apple.avfoundation.avcapturedevice.built-in_video:N`: `:0` back, `:1` front, the virtual ones higher), so the plain cameras come first and `switchCamera()` flips to "Back Camera". The others stay listed for a picker.
  - **Android and macOS don't select the microphone named in `getUserMedia`**: they read `optional.sourceId` only to report it back in the track's settings, and capture from whichever input `Helper.selectAudioInput` chose last. So on both the backend calls `selectAudioInput` before capturing a microphone. Windows selects it from the constraints.
    - **macOS:** the Darwin plugin means to select it (`getUserAudio` calls `selectAudioInput`), but behind `#if !defined(TARGET_OS_IPHONE)`, which is never true on an Apple platform (`TargetConditionals.h` defines `TARGET_OS_IPHONE` as 0 on macOS; reported as [flutter-webrtc #2216](https://github.com/flutter-webrtc/flutter-webrtc/issues/2216)). libwebrtc's audio device module is one per process and starts on the system default (its list has it first, as `deviceId` `default`, marked `isDefault`), so the call kept capturing from the default whatever the user chose. Found on a Mac whose default input is BlackHole, a silent loopback device: choosing "MacBook Pro Microphone" in the example's Devices sheet changed the track but not the recording device, and the remote heard nothing. With the fix the module logs `Setting input device: MacBook Pro Microphone` on each switch (`example/integration_test/microphone_capture_test.dart`).
    - **macOS: the audio device module undoes some switches**, so the backend selects the input again. WebRTC-SDK's AVAudioEngine module (as `flutter_webrtc` 1.6.2 creates it, with Apple's voice processing on) goes back to the system default whenever it sees the device list change, and rebuilding its voice-processing graph for a new input seems to change that list. On that Mac, switching between "MacBook Pro Microphone" and BlackHole, the module logged `Setting input device`, then `Did update devices` and `Using default input device` within a second or two (its state line: `inDev=89` → `inDev=0`, `inDevChanged=1`) on 5 of 27 switches in one set of runs and on 2 of 2 in another; selecting the same input again restored it, and selecting the input it already uses does nothing. `flutter_webrtc` doesn't pass the module's device updates on (it sets `audioDeviceModule.observer = self` before the module exists), so the package can't react to the event: `MacInputReselector` selects a non-default input again 1, 2, 4 and 8 s after each switch, and a newer selection cancels the pending ones. A selection (the first one too) waits while a description is being applied (`NativeNegotiation`, §4.2): the plugin selects on the main thread and waits for the module, which the first audio send keeps busy for up to 23 s on macOS, and a re-selection timed into that window froze the app for 8 s after a join. A device-list change later in the call (a headset plugged in) can still move the module to the default unseen; the same missing observer means `ondevicechange` never fires on macOS, so the device list isn't refreshed on plug or unplug there either (read from the plugin's source, not yet checked by hand). Both belong upstream.
    - **macOS, still open: capture sometimes stalled after a switch.** Before the re-selection was added, `audio_routing_test.dart` saw no packets reach the subscriber for 30 s after choosing the built-in microphone in 3 of 8 runs (0 of 3 without the selection fix, when nothing really switched), and a capture run saw no samples for 3 s; with the final code, 3 capture runs and 3 routing runs in a row passed, at a lower machine load (load average about 20 instead of 100–500). Not caught with native logging yet, so whether the re-selection or the load made the difference is unknown.
    - **Sound can't prove the choice.** With Apple's voice processing on, the built-in microphone read exact zeros for long stretches in a quiet room (and the room's sound when there was some), and a loopback device carries whatever the Mac plays, so `media-source` energy tells a real microphone from BlackHole only while someone talks. `microphone_capture_test.dart` therefore checks the module's own log line through `flutter_webrtc`'s native log, and checks energy only on request (`CF_REALTIME_EXPECT_SOUND=1`).
    - **iOS is unchanged and unchecked.** The same guard skips the selection there, and the plugin's `selectAudioInput` sets the session's preferred input (which moves the route), so it would interfere with call audio routing (§4.6, `Room.selectAudioRoute`). Whether `MicrophoneSource.setPreferredDevice` has any effect on iOS is still to be checked on a device.
  - **Windows silently opens the first camera** when the requested one is missing. The source trusts the track's `deviceId` setting over what it asked for.
  - **Native tracks never fire `onEnded`.** Device loss on native platforms is detected from the device list, and a desktop share ending from the capturer's source list (§10).
  - `ondevicechange` is a single callback slot. The backend multiplexes it and chains any previous handler.
  - Native errors are plain strings (`"Unable to getUserMedia: ..."`). Errors are classified by text.

### 4.6 Call audio routing (native)

**Decided (October 2026)** after comparing how Agora, LiveKit, ZEGOCLOUD, Stream, 100ms, Daily and others route call audio, and what Android and iOS allow. The research report lives outside the repository.

- **One route list on both phones.** The Room exposes `audioRoutes` (with `audioRoutesChanges`), each an `AudioRoute` with an `id`, a `kind` (`speaker`, `earpiece`, `wiredHeadset`, `bluetooth`, `usb`, `other`) and a `name`. It also exposes `audioRoute` with `audioRouteChanges`, and `selectAudioRoute(route)`. `setSpeakerphone(bool)` stays as shorthand for "the speaker" and "not the speaker". `canSelectAudioRoute` is `false` on desktops and the web, where `setAudioOutputDevice` chooses a device.
  - The id is opaque. Today, on Android, it is an `AudioDeviceInfo` id, so two Bluetooth headsets are two routes. Core-Telecom endpoint UUIDs can replace it later without an API change.
  - **Selection is a request, confirmed by events.** Android applies it asynchronously, and iOS resets the speaker override on any route change. The Room's `audioRoute` is always read back from the platform, never assumed.
  - **The list shows only routes the platform will honour.** Neither phone can reach the earpiece while a Bluetooth headset is connected, so the earpiece isn't listed then.
  - **iOS has no general output setter.** Its list is the speaker, the receiver (when no headset is connected), and wired and Bluetooth hands-free routes, which are reached by choosing their input (`setPreferredInput`, and the output follows). Stereo-only Bluetooth (A2DP) and AirPlay can only be chosen in Apple's route picker: they appear as the current route when the user picks them, but can't be selected in code. A system picker widget (`AVRoutePickerView`, behind a capability flag) is planned as an addition and doesn't change this API.
- **The default follows the call.** With `RoomOptions.speakerphone` left `null` (the default), a call starts on the earpiece and moves to the speaker once the call has video, the local camera or any received video, as FaceTime does. It doesn't move back by itself when the video stops. A connected headset always comes first. `true` or `false` forces the speaker or the earpiece.
- **A route the user picked sticks** until a new headset arrives or the chosen route disappears. Only automatic choices follow the default. Re-applying a priority order on every device change, as Daily and AudioSwitch do, overrides the user, and that is the most-reported routing bug in the SDKs studied.
- **The policy is Dart; the platform code is thin.** A small native layer in this package (it becomes a Flutter plugin for Android and iOS) only lists routes, reports the current route and changes, selects and clears, and activates and deactivates the call's audio session. The default, the stickiness and the "video started" rule live in Dart behind an internal `CallAudioBackend`, so they are unit-tested with a fake. A CallKit or Core-Telecom backend can replace the native one.
  - **Android, API 31 and later:** `AudioManager.setCommunicationDevice` from `getAvailableCommunicationDevices`, `getCommunicationDevice`, and `OnCommunicationDeviceChangedListener`; `MODE_IN_COMMUNICATION` and audio focus while a call has audio. Earlier releases use `setSpeakerphoneOn` and Bluetooth SCO. Bluetooth routes need the app's `BLUETOOTH_CONNECT` permission on Android 12+; without it they are simply missing.
  - **iOS:** WebRTC's `RTCAudioSession`, with its base configuration set (`playAndRecord`; `voiceChat`, or `videoChat` for the speaker; Bluetooth hands-free allowed), because WebRTC applies that configuration again whenever it starts audio. On top of that: `overrideOutputAudioPort`, `setPreferredInput`, `currentRoute`, and `routeChangeNotification`. The notification arrives off the main thread and is re-posted, and a re-entrancy guard keeps a route change caused by our own call from being handled as a user change.
  - **On Android, flutter_webrtc's audio management is turned off** when the plugin loads (`AudioSwitchManager.setAudioSessionManagementEnabled(false)`, called by reflection, so there is no build-time dependency on flutter_webrtc's Android code). Its AudioSwitch re-selects a route by its own priority on every device change, which would undo ours. With it off, flutter_webrtc's Android list of audio outputs is empty, so `audioRoutes` replaces it on phones. Microphone selection (`Helper.selectAudioInput`) doesn't go through AudioSwitch and keeps working.
  - **On iOS the base configuration follows the route being chosen:** voice chat for the receiver, video chat for the speaker, and the call's default for a headset. Clearing the speaker override (the way to the receiver and to headsets) falls back to the base's route, so with video chat as the base, choosing the receiver landed on the speaker again (seen on an iPhone, before this rule).
  - **On iOS, flutter_webrtc keeps managing the session.** Its session code doesn't re-route on its own; it only adjusts the session when tracks start, and it reports route changes. So the base configuration goes through its `Helper.setAppleAudioConfiguration`, and the plugin's iOS code is plain AVFoundation, with no dependency on flutter_webrtc or WebRTC.
- **Interruptions and the proximity sensor** follow the same split (policy in Dart, thin native code) and live next to the route in `CallAudio`: §4.7.
- **CallKit (iOS) and Android Telecom** (M11, §4.8). While a system call exists the system takes over the audio session and, on Android, routing: CallKit activates the session, and Core-Telecom routes through `requestEndpointChange`, forbidding `setCommunicationDevice`. `CallAudio` then runs on a `SystemCallAudioBackend` (`CallAudio.useSystemCall`) behind the same route API and the same policy: Telecom's endpoint UUIDs become the route IDs, and a route the user picked carries over by kind. Hence the backend seam above, and route ids that are not tied to AudioManager.

### 4.7 Calls outside the foreground: background, interruptions, proximity (native)

**Decided (October 2026), M10 part B.** A call keeps its microphone, camera and connection when the app is backgrounded, survives a phone call or another app taking the audio, and turns the screen off at the ear. One Dart API on every platform; the phones do the work, desktops and the web report `false`/`null` and do nothing. Part A of M10 (a publish that outlives an expired session, §4.2 and §8) is separate. The policy is Dart and unit-tested with fakes (`test/audio/call_audio_test.dart`, `test/background/call_background_test.dart`); the native code is thin, as in §4.6.

- **The API.**
  - Background: `RoomOptions.foregroundService` (Android, default `true`); `Room.cameraPause` / `cameraPauseChanges` / `canDetectCameraPause` with `RoomCameraPausedEvent(reason)` and `RoomCameraResumedEvent` (iOS; `CameraPauseReason`: `background`, `inUseByAnotherApp`, `multipleForegroundApps`, `systemPressure`, `other`). Failures to start the service are `RoomErrorEvent('foregroundService', …)`.
  - Interruptions: `Room.audioInterruption` (a `CallInterruptionReason` or `null`; `held` while a system call is on hold, §4.8) / `audioInterruptionChanges` / `canDetectAudioInterruptions`, `RoomAudioInterruptedEvent(reason)` and `RoomAudioResumedEvent(reason)`, and `Room.resumeAudio()`. App-wide, like the audio session, so held by `CallAudio` (§4.6) next to the route.
  - Proximity: `RoomOptions.proximitySensor` (default `true`) and `Room.proximitySensorActive` / `proximitySensorChanges`.
  - The screen kept on: `RoomOptions.keepScreenAwake` (`KeepScreenAwake.whileVideo`, the default; `always`; `never`) and `Room.keepingScreenAwake` / `keepingScreenAwakeChanges` / `canKeepScreenAwake`. Unlike the rest of this section it works on desktops and in browsers too (below).
- **Background on Android: this package's foreground service.** Android 11+ silences the microphone and stops the camera of a backgrounded app unless a foreground service of type `microphone` / `camera` runs, and Android 14+ lets such a service start only while the app is in the foreground and holds the runtime permission. So `CallBackground` (Dart, `lib/src/background/`) runs `CallService` while any joined room publishes a microphone or a *capturing* camera (a muted camera has released its capture, §4.3): type `microphone`, plus `camera` while a camera captures. It starts on the first publish (the app is in the foreground then), its types follow the camera, and it stops when nothing is published or the last room leaves. The manifest entries (the service, `FOREGROUND_SERVICE_MICROPHONE` and `_CAMERA`) merge into the app.
  - **Changing the types** calls `startForeground` again on the running service rather than starting it again: Android 12+ refuses a start from the background, not an update. Adding `camera` from the background is still refused on Android 14+ (while-in-use); that, or any refused start, is reported once as a `RoomErrorEvent` and retried when the app returns to the foreground.
  - Only types the app holds the permission for are requested (`RECORD_AUDIO`, `CAMERA`); with neither, there is no service. The notification (channel "Calls", low importance, texts and icon as overridable resources) taps back into the app. The package doesn't ask for `POST_NOTIFICATIONS` for it: without it the service runs and Android lists it only in the task manager. `stopWithTask`: swiping the app away ends the call.
  - **Separate from the screen share's service (§10), on purpose.** One service with combined types was the alternative. But the `mediaProjection` service has its own ordering rule (after consent, before capture), its own "Stop sharing" action and a lifecycle tied to the share, all verified on devices (M9); merging would tie the call's types to the projection's rules. The cost is two notifications during a share in a call.
  - `RoomOptions.foregroundService: false` (any room that sets it doesn't count) is for apps that run their own service. The `phoneCall` type is added by a system call (§4.8), which also makes `CallService`'s notification the call's `CallStyle` one. A receive-only call (nothing published) gets no service; its playback may stop once Android freezes the backgrounded app.
- **Background on iOS: the audio background mode.** The app declares `UIBackgroundModes: audio` (README); with an active audio session (any call with audio) iOS keeps it running. The `voip` mode belongs with PushKit (§4.8). The **camera** is different: iOS interrupts every capture session of a backgrounded app (`AVCaptureSession.wasInterruptedNotification`, reason `videoDeviceNotAvailableInBackground`). `flutter_webrtc` uses WebRTC's `RTCCameraVideoCapturer`, which restarts its session by itself when the interruption ends or the app becomes active again, so the track stays live and simply sends no frames meanwhile (subscribers see the last frame): nothing tells the app. The plugin (`CallBackground.swift`) observes the capture-session notifications for every session in the process (it can't reach `flutter_webrtc`'s) and reports `Room.cameraPause`; the room emits `RoomCameraPausedEvent` only while it publishes a camera. **Multitasking camera access** (`AVCaptureSession.isMultitaskingCameraAccessSupported`, iOS 16+) keeps the camera in multitasking scenes and in a video-call picture-in-picture window, never in the plain background. It is supported for an app linked against iOS 18+ with `voip` in `UIBackgroundModes` (no entitlement needed), an iPad with Stage Manager on an external display, or an app with the multitasking camera entitlement (the only way on iPhones with iOS 16–17). `flutter_webrtc` doesn't enable it, and today the package doesn't reconfigure `flutter_webrtc`'s session. Keeping the camera in the background therefore comes with picture-in-picture (M14; the plan is in [roadmap.md, M14 notes](roadmap.md#m14-notes-picture-in-picture-and-the-ios-camera-in-the-background)).
- **Interruptions, the same shape on both phones.** The platform says when the call's audio is taken away and (sometimes) given back; `CallAudio` holds the state and decides when to take the audio back:
  - **While interrupted** the room keeps the call silent: pulled audio tracks and the microphone's track are disabled (the microphone sends silence), with nothing announced: the track isn't muted in signaling, and the user's own mute state is untouched. iOS stops both directions itself; Android doesn't stop a VoIP app's playback during a phone call, so the room does it on both.
  - **Taking the audio back** (`CallAudioBackend.resume`: iOS activates the session again, Android requests the audio focus and `MODE_IN_COMMUNICATION`) happens when the platform ends the interruption, when the app returns to the foreground (the platform doesn't always end it), or on `Room.resumeAudio()`. It fails while something with priority (a phone call) holds the audio, and the call stays interrupted. Then the route is chosen again (§4.6).
  - **iOS:** `AVAudioSession.interruptionNotification` (began, ended). The reason is always `unknown`: iOS doesn't say whether a phone call, Siri, an alarm or another app's audio interrupted. (`CXCallObserver` would tell a phone call apart. With a system call (§4.8), CallKit holds the call instead, which arrives as `held`; the interruptions then come from the call, not from the audio session, and the plugin doesn't forward the session's notifications while a CallKit call exists.) WebRTC's `RTCAudioSession` re-activates the session itself after any interruption, even one iOS says not to resume (`shouldResume` false), and treats the app becoming active during an interruption as its end; so the package resumes on any end too, and `flutter_webrtc` itself does nothing about interruptions on iOS.
  - **Android:** audio focus, requested with the call (§4.6; `flutter_webrtc`'s own focus handling is off with its AudioSwitch). `AUDIOFOCUS_LOSS` and `LOSS_TRANSIENT` begin an interruption, `GAIN` ends it; `LOSS_TRANSIENT_CAN_DUCK` (a navigation prompt, a notification) is ignored: the call goes on. A permanent loss (a media player) never ends by itself, so it lasts until the app returns to the foreground or calls `resumeAudio()`. The reason is `phoneCall` while the audio mode says a phone call rings or runs (`MODE_RINGTONE`, `MODE_IN_CALL`, `MODE_CALL_SCREENING`, `MODE_CALL_REDIRECT`; refined with `OnModeChangedListener` on Android 12+, since the mode may change after the focus), else `otherAudio`; no `READ_PHONE_STATE` is needed. During a phone call Android also gives other apps' microphones silence.
- **The proximity sensor.** On while call audio plays on the earpiece (`CallAudio.current`'s kind) and no room has video, unless a joined room turned it off; off on the speaker, a headset, with video, and when the last room leaves. "Video" is §4.6's rule (sent or received, for the rest of the call), so a call that had video never turns it on. Android: a `PROXIMITY_SCREEN_OFF_WAKE_LOCK` (the package declares `WAKE_LOCK`), released with `RELEASE_FLAG_WAIT_FOR_NO_PROXIMITY` so the screen doesn't come on against the ear; not on devices without the sensor. iOS: `UIDevice.isProximityMonitoringEnabled`, which reads back `false` without a sensor (iPads). `isProximitySensorActive` is what the platform confirmed.
- **Keeping the screen on** (found in the Windows ↔ Pixel checkpoint: during a video call on a Pixel 10, Android 16, the screen dimmed and would have locked). **During a live video call the screen must not dim or lock;** a voice call lets it sleep as usual, so the proximity sensor can turn it off at the ear. The policy is Dart (`ScreenAwake`, `lib/src/screen_awake/`, app-wide like `CallAudio`; each room's part in `room_screen_awake.dart`), behind a small `ScreenAwakeBackend` with a fake in `test/screen_awake/screen_awake_test.dart`.
  - **When.** A room wants the screen kept on while it is joined and not `disconnected` (connected, connecting or reconnecting; so not after it gave up, nor after `leave()`) and, with `whileVideo`, while **video is live**: a local camera or screen share (or app source) published and sending (not muted), or a remote video subscribed (`isSubscribed`: a mounted `ParticipantVideoView`'s lease, auto-subscribe or `subscribe()`, not a lease whose views stayed hidden) and not muted by its publisher. Unlike §4.6's "video" (sticky for the rest of the call), this follows the video now. `always` drops the video condition; `never` never asks (for apps with their own wakelock). The screen is kept on while **any** joined room wants it. The room re-evaluates on every room event, local change and remote publication change.
  - **The proximity sensor wins.** While it is on (`CallAudio.proximity`: a call on the earpiece without video) the screen is not kept on, so nothing fights it turning the screen off at the ear. With `whileVideo` the two never overlap anyway (video turns the sensor off for the rest of the call, §4.6); it matters for `always`. Both platforms also blank the screen near the ear whatever the window flag or idle timer says, so the gate is about intent rather than a race. The gate uses "the sensor is on", not "near": tracking near and far would need a sensor listener of our own, for no visible difference.
  - **Android:** `FLAG_KEEP_SCREEN_ON` on the activity's window, through the plugin (`keepScreenOn` on the call audio channel). A window flag, so no permission and no `PowerManager` wake lock; it is set again on a recreated activity (a rotation), and only a flag the plugin set is cleared (an app's own wakelock plugin may use the same flag). Without an activity (a background engine) it answers `false` and is applied when one attaches.
  - **iOS:** `UIApplication.isIdleTimerDisabled`, through the plugin; the value from before the first holder is restored when the last one lets go (engines are counted, process-wide).
  - **macOS:** an `IOPMAssertion` of type `PreventUserIdleDisplaySleep` (`IOPMAssertionCreateWithName` / `IOPMAssertionRelease`) through `dart:ffi` (IOKit and CoreFoundation; there is no macOS plugin). Allowed in the App Sandbox; `pmset -g assertions` lists it.
  - **Windows:** `SetThreadExecutionState(ES_CONTINUOUS | ES_DISPLAY_REQUIRED | ES_SYSTEM_REQUIRED)` through `dart:ffi`, cleared with `ES_CONTINUOUS`. The state belongs to the calling thread, so it is set and cleared from the root isolate, whose thread is Flutter's UI thread for the app's lifetime. `powercfg /requests` (elevated) lists it under `DISPLAY` and `SYSTEM`.
  - **Web:** the Screen Wake Lock API (`navigator.wakeLock.request('screen')`, `package:web`). The browser releases the lock whenever the tab is hidden and refuses one for a hidden tab, so it is requested again on `visibilitychange`; `isKeepingScreenAwake` follows. Browsers without the API (or where a permissions policy forbids it) report `canKeepScreenAwake == false`.
  - **Linux:** not supported (`canKeepScreenAwake == false`); an app can use its own inhibitor.
  - **Testing.** Unit tests: the policy (on, off, two rooms, the sensor winning, failures, the web's release and re-acquire) and the room (camera on, muted, unpublished; a remote video subscribed, unsubscribed, leased, muted by its publisher, unpublished; reconnecting keeps it, giving up and leaving release it; two rooms; each option; on a fake phone, the sensor winning on the earpiece with `always`). `example/integration_test/screen_awake_test.dart` on a device, with `screen_awake_test_driver.sh` on Android (the video is the camera, or on desktops a share of the first screen, since another app may hold the webcam).
  - **Verified** (October 2026) against the real SFU: on the Android emulator (API 34), with a 15 s screen timeout, the window had no `KEEP_SCREEN_ON` during the voice call, had it with the camera published and stayed `Awake` past the timeout, lost it when the camera was muted, had it again on unmute, and lost it on `leave()` (without the flag the emulator dozed within the timeout). On Windows 11, the root isolate's thread state went from `0x80000000` to `0x80000003` with video and back on mute and leave, and the system's execution state (`CallNtPowerInformation`) gained `ES_DISPLAY_REQUIRED` (`0x1` → `0x3`) and lost it again. On macOS 27 (October 3, `screen_awake_test`), `pmset -g assertions` listed the app's `PreventUserIdleDisplaySleep` assertion ("cloudflare_realtime: video call") from the start of the video, none during the voice-only part before it, released on mute, taken again on unmute and released on leave. On iOS the Swift builds with Swift Package Manager and CocoaPods; the Simulator's native tests toggle `isIdleTimerDisabled` (holders counted, the app's own value restored), and a room with `always` held and released it end to end; the `whileVideo` path needs a camera, so an iPhone is still to run. Safari refuses the wake lock (`NotAllowedError`); the call is unaffected. The Pixel 10 itself is still to check by hand.
- **Testing.** Unit tests cover the policy on fakes. `example/integration_test/background_test.dart` covers what can be automated on Android, with `background_test_driver.sh` pressing Home and coming back through adb: outbound audio, microphone energy and video frames rising for 20 s in the background, the service's presence and types (`dumpsys activity services`), focus loss and gain from another audio-focus client in the example app, and the proximity flag. Still manual: whether the screen really goes dark at the ear, a real phone call and Siri on both phones, and the iOS background run (a person presses Home; `CF_REALTIME_BACKGROUND_MANUAL=1`).

### 4.8 System calls: CallKit and Android Telecom (native)

**Decided (October 2026), M11.** A call can live in the phone's own call UI: on the lock screen, answered or ended from a headset, a car or a watch, held by the system when a phone call comes in, and muted from the system's button. iOS does this with CallKit (and wakes the app with PushKit), Android with Telecom through Jetpack Core-Telecom. As with §4.6 and §4.7, the package gives primitives, not app structure: the app decides when a call exists (its signaling, a push) and what answering means (joining a room); the package reports the call to the system, relays what the system's UI does, and hands call audio to the system while the call exists. The policy is Dart and unit-tested with a fake (`test/calls/system_calls_test.dart`); the native code is thin. **Status:** the Dart layer and the Android backend are done (verified on a Pixel 10, below); the iOS backend (CallKit and PushKit) is done and verified on an iPhone ("iOS status and findings", below), VoIP pushes aside. A phone without its backend reports `supported == false` and behaves like desktops.

- **The API** (`lib/src/calls/`).
  - `SystemCalls.instance` (one per app, like the system's call service): `configure(SystemCallsOptions)` completes with `supported`; `reportIncomingCall(id:, handle:, displayName:, video:, payload:, callerImage:)` and `startOutgoingCall(...)` complete with a `SystemCall`; `calls` / `callsChanges`, `call(id)`, and `events` (sealed `SystemCallEvent`: added, answered, ended with a `SystemCallEndReason`, held, muted, DTMF digits, audio activated and deactivated); `voipPush` (iOS).
  - `SystemCall`: `id` (a UUID, lowercase; the app's signaling carries it so both sides and a push agree; one is generated when omitted), `handle` (`CallHandle`: generic, phone number or email), `displayName`, `video`, `outgoing`, `payload`; `state` (`ringing`, `dialing`, `connecting`, `active`, `held`, `ended`) and `muted`, each with its stream; `endReason`, `whenEnded`. Methods: `answer()`, `end([reason])` (default `declined` while ringing, else `local`; the app passes `remoteEnded`, `unanswered`, `answeredElsewhere`... when its signaling says so), `setHeld(bool)`, `setMuted(bool)`, `reportConnecting()`, `reportConnected()`, `update(displayName:, video:)`.
  - **Requests, confirmed by events**, as for routes (§4.6): `answer`, `end`, `setHeld` and `setMuted` complete when the system accepted them; `state`, `muted` and `events` change when the system confirms, the same way as when the user acts in the system's UI. A refused request throws `SystemCallException` (`filtered`, `alreadyExists`, `notFound`, `unavailable`, `failed`); an `end` the system refuses ends the call locally (the system no longer has it).
  - **Room integration:** `Room.attachSystemCall(call, leaveWhenEnded: true, endWhenLeft: true)`, `Room.systemCall`, `detachSystemCall()`. The system's mute button and the room's microphone publication stay in step both ways; when they disagree at attach time, or a microphone is published later, muting wins (both end up muted, never unmuted by surprise). A loop guard queues the room's own mute requests so their confirmations don't flip the microphone back. When the call ends (the lock screen's End) the room leaves; when the room leaves, the call ends: `local`, or `failed` for an incoming call still ringing, since a room that leaves (on an error, for example) hasn't declined it (Who ended a ringing call, below; decided October 2026). An app that declines from its own UI ends the call first.
  - `VoipPush` (iOS): `supported`, `register()` (completes with the token if known; remembered across launches), `unregister()`, `token` / `tokenChanges`.
  - `CallInterruptionReason.held`: a held system call interrupts the call's audio through §4.7's machinery (silent both ways, nothing announced).
- **Everywhere else** (desktops, the web, and phones where the system or the native side refuses): `supported` is `false` and `LocalSystemCallBackend` keeps the calls in Dart, answering every request with its event. So the app's call flow (report, answer, hold, mute, end, attach) runs unchanged, without a system UI; nothing touches call audio.
- **Who owns what while a system call exists.**

  | | No system call | System call, iOS (CallKit) | System call, Android (Telecom) |
  |---|---|---|---|
  | Audio session / mode | `CallAudio` (§4.6) | **CallKit** activates the session (`didActivate`); WebRTC runs manual audio | **Telecom** sets the mode and holds the focus |
  | Route list and selection | `CallAudio` on the platform's routes | `CallAudio` on the platform's routes (`AVAudioSession` overrides work in a CallKit call) | `CallAudio` on **Telecom's endpoints**, `requestEndpointChange` (`setCommunicationDevice` is forbidden) |
  | Route policy (default, stickiness, new headset wins) | Dart | Dart, unchanged | Dart, unchanged; a user's choice carries over by kind |
  | Interruptions | `AVAudioSession` / audio focus (§4.7) | the call's hold, and audio deactivated without a hold (`unknown`; the deactivation a hold owes is the hold's, even after the unhold) | the call's hold (`onSetInactive`) |
  | `resumeAudio()` | re-activates / re-requests focus | asks to take the call off hold | asks to take the call off hold |
  | Proximity sensor, base configuration | package | package (unchanged) | package (unchanged) |
  | Foreground service | `CallService`: `microphone` (+`camera`) | — (`voip` and `audio` background modes) | `CallService` with `phoneCall` added, CallStyle notification |

  The mechanism: when the first system call appears, `SystemCalls` gives `CallAudio` a `SystemCallAudioBackend` (`CallAudio.useSystemCall`). With rooms joined, the platform's backend leaves call mode first (Android: mode, focus and communication device released before Telecom takes them), the new backend is followed, the route is chosen again on its routes, and an interruption from before is taken back. The last call ending hands the platform's backend back. The route API (`audioRoutes`, `selectAudioRoute`, `setSpeakerphone`) stays the same; Telecom endpoint UUIDs are the route IDs meanwhile (as §4.6 planned).
- **iOS audio: CallKit owns activation.** An app in a CallKit call must not activate its audio session; CallKit activates it after the start or answer action and calls `provider(_:didActivate:)`. WebRTC's `RTCAudioSession` supports exactly this: `useManualAudio = YES` (WebRTC won't start its audio unit by itself), `isAudioEnabled` (permission to start it), and `audioSessionDidActivate:` / `audioSessionDidDeactivate:` (tell it the system did). `flutter_webrtc` 1.6.2 exposes none of these to Dart, and its `+setAudioSessionManagementEnabled:` would also turn off `setAppleAudioConfiguration`, which §4.6 relies on. So the package's iOS code reaches `RTCAudioSession` itself through the Objective-C runtime (WebRTC is loaded in the process by `flutter_webrtc`; no build-time dependency, as M14 plans for its own use): manual audio on once system calls are configured, `isAudioEnabled` `true` whenever no CallKit call exists (normal calls are unchanged), `false` from a call's report until `didActivate`, `false` again on `didDeactivate`. The session's category is configured in the start and answer actions (before activation), as Apple asks; `flutter_webrtc`'s `ensureAudioSession` only sets the category, never activates. Its *deactivation* is another matter: `flutter_webrtc` deactivates the session itself when a peer connection closes, so the package guards it during CallKit calls (below).
- **iOS VoIP pushes (PushKit).** From iOS 13, every VoIP push must be reported to CallKit as a new incoming call before the push handler returns, or iOS terminates the app, and after repeated failures stops delivering VoIP pushes. A launch by a push may come before the Flutter engine runs Dart, so **the package reports pushed calls natively**: the push payload must carry the call (`id` UUID, `handle`, optional `handleType`, `displayName`, `video`; everything else becomes `SystemCall.payload`), and a payload without them is still reported (with a generated ID and a placeholder handle) and ended at once as `failed`. **Cancel pushes (decided October 2026):** a second push with the reserved key `ended` (a `SystemCallEndReason` name CallKit can be told: `remoteEnded`, `unanswered`, `failed`, `answeredElsewhere`, `declinedElsewhere`; any other value, `local` and `declined` included, is logged and taken as `remoteEnded`) and the call's `id` (no `handle` needed) stops the ring when the caller hangs up, another device answers or declines, or the ring times out. iOS wants a report for that push too, so the package can't simply skip it: a call it has is reported again (CallKit refuses the duplicate), then ended with `reportCall(endedAt:reason:)` and the `ended` event, as when the app ends it for that reason; a call it doesn't have (the cancel launched the app, or came twice) is reported as a placeholder with a new UUID and ended at once with the reason, and raises **no** event, so the app never sees a call that already ended. A call this device already took (answered, or outgoing) ends only for `remoteEnded` or `failed`: a reason about the ring doesn't end it, because a server may send the cancel to every device of the user, the one that answered too. **Pushes for calls that ended (decided October 2026, from a field report):** the package remembers the last 64 calls that ended, in memory, whoever ended them and with any reason (the app's `end`, its own ring timeout's `unanswered` included; the system's UI; CallKit; a reset; a cancel push), and the IDs of cancel pushes for calls it never had. A push for one of them doesn't ring and raises no event: a cancel arriving after the app ended the ring itself (in the report, the server's expiry job landed ~8 s after the app's local timeout, and the old code reported a placeholder that flashed and could add a Recents entry), or the call's own push after its cancel (APNs doesn't keep the order) or pushed again. iOS requires a report for every VoIP push, so the package reports the **call's own UUID** again. **What that achieves (measured on the Simulator, iOS 27.0):** CallKit refuses a UUID while it still remembers the call (`callUUIDAlreadyExists`), and then nothing shows; but it forgets soon: a UUID ended with `reportCall(endedAt:)` was refused at once and accepted 2 s and 6 s later, and one ended by an end action (the app's `local` or `declined`, the system's UI) was accepted at once. An accepted report is a call again, which the package ends at once with the original reason: no ring and no event, but it can show for an instant and, with `includesCallsInRecents`, leave a Recents entry, exactly as the placeholder did. So for the field report's timing (~8 s) the flash **can't be avoided by the package**: once CallKit has forgotten the call, the only way to satisfy PushKit is a visible report. What the change does fix: a ring push for a call that ended no longer rings (it used to be reported as a new call, with `reported`), duplicate or quick cancels are silent, and the call keeps its own UUID and handle instead of a stand-in's. That a refused report satisfies PushKit's rule is the assumption the package already makes for a push about a call it has (reported again, refused as a duplicate); still to confirm on a device with APNs. **For the app and its server:** don't send a cancel push to the device that ended the call (it already knows), and let the server's expiry, not a shorter local timer, end an unanswered ring (a cancel for a call that still rings is silent: it ends that call). A cancel for a call the package never had (the cancel launched the app) still needs the placeholder. Android has no VoIP pushes: the app's FCM handler ends the call with `SystemCalls.instance.call(id)?.end(reason)`, the same reasons. **Launch (decided October 2026):** the VoIP opt-in (`VoipPush.register()`) and the last `SystemCallsOptions` are persisted, and `SystemCalls.restore()` brings back the PushKit registry and the `CXProvider` before Dart runs. Apple asks for the registry (delegate and `desiredPushTypes`) to exist by the end of `application(_:didFinishLaunchingWithOptions:)`, so the host app calls the public `CloudflareRealtimePlugin.handleLaunch()` there (`@objc public static`, `import cloudflare_realtime` under SPM and CocoaPods; on the main thread, or queued to it). Plugin registration restores too, as before; `restore()` creates each object once, so the hook, a second call and any number of engines registering give one provider and one registry. Nothing in the restore needs an engine: UserDefaults, the provider, the registry and `RTCAudioSession` (looked up through the runtime; WebRTC is linked, so its class exists from launch whether or not `flutter_webrtc` has registered) are process-wide, and events wait in the process-wide buffer until an engine listens. The hook is **defensive**: in a UIScene app the implicit engine registers plugins from `didInitializeImplicitFlutterEngine`, which may follow `didFinishLaunching`; but in a field test (a consuming app on an iPhone with iOS 27.2, killed), iOS launched the app with its scene connected and CallKit had the pushed call 0.77 s after the push, so the gap didn't show there. Engine start may differ elsewhere (a prewarmed launch, an engine started later, add-to-app), and Apple's guidance is the launch. The app sends the pushes (APNs `voip` push type, its own certificate or token); out of scope.
- **Android: Core-Telecom.** `androidx.core:core-telecom` 1.0.1 (stable; 1.1.0 is in beta), Apache-2.0. `CallsManager.registerAppWithTelecom(CAPABILITY_BASELINE | CAPABILITY_SUPPORTS_VIDEO_CALLING)`, then `addCall(CallAttributesCompat(displayName, address, direction, callType, SUPPORTS_SET_INACTIVE), onAnswer, onDisconnect, onSetActive, onSetInactive) { CallControlScope }`: `answer(callType)`, `setActive()`, `setInactive()`, `disconnect(DisconnectCause)` (only `LOCAL`, `REMOTE`, `REJECTED`, `MISSED`), `requestEndpointChange(CallEndpointCompat)`, and the flows `currentCallEndpoint`, `availableEndpoints` and `isMuted`. Requires Android 8 (API 26; our `minSdk` 24 reports unsupported below); its manifest merges `MANAGE_OWN_CALLS`, `BLUETOOTH_CONNECT` and `MODIFY_AUDIO_SETTINGS` and its own `ConnectionService`. Each callback must finish within 5 s, and the app must post a `Notification.CallStyle` notification within 5 s of `addCall` (that keeps its foreground priority). `isMuted` is the global microphone mute, which Telecom's UI (a car, a watch) toggles; there is no "mute this call" request in 1.0, so the package sets `AudioManager.setMicrophoneMute` for `setMuted` (an app unmute must clear a system mute, or the microphone stays silent) and reports the flow. No DTMF.
- **Android notifications and the foreground service.** The package's `CallService` (§4.7) becomes the call's: while a Telecom call exists it runs with the type `phoneCall` (whose prerequisite is `MANAGE_OWN_CALLS`, not a while-in-use permission), plus `microphone` and `camera` as rooms publish, and its notification is the call's `CallStyle` (`forIncomingCall` with a full-screen intent to the package's ring activity and Answer/Decline actions while ringing, `forOngoingCall` with Hang up after). Android 12+ forbids notification trampolines, so Answer is an activity `PendingIntent` to that ring activity (visible, so the app is in the foreground, which also satisfies Android 14's while-in-use rule for the microphone service), and Decline a broadcast to the package. The ring activity, not the app, is what shows over the lock screen: next item. Starting the service from the background is allowed for a high-priority FCM message and for notification actions, so `reportIncomingCall` must be called from the foreground or a high-priority FCM handler (documented). Texts and the icon are resources the app overrides, as for §4.7's notification. `RoomOptions.foregroundService: false` drops only the publishing types.
- **The ring activity and the lock screen (decided October 2026; a security fix, found in an integration review).** Before, the ring's full-screen intent and its Answer opened the **app's launch activity** with the package's actions, and the plugin set `setShowWhenLocked` / `setTurnScreenOn` on that activity until the last call ended. For a typical app the launch activity is the whole app, so a ring on a locked phone showed the full, usable app above the keyguard, without authentication (reproduced on a Pixel 10 with Android 16 and on a PIN-locked emulator). And because a launch activity is necessarily exported while the plugin answered on any intent carrying the Answer action and a known call ID, another app that learned or guessed an ID could answer the call and open the microphone. Now:
  - **The package's own activity.** `IncomingCallActivity` (plain Android views, no Flutter engine) is the target of the full-screen intent, of the content intent while ringing, and of Answer. It is declared `exported="false"`, `excludeFromRecents`, `singleInstance` with its own affinity (`<applicationId>.cloudflare_realtime.incoming_call`): alone in its task, so closing it never reveals another of the app's activities, and one instance however many intents arrive. It shows the caller (the display name, else the handle) with Answer and Decline, accessible text buttons, in the system's light or dark theme (Android 10+; the style `CloudflareRealtime.IncomingCall` can be overridden). `setShowWhenLocked` is set in code while its call exists and `setTurnScreenOn` only while it rings, and both are cleared when it closes (`finish()`, not `finishAndRemoveTask()`: removing one of the app's tasks stops `CallService`, which is `stopWithTask`, and the call's notification with it; the first test run caught that). Neither is in the manifest, so SystemUI asks for the unlock before it starts the activity from a tap on a lock-screen notification (when the full-screen intent isn't allowed); the full-screen ring itself answers without one, as a phone call does.
  - **Answer** answers through the registry: native, no Dart needed, so an app that FCM woke with no UI engine answers too (the `answered` event goes to whichever engine listens, buffered until one does, and `activeCalls` lists the call active at `configure`). Then `KeyguardManager.requestDismissKeyguard`. Only on `onDismissSucceeded`, or when `isKeyguardLocked` is already false, does it start the app's **plain launch intent** (no action, no extras, no lock-screen flags) and close. If the unlock is cancelled or fails, the answered call stays on this screen (the caller, Hang up, Open app) over the lock screen, and the app stays behind the keyguard. The call's foreground service keeps the audio running while locked, and the visible activity keeps the app in the foreground for the microphone service type.
  - **Decline** ends the call `declined` and never unlocks or opens the app. A call that ends any other way closes the screen. A call answered elsewhere while it shows (a headset, a watch, the app in code) switches it to the answered state; it opens the app at once only on an unlocked device, with no unlock prompt nobody asked for.
  - **The app's activity** gets no lock-screen flags from the package any more, and the plugin no longer reads its intents: the old Answer and Show actions sent to it do nothing. The ongoing call's content intent is the plain launch intent, so on the lock screen the system asks for the unlock first. Answer, Decline and Hang up go only to non-exported components (the ring activity, `SystemCallActionReceiver`) through explicit, immutable `PendingIntent`s.
  - **Verified on the Pixel 10 (Android 16, October 4, 2026).** Before the fix, with a call ringing, `adb shell am start -n <app>/.MainActivity -a dev.kammcs.cloudflare_realtime.action.ANSWER_CALL --es dev.kammcs.cloudflare_realtime.extra.CALL_ID <id>` answered it (`active`). After, the call keeps ringing, and `am start` on the ring activity is refused (`SecurityException: … not exported`); `system_call_test.dart` checks both (7 tests with the driver, all passing; the notification's Answer goes through the ring activity, which hands off to the unlocked app). On the phone locked with its PIN (`dumpsys window` and `dumpsys activity activities`): while ringing, `KeyguardShowing=true Occluded=true` with only the ring activity resumed and visible, the app's activity `STOPPED`, not visible; after Answer, the unlock prompt over the ring activity, the app still not visible; with the unlock cancelled, the answered call on the ring screen, the app still not visible; Hang up there ended it `local`, and Decline on a second ring ended it `declined`, both leaving the keyguard up and unoccluded. The app's lifecycle never reached `resumed` while locked. **Verified by hand** the same day by the owner: entering the PIN after Answer opens the app in the call, and the lock-screen behaviour above held.
- **The caller's picture (decided October 2026, asked for by a consuming app).** The ring screen shows the caller's picture, else a monogram; Android only.
  - **The API:** `reportIncomingCall(callerImage: Uri?)`, a **local** `file:` or `content:` URI the app can read. It goes to the native side as the call map's optional `callerImage` (a string, incoming calls only, never read back). The package never fetches from the network: an app downloads the picture first (into its cache, say) and passes `Uri.file(path)`; an `http(s)` or any other scheme is ignored with a log line. The ring activity runs in the app's process, so a file in the app's own storage, or its own `FileProvider`'s `content:` URI, is readable without grants. The app should build the URI itself rather than pass one from a push unchecked.
  - **Decoding:** `SystemCallRegistry` decodes it before `addCall`, on `Dispatchers.IO`, so the ring screen and the notification have it from the first frame: `ImageDecoder` (Android 9+, which applies the EXIF orientation; software allocation, since the notification parcels it) with a target size whose shorter side is the ring screen's 120 dp, or `BitmapFactory` with a power-of-two `inSampleSize` below; then the middle square, scaled to 120 dp. The call waits at most 1 s for it (a local file takes milliseconds; a slow provider doesn't hold the ring back). Any failure (a missing file, an unknown format, the timeout, out of memory) is logged and leaves the monogram.
  - **The monogram:** up to two initials, the first character of the display name's first and last words (the handle when there's no display name), upper-cased. Characters are graphemes (`BreakIterator`), not UTF-16 units, so an emoji with its skin tone or joiners, a flag, a letter with combining marks or a character outside the BMP stays whole; CJK names, usually without spaces, give their first character. A word's leading punctuation and symbols are skipped, emoji excepted; a name with no letters or emoji (a phone number) gets a person's silhouette instead. The colour comes from the name (FNV-1a over its code points, so the same name has the same colour on every device), picked from the resource array `cloudflare_realtime_monogram_colors`: ten colours with at least 5:1 contrast with the white initials, which an app can override. Pure Kotlin (`CallerMonogram`), covered by the plugin's JVM unit tests (`android/src/test`).
  - **On screen:** a 120 dp circle above the name (the picture clipped to an oval outline, or the monogram's own circle), with a content description (`cloudflare_realtime_call_caller_photo` or `…_initials`, overridable). **In the notification:** the same picture, or the monogram, as the `Person`'s icon in `CallStyle` (Android 12+) and as the large icon below; also for outgoing calls, which have no picture.
  - **iOS:** accepted and ignored. CallKit has no API for an app's caller image: the system call UI shows a picture only when the handle matches a Contacts entry with one, so a VoIP app's caller shows the system's placeholder.
  - **Verified on the Pixel 10 (Android 16, October 4, 2026):** `system_call_test.dart` (8 tests with the driver, all passing) rings four calls and opens the ring screen through the notification's tap: without a picture, the monogram on the ring screen and as the notification's `CallStyle` person icon; with a local PNG (in the app's `code_cache`, `Directory.systemTemp`), the picture in both; with an `https:` URI (logged, ignored) and a missing file (logged `FileNotFoundException`), the monogram. The driver saves a screenshot of each ring screen (`SCREENSHOT_DIR`).
- **Who ended a ringing call (decided October 2026, from an integration review).** An app tells its server "declined" on `declined`, so `declined` must mean a person declined. A ringing call can also end without anyone choosing to, and each platform says so to a different degree:
  - **Android tells them apart.** The package's own Decline (the call notification, which is also the lock screen's and the banner's ring) and Dart's `end` set their reason before they disconnect, so they are tagged. Everything else arrives through Core-Telecom's `onDisconnect` with Telecom's cause (AOSP `Call.java`, `CallsManager.java`; Core-Telecom's `CallSession` and `CallSessionLegacy`). Telecom's **reject** is a person through Telecom: a Bluetooth headset, a car, a watch (an `InCallService`'s `reject`), a headset button's long press, the end-call key. It arrives as `REJECTED` and is `declined`. Telecom's **disconnect** of a ringing call is Telecom making room (`disconnectSelfManagedCalls` for an emergency call or a phone call the user confirms) or a companion's `disconnect`. On Android 14+ (Core-Telecom on the platform's transactional API) it carries the call's own disconnect cause, `UNKNOWN` unless Telecom set one; below 14, Core-Telecom's `ConnectionService` turns `Connection.onDisconnect` into `LOCAL`. Both are `failed` while ringing. Before this, `LOCAL` while ringing was `declined`, so Android 8–13 said `declined` where 14+ said `failed`. **One exception:** an emergency call placed while the call rings is a reject in Telecom (`makeRoomForOutgoingEmergencyCall`; Telecom logs it as missed, but a transactional call is sent `REJECTED`), so it reads as `declined`. It is rare, and the user's own action. Verified on the Pixel 10 with a companion `InCallService` in the example (debug builds; the driver allows its `MANAGE_ONGOING_CALLS` app op): its `reject` is `declined`; its `disconnect` reaches the package as `UNKNOWN` and is `failed`.
  - **The package's own ends.** `Room.attachSystemCall`'s `endWhenLeft` ends a ringing incoming call `failed` when the room leaves, on both phones: nobody chose that end, and `SystemCall.end()`'s default for a ringing call (`declined`) would tell the server about a decline the user never made.
  - **iOS can't, for the end action.** The user's Decline (the lock screen, the banner, full screen, a headset, a watch) arrives as `provider(_:perform: CXEndCallAction)`, which carries only the call's UUID. CallKit ending the call itself arrives the same way: on the iOS 27 Simulator, `callservicesd` logs "Disconnecting call because there wont be a UI to host the call" (an internal disconnect reason, 55) about 0.9 s after the report, then asks the provider to perform an ordinary `CXEndCallAction` (seen with `log stream`; `testCallKitEndingARingingCallItselfIsDeclinedOnSimulator` records it). Neither the action nor `CXCallObserver`'s `CXCall` says who asked. A timing rule (an end soon after the report) would misfile a quick Decline and relies on undocumented behaviour, so there is none: an end the app didn't request on a ringing incoming call stays `declined`, and the docs say it may be CallKit's (for example when another call takes over). What iOS does report: a report CallKit refuses (`CXErrorCodeIncomingCallError`: `filteredByDoNotDisturb`, `filteredByBlockList` and the newer filters → `filtered`; `callUUIDAlreadyExists` → `alreadyExists`; `unentitled` → `unavailable`; `unknown` → `failed`), which throws for a call Dart reports and ends a pushed call as `failed`; and `providerDidReset` (`failed`, each call). So Focus and Do Not Disturb never produce `declined`: they refuse the report.
  - **The API: no new value; `failed` is widened.** `failed` already meant that nobody chose the end: a reset call service, a refused pushed call, Telecom's other causes, and on Android 14+ these very disconnects. A new `systemEnded` value would have split those cases by platform and broken exhaustive `switch`es without new information. A flag on `declined` would have been `false` for every case iOS can't tell. So the same situation gives the same reason on both phones wherever the platform says which it was: `failed` when the system ends a ringing call, `declined` when a person declines it, and on iOS also when CallKit ends it with its own end action. An app that must never report a system end as a decline can treat iOS's `declined` as "not answered here" unless its own UI declined the call (`doc/ios.md`).
- **Platform differences.** iOS has VoIP pushes, DTMF, Recents, a ringtone and an icon; Android has endpoints, the full-screen notification and the caller's picture on its ring screen, and fixes a call's name and type when it is added (`update` changes iOS only). iOS's `CXProviderConfiguration` is global; Android's phone account is per app. CallKit must not be used by apps on the China mainland App Store (Apple's rule, from MIIT); the app then simply doesn't call `configure`. Desktops and the web: `supported == false`, calls in Dart only (above).
- **What the host app supplies.** iOS: `UIBackgroundModes` `voip` (with `audio`, §4.7), the Push Notifications capability and an APNs VoIP certificate or key for its server, optionally a template icon in the asset catalog and a ringtone file; a server that sends `voip` pushes with the payload above, and a cancel push (`ended`) when a ring stops. #### The native contract

The Dart side (`lib/src/calls/system_call_backend.dart`, the comment block at its top) talks to the native code over two channels:

- `MethodChannel('dev.kammcs.cloudflare_realtime/system_calls')`
- `EventChannel('dev.kammcs.cloudflare_realtime/system_calls_events')`

**A call map**, both ways (Dart sends the first six keys, plus `callerImage: String`, a local URI, for an incoming call that has a picture; Android only, never sent back): `{id: String (UUID, lowercase), handle: String, handleType: "generic"|"phoneNumber"|"emailAddress", displayName: String?, video: bool, outgoing: bool, state: "ringing"|"dialing"|"connecting"|"active"|"held"|"ended", muted: bool, payload: Map<String, Object?>?}`. **A route map** is call audio's: `{id, kind: "speaker"|"earpiece"|"wiredHeadset"|"bluetooth"|"usb"|"other", name}`.

**Methods.** Errors are `PlatformException`s with the code `filtered`, `alreadyExists`, `notFound`, `unavailable` or `failed`.

| Method | Arguments | Result | iOS | Android |
|---|---|---|---|---|

**Rules.** `answer`, `end`, `setHeld` and `setMuted` are requests: the outcome always comes back as the event, whoever started it (the app or the system's UI), once per real change; every `CXAction` is fulfilled or failed, and every Core-Telecom callback returns within its 5 s. Events raised while no Dart listener exists are buffered in order and delivered on listen; `activeCalls` is the state for an engine that starts later. The call registry is process-wide: every attached engine's sink gets the events (on Android an FCM background engine may report the call that the UI engine answers).

**Native work, iOS** (`ios/cloudflare_realtime/Sources/`, linking CallKit and PushKit): a `SystemCalls.swift` with the provider, its delegate and the controller; the call registry (UUID → state); the `RTCAudioSession` hand-off above, through the Objective-C runtime; the PushKit registry and its native reporting of pushes, with the persisted opt-in and configuration; the channels in `CloudflareRealtimePlugin.register`; the podspec and `Package.swift` unchanged (system frameworks); `RunnerTests` for the maps and the payload parsing.

**Native work, Android** (`android/`, **done**): the `androidx.core:core-telecom:1.0.1` and `kotlinx-coroutines-android` dependencies; `SystemCalls.kt` with `SystemCallRegistry` (process-wide: the calls, the event sinks and the buffer), one `addCall` coroutine per call collecting its flows, and the call's notification; `CallService` combining the publishing types (from `CallBackground`) and `phoneCall` (while a call is in Telecom) in one `sync`, with the call's `CallStyle` notification; `IncomingCallActivity` for the full-screen ring and Answer (above) and `SystemCallActionReceiver` for Decline and Hang up, neither exported; the manifest entries. The call audio plugin needed no change: Dart deactivates it before Telecom takes the audio. No native unit tests for the maps: `system_call_test.dart` exercises every conversion on a device (a Robolectric setup for the plugin is still open). The plugin's JVM unit tests (`android/src/test`, JUnit, no Android classes; from `example/android`, `./gradlew :cloudflare_realtime:testDebugUnitTest`) cover the pure Kotlin: the monogram's initials and colour.

**What the Android backend does, and what building it showed** (Pixel 10, Android 16, October 2026):

- **`addCall` suspends for the whole call, and its flows are channels that never close.** The block runs once Telecom has the call (that is when `reportIncomingCall` / `startOutgoingCall` complete); the collectors launched in it are cancelled when the call ends, or `addCall` never returns. A call ended while Telecom is still adding it cancels the add and fails the pending report.
- **Events follow state, deduplicated natively:** `answered` (then `audioActivated`) from `answer` or `onAnswer`; `held` (then `audioDeactivated` / `audioActivated`) from `setInactive` / `setActive` or `onSetInactive` / `onSetActive`; `ended` once, from `disconnect` (the app's reason) or `onDisconnect` (`LOCAL` → `local`, or `failed` while ringing; `REJECTED` → `declined`; `MISSED`, and `CANCELED` for an incoming call → `unanswered`; `REMOTE`, `BUSY` → `remoteEnded`; `ANSWERED_ELSEWHERE` → `answeredElsewhere`; else `failed`). `reportConnected` is `setActive` and emits `audioActivated`. Core-Telecom reports the endpoint list and the current endpoint separately and repeatedly; `endpointsChanged` is sent once per change and coalesced to one per main-loop turn.
- **Mute.** `setMuted` sets `AudioManager.setMicrophoneMute` and reads it back. Telecom notices a change of the global mute made by anyone (`MUTE_EXTERNALLY_CHANGED`) and reports it through `isMuted`, so a car, a watch or another app muting the microphone reaches the call and, through `attachSystemCall`, the room. A value that disagrees with the global mute when it arrives is an older one crossing a newer request, and is dropped (a time window dropped real changes). The mute is cleared when the last call ends.
- **Ringing.** Telecom doesn't ring a self-managed call (it only sets `MODE_RINGTONE`), so the incoming notification rings: its channel ("Incoming calls", high importance) plays the default ringtone (`USAGE_NOTIFICATION_RINGTONE`) with `FLAG_INSISTENT`, and replacing it with the ongoing notification or removing it stops it. It follows the ringer mode, Do Not Disturb and the user's channel settings (with the ringer muted it vibrates).
- **The service.** Its types were `0x4` (phoneCall) while ringing or dialing and `0x84` with the microphone published; Telecom adds its own `PHONE_CALL` foreground record for the app. When the last call ends and rooms still publish, the service goes back to its publishing types and "Call in progress" notification; with nothing published it stops. If Android refuses the service (a start from the background outside the allowed cases), the call's notification is posted without it, as Telecom requires. A report a second after Home started the service (Android's grace period); the FCM path itself is the app's to test.
- **Audio.** Telecom set `MODE_RINGTONE` while ringing, `MODE_IN_COMMUNICATION` while active, and changed the mode on hold; after the last call, with a room still joined, `CallAudio`'s platform backend took call mode back, as designed. The routes were Telecom's endpoints (the speaker and the earpiece, UUIDs), selected with `requestEndpointChange`.
- **The activity.** Answer and the full-screen intent open the package's `IncomingCallActivity` (The ring activity and the lock screen, above); it resets the intent's action after answering, so a recreated activity doesn't answer again. Until October 2026 they opened the app's launch activity and set the lock-screen flags on it: the security fix above.

- **WebRTC through the Objective-C runtime, not linked.** `flutter_webrtc`'s `Package.swift` exports a `WebRTC` product, but another plugin's package can't reach it by a stable path (Flutter's generated package links plugins from the pub cache; only `../FlutterFramework` is provided), and the podspec would need `s.dependency 'flutter_webrtc'` and the same WebRTC-SDK pin. So `RTCAudioSession` (no class prefix in WebRTC-SDK 150) is found with `NSClassFromString`, every selector the hand-off uses is checked with `respondsToSelector:`, and they are sent through an `@objc` protocol. Without it the hand-off is off and the category goes to `AVAudioSession` directly. Built and unit-tested under both SPM and CocoaPods (Simulator and signed device builds).
- **The audio device module.** On devices `flutter_webrtc` 1.6.2 uses WebRTC-SDK's `AVAudioEngine` module (the Simulator keeps the platform default). Its source (WebRTC-SDK `m150_release`, `audio_engine_device.mm`) ignores `canPlayOrRecord` (`OnCanPlayOrRecordChange` only logs), so `useManualAudio` / `isAudioEnabled` gate only the platform module; what starts and stops the engine is `RTCAudioSession`'s interruptions: it stops at a begin and restarts only at an end (`DidEndInterruption`). `audioSessionDidActivate:` always sends an end.
- **A hold stopped the call's audio for good (fixed October 2026).** On an iPhone 16 Pro Max (iOS 27), CallKit deactivates the app's session ~0.5 s after a hold (`didDeactivate`) and activates it after the unhold (`didActivate`); iOS stops the app's audio I/O then ("iounit stopped unexpectedly > pausing the engine") but posts no `AVAudioSession` interruption. So WebRTC never saw a begin, its module still believed the engine ran, and `didActivate`'s end changed nothing: no audio either way after any hold (the engine read `isEngineRunning = 0` for good, with `playing` / `recording` on). Now `didDeactivate` also begins an interruption in `RTCAudioSession` (`isInterrupted`, then `notifyDidBeginInterruption`, private selectors checked at runtime; nothing when a real interruption already began it), as its own notification handler does, and `didActivate` ends it: the engine restarts at once. After the last call, the begun interruption is ended by the next activation (`RTCAudioSession`'s `setActive:YES` or the next call's `didActivate`). With a quick hold (the integration test's first one, ~0.5 s) the deactivation arrives after the unhold; Dart's `SystemCalls` counts it as the hold's (a hold owes one deactivation), so the room isn't interrupted a second time as `unknown`, and the plugin no longer forwards `AVAudioSession` interruptions while a CallKit call exists (none were observed during holds, but one arriving late must not interrupt the room either). Verified on the device: a quick hold and a 4 s hold, each with audio both ways after it, in the outgoing and the answered call.
- **A publish hung after answering (October 2026, guarded; cause not yet found).** Reported from a consuming app on an iPhone (iOS 27.2): 1 of 14 CallKit answers hung in the microphone publish after `didActivate` and before `tracks/new`, until the app's own 60 s join timeout. What the publish awaits before `tracks/new`, and what could hang:
  - **Not a Dart wait on the activation:** the package never waits for `audioActivated` (the event only feeds `CallAudio`), and nothing in `Room.attachSystemCall` blocks a publish.
  - **The capture** (`getUserMedia`, and the device enumeration before it): on iOS `getUserAudio` runs on the main thread (after `AVCaptureDevice.requestAccess`), creates the audio source and track through the factory (a synchronous call to WebRTC's signaling thread), then `ensureAudioSession` takes `RTCAudioSession`'s configuration lock. It doesn't touch the audio device module, and the module (WebRTC-SDK `m150_release`, `audio_engine_device.mm`) never takes that lock, so manual audio and `isAudioEnabled` don't gate it; a hang here means the main or signaling thread is blocked.
  - **The negotiation** (`addTransceiver`, `setCodecPreferences`, `createOffer`, `setLocalDescription`, `mid`), behind whatever is ahead of it on the session's queue (the join's early connect, auto-subscribed pulls). `flutter_webrtc` calls them on the main thread through WebRTC's proxies, which block until the signaling thread runs them, and the signaling thread waits on the worker thread for anything that touches a media channel. The `AVAudioEngine` module runs its engine changes on that worker thread, synchronously (`ModifyEngineState`: `setVoiceProcessingEnabled`, `startAndReturnError` with up to `kStartEngineMaxRetries` retries), and at an answer it has reasons to: `audioSessionDidActivate:` ends the interruption (`OnInterruptionEnd` posts an engine restart to that thread), and a pulled audio track starts playout. An engine start that blocks while CallKit hands over the session would hold up every peer-connection call queued behind it, and the main thread with it. Its interruption callbacks only post tasks, so no deadlock was found by reading; it is the leading suspect, unconfirmed.

  Without a device trace the cause stays open, so the package bounds every step instead (§4.2, Bounded negotiation steps; §4.5, Bounded capture; §4.3, Bounded publish): such a publish now throws or re-sessions within at most 30 s (capture) or 60 s (a negotiation step), and the log line names the step that stuck. **A device repro needs:** the answer loop run until it hangs (about 1 in 14), with the app started from Xcode (not `flutter run`, which is killed at lock) and the console captured (`cloudflare_realtime:` lines name the stuck step; WebRTC-SDK's own lines, such as `Starting AVAudioEngine...` without its result, show the module's state); then, while it hangs, a pause in the debugger and every thread's backtrace (main, `signaling_thread`, `worker_thread`), to see what blocks.
- **`flutter_webrtc` deactivates the session under CallKit (verified in its source, guarded).** `-deactiveRtcAudioSession` runs on `peerConnectionClose`, `peerConnectionDispose` and `mediaStreamDispose` when no local audio track and no open peer connection is left, and `+[AudioUtils deactiveRtcAudioSession]` then calls `setActive:NO`. CallKit's activation counts once in `RTCAudioSession` (`audioSessionDidActivate:`), and close plus dispose call it twice, so the session really is deactivated under CallKit: a receive-only room's re-session (§8.1), or a room that closes before its call ends. The guard replaces `+[AudioUtils deactiveRtcAudioSession]` (`method_setImplementation`, installed with manual audio) with a check that skips it while a CallKit call exists and calls the original otherwise; CallKit deactivates the session itself when the call ends. Unit-tested on the Simulator (the activation count stays).
- **Requests and events.** Every event comes from the provider's `perform` (or the package's own `reportCall(endedAt:)`), only for a real change: `setMuted` / `setHeld` to the current value is accepted with no action and no event; a ringing or dialing call can't be held (`false`). `end` with `local` or `declined` is a `CXEndCallAction` (the requested reason is kept for its `perform`; from the system's UI it is `declined` while ringing incoming, else `local`; CallKit ending a ringing call itself looks the same, so it is `declined` too: Who ended a ringing call, above); the other reasons are told with `reportCall(endedAt:reason:)` and the package sends `ended`. An end CallKit refuses for an unknown UUID returns `false` (Dart ends the call locally). Unknown IDs are `notFound`; reporting before `configure` is `unavailable`.
- **Pushes.** Reported synchronously inside the PushKit delegate; the delegate's completion runs once CallKit answered. `aps` is not part of `payload`; `video` accepts `true`, `1` or `"true"`. A push before any configuration creates the provider with the defaults. A push for a UUID the package already has (the app's signaling reported it first) is reported again, as iOS requires, and CallKit refuses the duplicate; no event. A pushed call CallKit refuses (Do Not Disturb, the block list) is `reported`, then `ended` as `failed`. A malformed push rings for an instant, is ended as `failed`, and raises no event. A cancel push (`ended`, above) ends a call the package has with its reason and the `ended` event (buffered, after the call's `reported`, while Dart doesn't listen). A push (ring or cancel) for a call that ended here is reported again under its own UUID, with no event: refused by CallKit while it remembers the call, else ended at once (Pushes for calls that ended, above); for an ID the package never had, a placeholder (a new UUID, the push's handle and name if any) is reported and ended at once with the reason, without an event. Placeholders may show for an instant, and with `includesCallsInRecents` may leave a Recents entry. Not yet checked on a device (needs APNs).
- **With §4.6–§4.7 (M10).** The call audio channel's `resume` never activates the session while a CallKit call exists (it answers whether CallKit activated it); Dart already takes the call off hold instead. `CallBackground` (camera interruptions) is unchanged. ### 4.9 Logging

The package logs what it recovers from or works around (a failed prewarm, a refused screen wake lock, a stuck negotiation step it gave up on, a failed device list, call audio routing), a few events that explain a call later (a screen broadcast that didn't start), and the output of debug aids the app turns on (§4.2, platform call timing). Device logs aren't private: Android's logcat is readable over adb, and crash reporters often collect the console. So **the package's log lines carry no error text by default**, because an error's text can echo a broker's response body (the app's own data), a URL or a platform message.

- **Dart: one seam, `CloudflareRealtime.logger`** (a `CloudflareRealtimeLogger`, `void Function(CloudflareRealtimeLogRecord)`). Every line is a record: a `level` (`debug`, `info`, `warning`, `error`), a `message` written by the package, the error's `errorType` (its class name) and `errorCode` (a `PlatformException.code`, a broker error's HTTP status and `errorCode`, the SFU's `errorCode`, a `SystemCallException` code; capped at 64 characters), and, in separate fields, the `error` itself and its `stackTrace`. The default, `CloudflareRealtime.defaultLogger`, prints `record.toString()` with `debugPrint`, for example `cloudflare_realtime: prewarm failed (PlatformException, code: error)`, and never the error or the stack. `CloudflareRealtime.debugLogFullErrors = true` makes it print both, while debugging. An app routes the records to its own logging, or drops them, by setting `logger`; it gets the full error and decides. A logger that throws is skipped for that record, which goes to the default.
- **Exceptions are log-safe too**, for apps that print them: `toString()` has the class, the operation, an HTTP status and a code, never a response body. `BrokerException` leaves out `errorDescription`, `SfuTrackException`, `SfuRequestException` and `SfuDataChannelException` leave out the SFU's `errorDescription`, `MediaException` and `AudioOutputException` give the type of their `cause` rather than its text, and `SystemCallException` leaves out the platform's `message`. The fields keep the data. `BrokerNetworkException.cause` was already left out (its message can contain the URL).
- **Native code** logs to logcat (tag `cloudflare_realtime`) and the unified log (`NSLog`, prefixed `cloudflare_realtime:`) itself; `CloudflareRealtime.logger` doesn't reach it. It logs events (a system call answered, ended or refused, an audio interruption, a screen broadcast starting), call IDs, and for errors the exception's class name on Android and the `NSError` domain and code on iOS, never their messages. **Never logged, anywhere:** VoIP push payloads (not even an unknown `ended` value), PushKit tokens, caller handles and display names, session tokens, SDP, request and response bodies, and header values.
- **Not routed through the logger:** a failure inside `ParticipantVideoView` or a media source's reconcile is a bug, reported with `FlutterError.reportError`, so it reaches the app's own `FlutterError.onError` (its crash reporter) with the full error, as Flutter's own errors do.

## 5. Broker contract

The broker is a small HTTPS endpoint **the app operates**. It holds the App ID and App Secret and forwards requests to `https://rtc.live.cloudflare.com/v1/apps/{appId}`.

**Paths.** They mirror the SFU API with `/apps/{appId}` replaced by the broker's base path. This matches partytracks' `routePartyTracksRequest`, so an existing partytracks Worker proxy works with only an auth change.

| Client calls | Broker forwards to |
|---|---|
| `POST {base}/sessions/new` | `POST /apps/{appId}/sessions/new` |
| `POST {base}/sessions/{id}/tracks/new` | same path under `/apps/{appId}` |
| `PUT {base}/sessions/{id}/tracks/update` | 〃 |
| `PUT {base}/sessions/{id}/renegotiate` | 〃 |
| `PUT {base}/sessions/{id}/tracks/close` | 〃 |
| `GET {base}/sessions/{id}` | 〃 |
| `POST {base}/sessions/{id}/datachannels/establish` | 〃 |
| `POST {base}/sessions/{id}/datachannels/new` | 〃 |
| `PUT {base}/sessions/{id}/datachannels/update` | 〃 |
| `PUT {base}/sessions/{id}/datachannels/close` | 〃 |
| `POST {base}/generate-ice-servers` | TURN credentials: `POST /turn/keys/{turnKeyId}/credentials/generate-ice-servers`. Without TURN, it returns Cloudflare STUN only. |

**Wire details.** Both the Dart `BrokerClient` and the reference brokers follow these exactly.

- **Headers on every request**, including `generate-ice-servers` (so TURN credentials only go to room members):
  - the app's own auth headers, from the `headers` provider;
  - `X-Realtime-Room: <roomId>`, the room the caller is acting in.
- **Session token (optional).**
  - On `POST sessions/new`, the broker MAY return a response header `X-Realtime-Session-Token`.
  - If it does, the client sends it back as the request header `X-Realtime-Session-Token` on every later call for that session. The client keeps one token per session ID, because reconnection creates new sessions.
  - A broker may instead bind sessions server-side and never send a token. The client works either way.
  - The client never lets the app's headers set `X-Realtime-Room` or `X-Realtime-Session-Token`.
  - Browsers can only read the header if the broker lists it in `Access-Control-Expose-Headers`.
- **`sessions/new` body:** none, unless the client has an initial offer. `correlationId` travels as a query parameter, which the broker passes through.
- **Broker errors:**
  - `401`: the caller isn't authenticated. The body is unspecified.
  - `403` with `{"errorCode": "forbidden", "errorDescription": "..."}`: the caller isn't in the room, doesn't own the session, names a session from another room, or (with the optional DataChannel rules below) isn't allowed the DataChannels it names.
  - The reference brokers also use `400` (missing room header, malformed body), `404`/`405` (unknown path or method), `413` (body over 1 MiB) and `502` (Cloudflare unreachable).
  - Otherwise the SFU's status and body pass through unchanged, including `410` with `errorCode: session_error` for an expired session.
- **`generate-ice-servers`** responds `200` with `{"iceServers": [{"urls": ["..."], "username"?: "...", "credential"?: "..."}]}`. Without TURN configured, it returns Cloudflare STUN only: `{"iceServers": [{"urls": ["stun:stun.cloudflare.com:3478"]}]}`. The reference brokers drop TURN URLs on port 53, which browsers block, and also accept `GET`, as partytracks clients use it.

**The broker must enforce these security requirements.** Document them in the README, and follow them in any reference broker:

1. **Authenticate the caller** with the app's own credential.
   - partytracks uses cookies, but native Flutter clients don't keep cookies. So the package sends whatever headers the app's `headers` provider returns.
   - The broker then replaces `Authorization` with the App Secret before forwarding.
2. **Authorize the room.** The client names the room it's joining in the `X-Realtime-Room` header. The broker checks that the caller is a member of it.
3. **Bind sessions to their creator.** After `sessions/new`, only the same caller, in the same room, may use that session (every `sessions/{id}` route, including `GET`).
   - partytracks does this with a JWT cookie. Here, the broker either keeps a server-side map, or returns a signed session token in `X-Realtime-Session-Token` that the client echoes on later calls.
   - The package supports echoing such a token (see the wire details above).
4. **Restrict pulls to the same room.** A `tracks/new` pull names another participant's `sessionId`. The broker must check that the session belongs to the same room. **Otherwise anyone with a valid login could subscribe to any room's media by guessing or learning a session ID.**
   - The same applies to every body that names a `sessionId`: `tracks/update` (reusing a transceiver for another publisher's track), `datachannels/new` and `datachannels/update` (subscriptions and `canReply`). The reference brokers check each `sessionId` found anywhere in any request body.
   - So the broker needs a **session store** (session → room, owner) even when it uses signed tokens: only the store knows another participant's room. The store must be readable from every broker instance within seconds of a write, because peers pull new sessions quickly.
5. Strip client-supplied headers that shouldn't reach Cloudflare: forward only `Authorization: Bearer <App Secret>` and `Content-Type`. Never log the App Secret, SDP bodies or tokens.

**Key spellings.** The broker reasons about some body keys: `sessionId`, `tracks`, `dataChannels`, `dataChannel`, `location`, `dataChannelName`, `canReply` and `id`. A JSON decoder that matches keys case-insensitively, as Go's `encoding/json` does with Unicode simple folding (`ſ` matches `s`, the Kelvin sign `K` matches `k`), would read `SessionId` or `ſessionId` as `sessionId` while the broker sees another key. So the reference brokers refuse, with `400`, any key that folds to one of these but isn't spelled exactly the same. Duplicate keys are harmless: the broker forwards its own serialization of the value it checked.

**Optional DataChannel rules (`authorizeDataChannels`).** The SFU forwards a published DataChannel to every subscriber that names it, and lets any publisher use any name. Rule 4 keeps subscriptions in the room, but inside a room nothing stops a participant from subscribing to, or publishing on, a channel name the app reserves for certain participants (for example a channel only two users may share). An app with such names sets the reference core's `authorizeDataChannels(caller, roomId, sessionId, route, entries)` hook, so it doesn't have to wrap the handler, read the body again and authenticate twice.
- **Where it runs:** on every `datachannels/*` route (`establish`, `new`, `update`, `close`), after rules 1 to 4 have passed and just before the request is forwarded. A request refused by an earlier rule never reaches it.
- **What it gets:** the caller, the room, the session in the path, the route, and the DataChannels named in the body (the `dataChannel` object, then each `dataChannels[]` entry; `location`, `dataChannelName`, `sessionId`, `canReply`, `id`), copied from the same parsed value that is forwarded. There is no second parse for the client to play against. A field of the wrong type is a `400` before the hook.
- **What it returns:** `true` forwards the request; anything else is `403 forbidden`; a throw is `500 internal_error` with no error text in the response or the diagnostics. Nothing reaches the SFU unless it returns `true`.
- **Limits:** it decides on requests, not on channels already set up, so a revoked grant doesn't cut off an existing subscription. It knows a remote entry's publisher only by session ID (already checked to be in the room); a rule that needs the publisher's identity encodes it in the channel name (`pair:<userA>:<userB>`), which the hook checks against the caller on both publish and subscribe.
- Unset, the broker behaves as before: every DataChannel request that passes rules 1 to 4 is forwarded. Both reference brokers wire it from `data_channels.ts`, unset by default.

**Reference brokers** live in [`broker/`](../broker/README.md): a Cloudflare Worker (Durable Object session store, `jose` JWT auth) and a Supabase Edge Function (Postgres session store, Supabase JWT auth). They share a dependency-free TypeScript core in `broker/supabase/functions/_shared/broker-core/`, which is where the Supabase CLI can bundle it and where wrangler can import it too. Both ship a room-membership stub that fails closed; the app implements it.

## 6. Simulcast

- **Why it's mandatory.** Assume a 4-person call with a 720p camera at about 1.5 Mbps, and a 20% share of time spent screen sharing at about 2.5 Mbps.
  - Egress is about **2.25 GB per participant-hour** without simulcast.
  - It's about **0.75 GB** when receivers pull 360p in the gallery and 180p thumbnails during screen share.
- **Publish:** three encodings named so that **`a` is the highest**:
  - `a` = full resolution,
  - `b` = ½ (`scaleResolutionDownBy: 2`),
  - `c` = ¼.

  This lets subscribers use the SFU's `asciibetical` ordering, where 'a' is the most desirable.
- **Subscribe** (implemented in M4, §6.1):
  - Pick `preferredRid` from the rendered tile size: the stage gets `a`, a gallery tile `b`, a thumbnail `c`.
  - Change it with `tracks/update`.
  - Set `ridNotAvailable: "asciibetical"` so a subscriber falls back when a layer stops, for example when the publisher's CPU throttles. Every Room pull sends it (`LayerSelectionOptions.ridNotAvailable`), and `tracks/update` keeps it. The SFU doesn't always return to the preferred layer when it comes back (§6.2).
  - **`priorityOrdering` is left at the SFU default (`none`)**, so a subscriber gets exactly the layer the client chose. That keeps layer switching predictable for the week-6 checkpoint. `LayerSelectionOptions.priorityOrdering` opts in to `asciibetical` (the SFU may step down under bandwidth pressure). Revisit after measuring on constrained links.
- **Screen share:** **one layer by default** (decided for the week-6 checkpoint, §12 question 2): `ScreenSharePresets.detail`, the captured resolution at up to 15 fps and 2.5 Mbps, which is the 2.5 Mbps the egress estimate above assumes. `ScreenSharePresets.simulcast` adds a `b` layer (¼ size, 5 fps, 250 kbps) for apps that show shares as thumbnails; subscribers then pick by tile size as for cameras. Measure both on devices before 1.0.
- **Codec:** **default to VP8 on every platform**, for every video track including screen shares, via `setCodecPreferences` on the transceiver (`defaultVideoCodecPreferences()`, §4.2).
  - **Why everywhere, not only on Windows.** H.264 has crashed `flutter_webrtc` on Windows (flutter-webrtc #982). The SFU forwards what each publisher encodes, so in a mixed room a Windows subscriber would have to decode H.264 from a macOS or Android publisher whose platform prefers it. VP8 decodes on every platform, and its simulcast is well-trodden. The cost is giving up hardware H.264 encoding on some mobile devices.
  - **Choosing another (M12):** `RoomOptions.videoCodec` (a `VideoCodec`: `vp8`, `h264`, `vp9`, `av1`; `null`, the default, keeps the session's preferences, VP8 unless changed) applies to every video the room publishes, and `publishCamera` / `publishScreen` / `publishMediaSource(codec:)` override it per publication (`LocalMediaPublication.videoCodec`). The preferences are the codec, then VP8, so a platform without that encoder sends VP8 (`setCodecPreferences` keeps only codecs the platform has). The SFU accepts H.264, H.265, VP8, VP9 and AV1 ([cloudflare-sfu.md](cloudflare-sfu.md#simulcast)).
  - **Windows:** a Windows publisher asked for H.264 sends VP8 and reports `RoomErrorEvent('videoCodec', UnsupportedError)`. Nothing protects a Windows *subscriber*: keep a room with Windows participants on VP8 ([checkpoint.md](checkpoint.md#windows-h264-crash)).
  - **Firefox without OpenH264:** Firefox encodes H.264 with the OpenH264 plugin, which it downloads by itself, but a fresh or locked-down profile (or `flutter drive`, which turns plugin downloads off) may not have it. Firefox still lists `video/H264` in its capabilities, so H.264 is negotiated, every layer stays at `framesEncoded: 0`, and the publication never starts sending (`whenSending()` never completes); nothing reports it (M13, Firefox 155). With the plugin, Firefox sends H.264 in three layers. A watchdog that falls back to VP8 when a non-VP8 video encodes nothing is a possible follow-up.
  - **H.264 and simulcast:** libwebrtc's `SimulcastEncoderAdapter` runs one encoder per layer. On a Pixel 10 (Android 16) that is three hardware `c2.google.avc.encoder` instances, and the subscriber decodes with `c2.google.avc.decoder`; all three layers sent (`publish_quality_test.dart`, M12). Some devices limit concurrent hardware encoders, and H.264 hardware encoders may refuse small or unaligned sizes; libwebrtc then falls back per layer or drops it. Check new devices with that test.
  - **VP9 and AV1 are experimental:** on the Pixel 10 they sent **a single stream** for the three `rid` encodings (only `a` in `outbound-rtp`; AV1 on the hardware `c2.google.av1.encoder`, VP9 on libvpx), so there is no layer to choose and every subscriber pulls the full size: simulcast's egress saving (above) is lost. libwebrtc expresses VP9/AV1 layers with `scalabilityMode`, which the package doesn't set.
  - `SfuSessionDefaults.videoCodecPreferences: const []` still gives the platform's order. Revisit the default after the checkpoint's device runs show whether Windows decodes H.264 safely.

### 6.1 Layer selection

The building blocks are in `lib/src/quality/`; the Room wires them (M4, `lib/src/room/remote_track_layers.dart`). The Room owns one `LayerSelectionController` and hands it to the views as `Room.layerReporter`.

- **Publisher ladder** (`SimulcastLadder`, internal): the layers a publisher sends, highest first. `SimulcastLadder.fromPreset(VideoPreset.h720)` is `a`=1280×720, `b`=640×360, `c`=320×180.
  - **Encoder layer limit.** libwebrtc's legacy simulcast limit sends 3 layers from 960×540 up, 2 from 480×270 up, and otherwise 1. It drops the **lowest** layers, so a 360p publisher sends only `a` and `b`. The ladder applies this limit by default, so the policy never asks for a layer the publisher doesn't send.
  - This is an expectation, not a guarantee: capture can come out smaller than requested, and libwebrtc versions differ. `ridNotAvailable: asciibetical` covers the remaining mismatch. **Check it on devices.**
  - Publishers announce their layers in `TrackInfo.simulcast` (§4.4). The internal `simulcastLadderFor(info)` (`lib/src/room/simulcast_hint.dart`) turns that into a ladder (16:9 and 1/2/4 when not stated, with the encoder limit). A hint without a size is read as a 720p capture with the hint's rids. The Room sets each publication's ladder when it appears and again whenever its hint changes. Video without a hint gets no rid: only the hidden-view release below applies to it.
- **Demand** (`TileDemand`, public): the tile's size in **physical** pixels (logical size × device-pixel ratio), plus whether it is visible.
- **Policy** (`SimulcastLayerPolicy`, internal), for a visible `w×h` tile:
  1. **Required lines:** `max(h, w × layerHeight / layerWidth)`. This assumes the video fills the tile ("cover"), which errs towards quality.
  2. **Up:** the lowest layer with `height × maxUpscale ≥ required`, or the highest layer if none is big enough.
  3. **Down:** the same with `height × maxUpscale × (1 − downgradeHysteresis)`, which is stricter.
  4. With no current layer, take "up". Otherwise upgrade at once if "up" is higher, downgrade only if "down" is lower, and stay put in between.
  5. A hidden or empty tile is **paused**. The SFU has no pause for a pulled track, so the Room decides what paused means: switch to the lowest layer, or close the pull after it has stayed paused for a while.
- **Defaults** (`LayerSelectionOptions`, public): `maxUpscale` 1.5, `downgradeHysteresis` 0.15, `debounce` 300 ms, `ridNotAvailable` `asciibetical`, `priorityOrdering` unset.
  - With a 720p publisher, a tile up to 270 physical lines gets `c`, up to 540 gets `b`, and anything bigger gets `a`. So a 2×2 gallery on a 1080p screen pulls `b`, which is what the egress estimate above assumes.
  - Once on `a`, a tile drops to `b` only at 459 lines or fewer (540 × 0.85).
- **Aggregation and debounce** (`LayerSelectionController`, internal): one per Room, keyed by a subscription ID.
  - Several views of one track each report under their own key. Each view goes through the policy (with the subscription's current layer, for hysteresis), and the **highest** layer wins. With no visible view, the subscription is paused.
  - The **first** choice for a subscription (after its first view reports) is emitted at once, so a new pull starts with the right layer. So is a change from **paused to visible**, so video appears as soon as a tile scrolls into view.
  - Every other change waits until the new choice has stood for the debounce. A choice that reverts before then emits nothing.
- **Widget** (`SimulcastLayerReporter`, public): wraps a video view.
  - After each frame, it reports the child's laid-out size × `MediaQuery.devicePixelRatioOf`, and only when the demand changed.
  - The view counts as hidden when `visible` is `false` (the app knows about scrolling and tabs) or when `TickerMode` is off (a covered route).
  - It removes its view on dispose, and when its subscription ID or reporter changes.
  - It talks only to the `LayerDemandReporter` interface. `ParticipantVideoView.remote` uses it with `Room.layerReporter` by default.
- **In the Room** (M4):
  - **Target layer**, per remote video publication: the manual `setPreferredLayer` if set; else the controller's choice; else, while every view is hidden (paused), the ladder's lowest layer; else, before any view reported, `RoomOptions.defaultVideoLayer`. A new pull starts with it; a live pull is switched with `tracks/update` (failures are reported as `RoomErrorEvent('tracks/update')` and retried on the next change); a pull that is off its session only remembers it. After every (re)pull the target is applied again, so a change made while the pull was in flight is not lost.
  - **Hidden or paused tiles:** the track drops to its lowest layer as soon as the controller reports paused (after the debounce), and after `RoomOptions.hiddenVideoLinger` (default 5 s; `null` never) the pull is released: leases stop counting (`RemoteTrackLayerState.released`) and the pull is closed. A view that becomes visible again sooner just gets its layer back; one that does so later is pulled again at once, at its layer. This avoids pull/close churn when scrolling. An explicit `subscribe()` (or `AutoSubscribe.video`) keeps a hidden track pulled at its lowest layer.
  - **Lease grace:** see §4.3 (`RoomOptions.leaseReleaseGrace`, 500 ms).
  - **Manual override:** `RemoteTrackPublication.setPreferredLayer(layer)` wins until `clearPreferredLayer()` (or `setPreferredLayer(null)`); the automatic choice then applies again.
  - **Debug UIs:** `RemoteTrackPublication.currentRid` (the rid the live pull asks for), `layerState` and the replaying `layerStateChanges` (`RemoteTrackLayerState`: current and target rid, automatic rid, manual layer, hidden, released). The received resolution is in the typed stats (`RemoteTrackPublication.stats`: `width`, `height`, `framesPerSecond`; §7.1), as the example's tile overlay shows.
  - Reports for tracks the room doesn't show as video (closed, audio, unknown IDs) are ignored.

### 6.2 Publisher-side layer pausing (M12)

A publisher can stop encoding the simulcast layers no one pulls (`active: false` on the encoding, through `RTCRtpSender.setParameters`; no renegotiation), which saves its uplink, CPU and battery. Implemented in `lib/src/quality/layer_pausing.dart` (the policy and `LayerPauser`) and `lib/src/room/room_publish_quality.dart` (the Room's wiring). **Pausing is off by default** (`RoomOptions.layerPausing`, `LayerPausingOptions.on` turns it on); reporting the demand is on. Why off: see "What the SFU does" below.

- **How a publisher learns the demand.** The SFU doesn't tell it: no API call, header or DataChannel event says which `rid` each subscriber pulls (the docs and the OpenAPI schema have nothing like it; the `server-events` DataChannel carries none). So rooms tell each other through signaling. Each participant announces **`ParticipantState.layerDemand`**: SFU `trackName` → the RID it asks for, for every simulcast video it pulls or is about to pull (subscribed, or held by a view that isn't released; the target RID of §6.1, so a hidden view reports the lowest layer and a released pull drops out). A track that isn't listed isn't pulled. `null` (the field absent) means the participant doesn't report: an older client, or `LayerPausingOptions.reportDemand: false`. The room names tracks `<source>-<uuid>`, so the map needs no publisher key. A change of demand re-announces the local state through the room's coalescing announcer; layer choices are already debounced (§6.1), so this adds at most one signaling update per settled layer change. The announcement goes out alongside the pull or `tracks/update`, not after it.
- **Aggregation, per published simulcast video** (`layersToSend`): every other participant with a session contributes a wish: its RID for the track, nothing if it doesn't list the track, or "every layer" if it doesn't report (`layerDemand == null`) or names a RID the track doesn't announce. The publisher keeps **every layer from the lowest up to the highest one wished for**, plus the lowest `minActiveLayers` (default 1), and pauses the layers above. Lower layers are never paused for being unwanted: they are cheap, the SFU falls back to them while a paused layer resumes (`ridNotAvailable: asciibetical`), and a subscriber whose SFU steps down under bandwidth pressure (`priorityOrdering: asciibetical`, §6) needs them. The ladder is the announced one with libwebrtc's layer limit applied (§6.1), from the announced size (§6.3): a RID the encoder doesn't send counts as the lowest layer, and is left as it is.
- **Timing** (`LayerPauser`): a layer is resumed **at once** when someone wants it, and paused only after it has been unwanted for `pauseDelay` (5 s), so a view that shrinks and grows back (scrolling, a layout change) never waits for a resume. Each layer's delay runs from when it became unwanted. Encoder changes are applied one at a time, ending on the latest set.
- **Edge cases.**
  - **New subscribers:** the floor layer is always on, so a new pull gets a frame at once (at the floor while its own layer resumes). It reports its layer as soon as the pull is wanted.
  - **Older clients** (no `layerDemand`) keep every layer on while they are in the room.
  - **Single-layer video** (a screen share's default `ScreenSharePresets.detail`, or `encodings: []`) announces no simulcast and is never touched. A layer the app turned off in its encodings stays off.
  - **Re-session:** `setEncodings` on a publication off its session only stores the encodings, so a republish (§8) pushes the paused layers as paused; demand changes then apply to the new transceiver.
  - Only participants in the room's signaling count: someone pulling the track by its session ID and name from outside the room is invisible to the publisher.
  - **Not on Windows.** flutter_webrtc's Windows plugin (1.6) ignores encoding changes in `setParameters`: it edits copies of the encodings, never writes them back, and reports success. A paused `a` kept `active: true` and kept encoding (M13 Windows run). The Linux plugin builds the same C++ code. So a Windows or Linux publisher never pauses: with pausing on, it keeps every layer and reports `RoomErrorEvent('layerPausing', UnsupportedError)` once. Windows participants still report their demand, so publishers on other platforms can pause for them. The same limit affects `TrackPublication.setEncodings` on Windows (the new encodings apply only at the next republish).
- **Keyframes on resume.** Re-activating a VP8 layer makes libwebrtc encode a keyframe for it at once (`keyFramesEncoded` rises), so a subscriber that the SFU moves to that layer doesn't wait for a PLI. The SFU asks for keyframes with FIR and PLI on its own schedule (`firCount`, `pliCount`).
- **What the SFU does** (measured on a Pixel 10, loopback through the real SFU, M12; `publish_quality_test.dart` and an ad-hoc session-level experiment):
  - A paused layer leaves the subscribers on it within about 1.7 s (to the next available layer, `ridNotAvailable: asciibetical`).
  - **A new pull of a paused-then-resumed layer** gets it fast: 0.4–0.6 s through the Room (the demand resumes the layer while the pull negotiates), 1.2–1.7 s at the session level. The paused layer itself works.
  - **Switching up with `tracks/update` is the weak spot.** Even with every layer on, the SFU moves a subscriber up on a cadence of about 6 s (6.2–6.5 s, sometimes 10–12 s), and sometimes never within 20 s: it then keeps forwarding a lower layer (`b`, or `c`) although the subscriber asked for `a`. Room level, `c` → `a`: 3 of 3 in 6.4–10.5 s with every layer on; 2 of 4 (6.5 s, 6.6 s) when `a` and `b` had been paused and resumed with the request. Session level: 5 of 8 with every layer on, 1 of 7 when the request and the resume went together, and re-sending the same RID (or going through `b`) every 6.5 s for 40 s didn't help a stuck subscription. The SFU's decision is invisible (FIR on the target layer is sometimes never sent); a bandwidth estimate that grew only to the lower layer's rate is the likely reason, since a fresh pull isn't affected.
  - **In Chrome 154** (M13, `publish_quality_test.dart` as JS and as Wasm): paused after 2.3 s, resumed 78–90 ms after the request, a new pull of the paused `a` decoded in 0.24–0.35 s, and switching up from `c` to `a` after the pause stayed on `b` for 20 s in both runs: the same weak spot as on the Pixel.
  - **Decision:** pausing stays opt-in until up-switches are reliable. A stuck subscriber still gets continuous video, only at a lower resolution than its view wants. Possible fix: switch up to a layer that was paused by pulling it afresh (make before break: pull the new layer, swap the rendered track, close the old pull), which costs a renegotiation and a brief double egress; see §12, question 6.

### 6.3 The announced simulcast size (M12)

`TrackInfo.simulcast` carries the highest layer's size, and subscribers build their ladder from it (§6.1). Until M12 it was the size the publisher **asked** for, while cameras capture something else: a Mac's FaceTime HD camera gives 640×480 for 640×360, and a phone held upright sends **portrait**. Android's capturer rotates frames before they are encoded: the Pixel 10 asked for 1280×720 sent 720×1280 (`outbound-rtp` and `media-source` both), while the track's settings still said 1280×720. A landscape ladder for a portrait video picks layers that are too large for portrait tiles (a 400×700 tile wanted `a` instead of `b`).

- **What is announced:** the size the encoder gets: the captured size, after rotation and after libwebrtc's CPU adaptation. At publish, the track's settings (accurate on macOS and the web; the requested size on phones and on Windows). Then, from `getStats()`, the `outbound-rtp` layers of the track's `media-source` (`mediaSourceId`): the sending layer with the smallest scale, multiplied back by its `scaleResolutionDownBy`, skipping paused layers and layers whose `qualityLimitationReason` is `bandwidth`. Without such a layer, the `media-source` report's own size (`width`, `height`), turned to the orientation of the lowest sending layer when one reports a size (see iOS below), and in browsers the track's settings.
- **Why the layers, not the `media-source`:** the `media-source` has the camera's frames *before* libwebrtc's resolution adaptation, which scales the encoder's input (every layer) when encoding takes too long (`qualityLimitationReason: cpu`). The Pixel 10 has no VP8 hardware encoder (libwebrtc logs "Failed to create primary VP8 encoder", then libvpx encodes all three layers); at about 85 % encode usage, libwebrtc scaled the input to ¾ about 20 s into the call: `media-source` 720×1280, layers 540×960 / 270×480 / 135×240, `qualityLimitationReason: cpu` (2026-10-03, single device and `cross_device_test` with a Mac). Announcing 720×1280 made subscribers' ladder a third too large (a tile wanting 721–960 lines got `b`, 480 lines, an upscale of up to 2× instead of `maxUpscale` 1.5), and a deeper step can drop the lowest layer (§6.1's encoder limit) while the ladder still lists it. CPU adaptation steps are seconds apart (libwebrtc checks every 5 s and steps back up only after 40 s or more), so following them with the 3 s check costs few announcements.
- **Why not `bandwidth`:** libwebrtc's quality scaler (`qualityLimitationReason: bandwidth`) scales the input only while a single layer is active, which layer pausing (§6.2) causes. Announcing that size would feed back: a smaller ladder keeps a second layer on, which stops the scaler, which brings the full size back. A top layer that the bandwidth estimate suspends reports `bandwidth` too, and keeps its last size; the `media-source` is right then.
- **iOS: the `media-source` is landscape.** The iPhone's capturer rotates by frame metadata, so the `media-source` keeps the sensor's orientation while the encoded layers are rotated: an iPhone 16 Pro Max (iOS 27) held upright had `media-source` 1280×720 and layers 720×1280 / 360×640 / 180×320 (Android's capturer rotates the pixels, so its `media-source` is portrait already). While `a` and `b` were paused and `c` was limited by `bandwidth` (no one pulling yet, so pausing kept only `c`), no layer qualified, and the room announced the landscape 1280×720 for a portrait video; `publish_quality_test` passed on it because it compared with the same `media-source`. So the fallback takes the **orientation** (only) from the lowest active layer that reports a size, whatever limits it: that layer is pausing's floor and the last the bandwidth estimate suspends, so its size is current, while a paused layer keeps the size from before it paused (stale after the phone turned). The size stays the `media-source`'s: rotation doesn't depend on the bandwidth, so this doesn't bring back the quality scaler's feedback. Before any layer reports a size, the `media-source` is announced as it is, and corrected within one check. `publish_quality_test` now samples the announcement's aspect against the layers being encoded every 500 ms; after the fix it passed on the iPhone (59 samples, none mismatched) and the Pixel 10. In those runs, and in one run of the old code, every layer was `limited by none`, so the fallback was not reached on the device; the unit tests cover it.
- **Windows:** its `media-source` report has no size (flutter_webrtc's capturer gives libwebrtc no source stats), and its track settings are the requested size, so only the layers give a size; while they are `bandwidth`-limited, the last size stays. M13 Windows run: an OBSBOT Tiny 2 asked for 960×540 captures 1280×720 (announced 960×540 before the fix, 1280×720 after); a virtual camera asked for 640×360 sends 1920×1080.
- **When:** right after the publish, 0.7 s after every new track (a camera switch, an unmute), and every 3 s while the track is sent (a phone turned, a window resized, a constraint change, the CPU adaptation). A change re-announces the local state and re-evaluates layer pausing (§6.2). While muted, nothing is sent and the last size stays.
- Only the size changes; the RIDs and scale factors are the encodings'. It applies to every simulcast video the room publishes: the camera, `ScreenSharePresets.simulcast` (which announced no size before, so subscribers assumed 720p), and `publishMediaSource` with a `simulcast` hint.
- Checked on the Pixel 10: `publish_quality_test.dart` (captured 720×1280, announced 720×1280, the camera's settings 1280×720) and `camera_switch_test.dart` (360×640 for the 640×360 preset after two switches, and Bob's view matches). The CPU adaptation (2026-10-03): announced 720×1280, then 540×960 within 3 s of the adaptation (`media-source` still 720×1280), and the Mac in `cross_device_test` saw 540×960 announced and received 960p from `a`.
- This reads one raw stats report. When typed stats arrive (M12 part A), it should read them instead.

## 7. Active speaker

- Poll `getStats()` for audio `inbound-rtp` / receiver `audioLevel`, every 200–500 ms.
- Smooth with a short window, and apply a threshold plus hold time so the speaker doesn't flicker.
- Include the local microphone level, so "you are speaking while muted" hints are possible.
- Emit an ordered list of participant IDs.

The building blocks are in `lib/src/quality/`; the Room wires them (M4, `lib/src/room/room_speakers.dart` and `room_audio_levels.dart`). Only `ActiveSpeakerOptions` (as `RoomOptions.activeSpeaker`) and the Room's outputs are public.

- **API** (M4):
  - `Room.activeSpeakers` (`List<String>`) and `activeSpeakersChanges` (replaying); `Room.dominantSpeaker` (`String?`) and `dominantSpeakerChanges`.
  - `RemoteParticipant.isSpeaking`/`speakingChanges`, and `audioLevel`/`audioLevelChanges` (smoothed, `0..1`, for meters).
  - `LocalParticipant.isSpeaking`/`speakingChanges`, and `isSpeakingWhileMuted`/`speakingWhileMutedChanges` with `canDetectSpeakingWhileMuted` (see below).
  - `RoomOptions.activeSpeaker` (default `ActiveSpeakerOptions()`); `null` turns detection off (no stats polls, empty outputs).
- **Room wiring:**
  - One `ActiveSpeakerMonitor` per room, started when the room joins and disposed on `leave()` (the poll timer stops before anything else).
  - **It polls for as long as the room is joined, not only while someone listens.** The synchronous getters must be right without a listener, and the detector's smoothing and hold times need a continuous series of samples; a listener-driven start would make the first seconds after subscribing wrong. The cost is one `getStats()` per poll, and **none while there is no audio to measure** (no microphone pulled and no local microphone sending).
  - **Levels** come from `RoomAudioLevelSource` over `SfuSession.getStats()`: remote `inbound-rtp` reports map to participants by `mid`, then `trackIdentifier`, through the room's microphone publications whose pull is on the current session (screen-share audio doesn't count). The local level is the `media-source` of the microphone's current track; without one (no microphone, or muted), local audio never counts, so screen-share audio can't make the local participant "speak".
  - **Session replacement (§8):** the source reads `Room._session` on every poll and rebuilds its stats reader when the session object changed, so energy baselines never mix two peer connections. `Room._onSessionReplaced()` (a private extension in `room_speakers.dart`) forces that at once: `Room._replaceSession` calls it. Nothing else is needed.
  - A participant who leaves is removed from the detector at once.

- **Levels** (`AudioLevelSource`; `StatsAudioLevelSource` reads a peer connection's `getStats()`):
  - **Remote:** audio `inbound-rtp` reports. The Room maps each report's `trackIdentifier`/`mid` to a participant. It returns `null` for streams that shouldn't count, such as screen-share audio. When several streams map to one participant, the loudest wins.
  - **Local:** audio `media-source` reports, under the local participant's ID. The Room can name the microphone track, so other audio sources don't count.
  - **The level** is the report's `audioLevel`. When that's missing, it's `sqrt(ΔtotalAudioEnergy / ΔtotalSamplesDuration)` between polls, which is the RMS of `audioLevel` per the W3C stats spec. A stream's first poll then has no reading, and a duration that didn't grow reads as 0.
  - **What `flutter_webrtc` 1.6.2 reports:**
    - Every platform returns W3C stats. Native platforms copy libwebrtc's members as they are.
    - Native libwebrtc has `audioLevel`, `totalAudioEnergy` and `totalSamplesDuration` on audio `inbound-rtp` and `media-source`, and `trackIdentifier` and `mid` on `inbound-rtp`. The legacy `track` stats type is gone.
    - Browsers vary (Firefox has lacked `audioLevel` on some types), which is what the energy fallback is for.
    - Report timestamps are µs on native and ms on the web, so they are never used.
- **Poller** (`ActiveSpeakerMonitor`):
  - It polls every `pollInterval`. Polls never overlap: a tick during a running poll is skipped.
  - A failed poll is skipped silently, since `getStats` can fail briefly during renegotiation.
  - It exposes `speakers`, `dominantSpeaker`, `localSpeakingWhileMuted` and `snapshots` (with smoothed levels, for meters). Each replays its current value.
- **Detector** (`ActiveSpeakerDetector`, pure Dart), per participant and per sample:
  1. **Smooth:** an exponential moving average with time constant τ: `level += (1 − e^(−Δt/τ)) × (raw − level)`. A participant missing from a sample counts as 0.
  2. **Start speaking** once the smoothed level has stayed ≥ `speakingThreshold` for `activationTime`.
  3. **Stop speaking** once it has stayed < `silenceThreshold` for `releaseTime`. The gap between the thresholds is the hysteresis; the release time bridges pauses between words.
  4. **Order** loudest first. Speakers keep their previous order and newcomers are appended by level. Then neighbours swap only when the lower one is louder by more than `reorderMargin`.
  5. **Dominant speaker:** the first speaker is dominant at once. A new loudest speaker takes over after staying loudest for `dominantSwitchTime`. A dominant speaker who falls silent stays dominant until someone else takes over, or leaves. The local participant can't be dominant unless `localCanBeDominant` is set.
  6. **Muted local participant:** left out of `speakers`, because nobody hears them. The same state machine, with `mutedActivationTime`, drives `localSpeakingWhileMuted` instead. Muting or unmuting restarts the local speaking state, so the hint doesn't pop up the moment someone mutes mid-sentence.
- **Defaults** (`ActiveSpeakerOptions`): poll every 250 ms, τ 300 ms, speaking threshold 0.04 (about −28 dBFS), silence threshold 0.02, activation 200 ms (two loud polls in a row), release 800 ms, reorder margin 0.02, dominant switch 1.5 s, local not dominant, muted-hint activation 500 ms.
- **The muted microphone's level: not supported yet** (`LocalParticipant.canDetectSpeakingWhileMuted` is `false`, and `isSpeakingWhileMuted` stays `false`).
  - With `MutePolicy.keepCapture` the mic keeps capturing, but muting is `replaceTrack(null)` on the sender (§4.2), and a sender without a track has no `media-source` report.
  - **`flutter_webrtc` 1.6.x has no other way to read a local track's level** (checked in 1.6.2+hotfix.3): `getStats(track)` only finds tracks attached to a sender or receiver, and the native audio sinks and processing hooks (`AudioProcessingAdapter`, `FlutterRTCAudioSink`) have no Dart API.
  - Options for later, each needing device checks: mute a `keepCapture` microphone with `track.enabled = false` and keep it on the sender (native libwebrtc appears to measure the `media-source` level before the send-side mute, but that changes the mute model of §4.5); a second, local-only peer connection that sends the captured track (costly); on the web, a Web Audio `AnalyserNode` on the track.

### 7.1 Typed stats and connection quality (M12)

Typed, immutable models over `getStats()`, and a quality rating per participant, so apps don't parse raw reports. The models are in `lib/src/quality/call_stats.dart` (public), the parser in `call_stats_reader.dart` (internal), the rating in `connection_quality.dart` (`ConnectionQuality`, `ConnectionQualityOptions`, `QualityThresholds`, `RoomStatsOptions` public; the rating and hysteresis internal); the Room wires them in `lib/src/room/room_stats.dart`.

- **API:**
  - `Room.stats` (the latest `RoomStats`, or `null`), `Room.statsChanges` (each snapshot, replaying the latest; listening starts the polling), and `Room.getStats()` for one snapshot now. `RoomStats` has `connection` (`ConnectionStats`: the selected pair's `roundTripTime`, `availableOutgoingBitrate`, the local and remote `IceCandidateStats` with `type` (`host`/`srflx`/`prflx`/`relay`) and `isRelayed`, bytes and their rates), `local` (`LocalTrackStats` by track name, with one `OutboundLayerStats` per simulcast layer, highest first: `rid`, `active`, `codec`, `bitrate`, `targetBitrate`, size, `framesPerSecond`, `qualityLimitationReason`, packets and bytes sent, retransmissions, frames and key frames encoded, NACK/PLI/FIR counts, and the SFU's receiver report: `roundTripTime`, `packetsLost`, `fractionLost`, `jitter`), `remote` (`RemoteTrackStats` by `RemoteTrackPublication.id`: `codec`, `bitrate`, size, `framesPerSecond`, packets received and lost, `packetLoss` over the interval, `jitter`, frames decoded and dropped, `freezeCount` and `totalFreezesDuration`, NACK/PLI/FIR, and for audio `audioLevel`, concealed samples and `concealment` over the interval), `interval`, and `reports` (the raw reports, so nothing is lost; `room.session.getStats()` stays too).
  - `LocalMediaPublication.stats` / `statsChanges` and `RemoteTrackPublication.stats` / `statsChanges`: the same, for one track (`null` while it has no reports).
  - `Participant` (sealed; `LocalParticipant` and `RemoteParticipant` implement it) with `connectionQuality` / `connectionQualityChanges`, and `ParticipantConnectionQualityChangedEvent(participant, quality)` on `Room.events`. `ConnectionQuality`: `unknown`, `lost`, `poor`, `good`, `excellent` (`isAtLeast`).
  - `RoomOptions.stats` (`RoomStatsOptions`): `interval` (2 s) and `connectionQuality` (`ConnectionQualityOptions`, on by default; `null` turns it off).
- **Polling.** One `getStats()` on the current session per interval feeds both. It runs while the room is joined and someone listens to a stats stream, **or** connection quality is on (the default): the synchronous `connectionQuality` getters and the hysteresis need a continuous series, as active speaker does (§7). That is one call every 2 s, next to active speaker's every 250 ms. With quality off and no listener nothing is polled. Polls never overlap; a failed poll is skipped; `leave()` stops the timer first and completes the streams.
- **Mapping** (`CallStatsReader`):
  - A local track's `outbound-rtp` reports (one per simulcast layer) by the publication's `mid` on the current session (the session's `mid` is the one re-read through the sender's ID, §4.2), else through the `media-source` whose `trackIdentifier` is the sent track (`mediaSourceId`). Each layer's `remote-inbound-rtp` (the SFU's RTCP receiver report) by `remoteId`, else `localId`, else `ssrc`. Layers are ordered by `encodingIndex`, else by `rid`.
  - A remote track's `inbound-rtp` by the pull's `mid`, else by `trackIdentifier` (as active speaker, §7). Only pulls on the current session count, so a `mid` reused by a new peer connection maps to the current pull.
  - The connection: the transport's `selectedCandidatePairId`, else a pair marked `selected` (older Firefox versions have no `transport` report; Firefox 155 has one), else the nominated, `succeeded` pair that carried the most bytes. Its candidates by `localCandidateId` / `remoteCandidateId`. Addresses are not modelled (they stay in `reports`).
  - Codecs by `codecId` (`mimeType`).
- **Platform differences.** Values may be numbers or numeric strings; `kind` may be `mediaType` on older platforms. **A missing value is `null`, never 0**: libwebrtc leaves out `frameWidth` until the first frame, `targetBitrate` on some platforms, `freezeCount` in older libwebrtc versions; browsers leave out `availableIncomingBitrate`; Firefox has no `qualityLimitationReason`. Seen on macOS (libwebrtc M150, `flutter_webrtc` 1.6.2): `remote-inbound-rtp` exists for the audio stream before any packet is sent, with `roundTripTimeMeasurements: 0`; `candidate-pair` has `currentRoundTripTime` and `availableOutgoingBitrate` (300 kbps before media); `outbound-rtp` has `rid`, `encodingIndex`, `mid`, `active`, `qualityLimitationReason` and `qualityLimitationDurations` (a map, ignored). Seen in Chrome 154 (M13): the same fields, `mid` maps every track, timestamps are in milliseconds, the audio `outbound-rtp` has `mid`, `mediaSourceId` and `remoteId` but no `rid`, and the pair is `prflx` → `host` over UDP. Compiled to Wasm, every number from JavaScript is a `double` (`36.0` packets), which the reader's parsing rounds; never test stats values with `is int`. Seen in Firefox 155 (M13, Windows): a `transport` report with `selectedCandidatePairId`; the pair has no `availableOutgoingBitrate` or `availableIncomingBitrate` (the estimates are `null`); the video `outbound-rtp` has `rid`, `mid`, `remoteId`, the size and the frame counters but no `encodingIndex`, `active`, `mediaSourceId`, `qualityLimitationReason`, `targetBitrate` or `encoderImplementation` (so `OutboundLayerStats.active` is always `null` there, and layer pausing shows only as `framesEncoded` staying flat); the audio `media-source` has no `audioLevel` (the active speaker uses the energy fallback); `inbound-rtp` has no `decoderImplementation`; timestamps are in milliseconds, and every track maps by `mid`.
- **Rates** come from the change of each report's counters (per report `id`, stable for one RTP stream) since the previous snapshot of the same session: bitrates from bytes, frame rates from frame counters when `framesPerSecond` is missing, loss and concealment over the interval. The interval is the reports' own `timestamp` difference when plausible (µs on native platforms, ms in browsers; accepted within a factor of two of the wall time between the reads), else the wall time (`package:clock`, so tests use fake time). A counter that goes down (a reset) gives no rate. The first snapshot after joining or a re-session has no rates: `Room._replaceSession` rebinds the reader (`_onSessionReplaced`), and a poll that straddles the switch is not used as a baseline.
- **Connection quality.** The rating is per stats interval; **the worst metric decides**:

  | Metric | `excellent` | `good` | `poor` |
  |---|---|---|---|
  | Round-trip time to the SFU (local) | ≤ 150 ms | ≤ 300 ms | > 300 ms |
  | Packet loss | ≤ 1 % | ≤ 5 % | > 5 % |
  | Audio jitter | ≤ 20 ms | ≤ 50 ms | > 50 ms |
  | Time a received video was frozen (remote) | 0 | ≤ 10 % | > 10 % |
  | Sender bandwidth (local) | not limited | a video layer has `qualityLimitationReason: bandwidth` | the outgoing estimate is below 150 kbps while sending video |

  - **Local participant** (this client's own connection): the selected pair's `currentRoundTripTime` (STUN checks; else the receiver reports' `roundTripTime`), the `fractionLost` the SFU reports for what is sent (weighted by each sending layer's bitrate, so one lost packet on a quiet audio stream doesn't outweigh a video), the SFU's audio jitter, and the bandwidth rows. **`lost`** while the room is `reconnecting` or `disconnected` (set at once from the connection state); meanwhile every remote participant is `unknown`, since nothing can be measured.
  - **Remote participants** (what arrives from them, so their uplink and our downlink together): the loss over all packets of their pulled, unmuted tracks (from `packetsLost` and `packetsReceived`), the worst audio jitter, and the share of the interval a video was frozen (`totalFreezesDuration`). **`lost`** when none of their pulled, unmuted tracks received a byte for `lostAfter` (5 s) while they are still in signaling (a frozen app, a dead uplink, a session the SFU dropped). With nothing measurable (nothing pulled, everything muted) the level stays, so muting never reads as `lost`. RTT is ours, not theirs, so it isn't used for them.
  - **Hysteresis** (`QualityTracker`): a lower level applies once ratings have stayed below the current one for `degradeAfter` (4 s, two polls), a higher one once they have stayed above it for `improveAfter` (6 s, three polls; recovering more slowly than degrading is the usual choice, so an indicator doesn't flash green on a flaky link). The new level is the closest to the current one among those ratings, and a rating at the current level restarts the count, so a link alternating between two levels stays put. The first rating (from `unknown`) and anything after `lost` apply at once; `lost` itself has its own timeout. Time-based, so a different poll interval keeps the same behaviour.
  - **Why these numbers.** Common practice, as concepts: ITU-T G.114 puts one-way mouth-to-ear delay up to 150 ms as fine for most conversations and above 400 ms as unacceptable; the RTT here is only this client's leg to the nearest SFU edge, so 150 / 300 ms leaves room for the other leg, the jitter buffer and the codecs. Opus with in-band FEC and video with NACK hide about 1 % loss without anyone noticing, and conversations stay usable to about 5 %. A jitter buffer adds roughly twice the jitter in delay, so 20 / 50 ms of jitter is 40 / 100 ms more delay. Video freezes use the W3C stats' own definition (`freezeCount`, `totalFreezesDuration`). `qualityLimitationReason: bandwidth` is libwebrtc saying its bandwidth estimate keeps a layer down. Other WebRTC SDKs commonly rate a few levels from loss, RTT and jitter (often through a MOS-like score) and smooth them over seconds; this is the same idea, kept transparent: a table of limits, configurable through `ConnectionQualityOptions`.
  - **Left out, on purpose.** Remote bitrate against an expectation: a static scene, a layer switch or DTX legitimately drop the bitrate tenfold, and the publisher's encoder targets aren't known to subscribers; loss, freezes and `lost` catch the real failures. Remote video jitter: frames go out in bursts (pacing), which inflates it without hurting anyone. Frame rate: a loaded CPU lowers it (`qualityLimitationReason: cpu`), which is not the connection.
  - **Decision: quality is not shared through signaling** (for now). Each client rates what it can measure: its own connection, and what arrives from each other participant. Sharing the local rating in `ParticipantState` would let peers tell "their uplink is poor" from "my downlink is poor", but every change would be a presence update fanned out to the room (Supabase presence and similar adapters rate-limit those), older peers wouldn't send it, and the receiver already sees the effect of the sender's uplink in loss, freezes and `lost`. An app can tell the cases apart in the meantime: when only one remote participant degrades, it's theirs; when everyone does and `LocalParticipant.connectionQuality` drops too, it's ours. Revisit when the first consumer needs "X has a poor connection" exactly; it could then ride in `metadata` or a DataChannel rather than in the track state.
- **Tests:** `test/quality/call_stats_reader_test.dart` (mapping, layer order, rates and their intervals, resets, nulls, string numbers, the connection's pair selection), `test/quality/connection_quality_test.dart` (the limits, the hysteresis, the samples), `test/room/room_stats_test.dart` (polling only while listened to with quality off, always while joined with it on, stopping on leave; the mapping through a room; quality from `unknown` to rated, `poor` after 4 s of loss, `lost` after 5 s without bytes and back, muted tracks not counted, `lost`/`unknown` while reconnecting; a re-session's first snapshot without rates). On devices: `example/integration_test/stats_test.dart` (two rooms in one process: three layers sent at halving sizes with bitrates and frame rates, the received video and audio, RTT, quality reaching `good` or better, and `lost` on both sides when the publisher's session fails with reconnection off). First macOS run: the transport checks passed (RTT 2–3 ms, both `excellent`); the media checks are still to run on a machine whose camera delivers frames (roadmap M12).

## 8. Reconnection

Cloudflare's guidance is to **replace the connection**: create a new session and re-push and re-pull. ICE restart isn't documented for the SFU.

- **Triggers:**
  - `RTCPeerConnectionState.failed`, or `disconnected` for more than N seconds;
  - network-change events;
  - the mobile app returning to the foreground after the OS killed sockets;
  - broker errors that mean the session is gone. The SFU returns HTTP `410` with `session_error` for an expired session. An unconnected session can expire before its first track or DataChannel operation.
- **Procedure:**
  1. Create a new session.
  2. Re-push the current local tracks with the same `trackName`s.
  3. Update signaling with the new `sessionId`.
  4. Remote peers see the `sessionId` change and re-pull.
  5. Re-pull our own subscriptions from peers' current sessions.
- **Backoff:** exponential with jitter. Expose `reconnecting` and `reconnected` states.
- **Don't lose local capture.** Keep the `MediaStreamTrack`s and only replace the transport.

The building blocks are in `lib/src/reconnect/`. They are pure decision logic, with no timers or I/O; the Room wires them up (below). `BackoffOptions`, `ReconnectTriggerOptions` and `ReconnectReason` are public.

- **`Backoff`** (internal) covers one reconnection episode.
  - The delay before attempt `n` (0-based) is uniform in `[0, min(maxDelay, initialDelay × multiplier^n)]`. This is exponential backoff with **full jitter**, so clients that dropped together don't come back together.
  - `nextDelay()` returns `null` once `maxAttempts` delays have been handed out, or once `maxElapsed` has passed since the episode's first attempt.
  - `reset()` after a successful reconnection starts a fresh episode.
  - The random source and the clock are injectable. The default clock is `package:clock`'s stopwatch, so `fake_async` drives it; `Backoff.debugDefaultRandom` (tests only) makes the jitter deterministic.
  - **Defaults** (`BackoffOptions`): initial 500 ms, ×2, cap 10 s, no attempt limit, give up after 2 minutes.
- **`ReconnectTrigger`** (internal) decides *when* to re-session. The caller feeds it events with a monotonic timestamp, schedules a timer for `nextCheckAt`, and calls `check` when it fires. Every input returns a `ReconnectReason` when it decides to reconnect.
  - `failed` triggers at once.
  - `disconnected` triggers after `disconnectedTimeout`, or at once if a network change happened within `networkChangeWindow` before it.
  - A network change **while disconnected** triggers at once. While connected, it only arms that window, because platforms report changes that don't break the connection (a second interface coming up).
  - `new`/`connecting` for longer than `connectTimeout` triggers.
  - Resuming after at least `backgroundThreshold` in the background triggers, because the OS may have killed the sockets while the peer connection still says `connected`. Resuming also runs `check`, since timers may not have run while suspended.
  - `sessionGone` (a `SessionGoneException`: 410 or `session_error`) triggers at once.
  - `closed` clears the timers, because the package closed the connection itself.
  - Once triggered, it ignores input until `reset()`, so one outage causes one re-session. `reset()` keeps the background state.
  - **Defaults** (`ReconnectTriggerOptions`): disconnected timeout 5 s, connect timeout 15 s, network-change window 10 s, background threshold 30 s.

### 8.1 The Room's re-session (M5)

Implemented in `lib/src/room/room_reconnection.dart` (`_Reconnection`, a part of the room library). On by default; `RoomOptions.reconnect` (`ReconnectOptions`) tunes it and `ReconnectOptions.disabled` turns the automatic part off.

- **Inputs** feed one `ReconnectTrigger` per room:
  - the current session's `connectionState` (`initial` is left out, so an idle session with nothing negotiated never hits the connect timeout; `failed` comes from `failures` instead, which knows the reason) and its `failures`: `SfuSessionGone` → `sessionGone`, `SfuPeerConnectionFailed` → `peerConnectionFailed`. The session's own ICE timeout (7 s) and the trigger's `disconnected` timeout (5 s) overlap; whichever fires first wins.
  - **Network changes** from a `NetworkChangeSource` passed to `CloudflareRealtime(networkChanges:)`. **None by default:** the core package takes no connectivity plugin. The example app polls `NetworkInterface.list()` every 2 s and reports a change when the set of addresses changes (no native plugin to break the checkpoint builds on Windows, macOS and Android); apps that use `connectivity_plus` can wrap `onConnectivityChanged` in a few lines. The room doesn't drive the app's signaling, which has to recover on its own: the example's `WsSignaling` listens to the same source (a change cuts its backoff short and restarts a connect still pending) and abandons a connect that isn't open within 10 s, since one started while offline can hang until the OS gives up (75 s on macOS) and keep presence away long after the media is back.
  - **The app lifecycle** from an `AppLifecycleSource` (`CloudflareRealtime(appLifecycle:)`), by default `FlutterAppLifecycleSource`: one `AppLifecycleListener` per room; `paused` and `resumed` count. Without a Flutter binding it emits nothing.
  - Time comes from `package:clock`, so tests drive it with `fake_async`.
- **Episodes.** A trigger starts an episode: `reconnecting` plus `RoomReconnectingEvent(reason)`. Each attempt waits its backoff delay first (full jitter, so clients that dropped together spread out; `Room.reconnect()` skips the first wait), then:
  1. connects a new session through the room's connector (`CloudflareRealtime(connectSession:)`, the same one `join` used), while the old one carries on if it still works;
  2. **switches** to it in one operation, `Room._replaceSession` (below), and closes the old session quietly. **Deviation from the task order** (close the old session last): a `LocalTrackPublication` lives on one session at a time and `republish` needs it detached, so the old session is closed right after the new one exists; for a failed session that only releases its peer connection;
  3. republishes every local track (`SfuSession.republish`: same `trackName`, the same `MediaStreamTrack`, current encodings; capture is never touched) and every DataChannel published through `room.data` (`republishDataChannel`). The DataChannels go here rather than with the subscriptions, so peers that follow the new session find them;
  4. announces the local state with the new `sessionId` (announcements are held from the start of the attempt, so the old ID with half-moved tracks is never announced). A failing `Signaling.update` is reported as `RoomErrorEvent('signaling.update')` and retried with the same backoff schedule; if that runs out, the attempt fails;
  5. pulls every wanted remote track again from the publisher's *current* session (each `RemoteTrackPublication` reconciles: an interrupted subscription moves with `resubscribe`), and moves every `RemoteDataSubscription` (`resubscribeDataChannel`, or a fresh subscribe);
  6. connects the new session even when nothing moved onto it (`establishConnection()`, with `RoomOptions.connectEarly`, and always when a publish is waiting to run on it: see Publishing late, 3), so it isn't expired before the next publish; then waits while the new peer connection is `connecting`, until it connects or a trigger fires (the connect timeout, 15 s). If tracks or DataChannels were negotiated on it, a peer connection still `new` is waited for too (its states arrive asynchronously, so right after the negotiation it often is), with the connect timeout armed for it; otherwise the room would show `connected`, then `connecting`, then `connected` again. With nothing negotiated, `new` is final and the room is `connected` at once.

  Then `connected` and `RoomReconnectedEvent(reason, duration, attempts)`.

  Each attempt starts with a `RoomReconnectAttemptEvent(reason, attempt, delay, waited, restarted)`: the backoff delay it drew and how long it actually waited (shorter when a network change, a return to the foreground or `Room.reconnect()` cut the wait short), and whether a network change abandoned the previous attempt (below). With the `RoomErrorEvent('reconnect')` of a failed attempt, that shows where a slow recovery spent its time; the example app prints all of them, with timestamps.
- **Failures inside an attempt.** A new session that can't be created, fails, is reported gone, or doesn't connect makes the attempt fail: it is closed, a `RoomErrorEvent('reconnect')` is emitted, and the next attempt follows its backoff delay. A per-track (`SfuTrackException`) or per-channel rejection doesn't fail the attempt: it is reported, the track stays `failed` and isn't announced (`LocalParticipant.state` leaves it out), and the next re-session tries it again. Remote pulls that fail keep their own retries (`RoomOptions.pullRetry`).
- **Giving up.** When the backoff runs out (default: after 2 minutes), the room is `disconnected` with `RoomReconnectFailedEvent(reason, attempts, error)`. It stays in signaling (with its last session ID) and usable: `leave()` works, `Room.reconnect()` starts again with a fresh budget, and a network change or a return to the foreground also starts again. Automatic triggers don't, so a dead network doesn't loop.
- **One at a time.** Triggers during an episode coalesce into it: one about the attempt's own new session fails that attempt; a network change or a return to the foreground cuts a backoff wait short; `Room.reconnect()` returns the running episode (skipping its current wait).
- **A network change during an attempt.** An attempt started while offline can be stuck on the old network: on macOS, a connect into a dead route can hang, so its `sessions/new` runs to the broker timeout (15 s) even after the network is back (seen in the checkpoint's real drop on a Mac: media back 6.9 s after the link, against 4 ms for the example's signaling). So a network change **abandons** an attempt that is still waiting
  - for its new session (step 1: the held announcement in flight, `sessions/new`, the ICE servers, the peer connection), or
  - for that session's peer connection to connect (step 6; its candidates may be from the old network),

  and the next attempt starts at once: `RoomReconnectAttemptEvent(restarted: true)`, with no backoff wait and no `RoomErrorEvent`. It still draws a backoff delay, so abandoned attempts count against `maxAttempts`/`maxElapsed` and a network that keeps changing can't restart attempts forever; each change abandons at most one attempt. The abandoned attempt leaves nothing behind: a session that arrives late is closed at once (the broker client forgets it, its peer connection closes) and nothing is ever pushed on it; a late failure is ignored; a session waiting to connect is closed, which interrupts what moved onto it, so the next attempt republishes it. `HttpBrokerClient` needs no way to abort a request: the abandoned request ends at its own timeout (it already aborts itself then), and its result is discarded. `leave()` uses the same path, so it no longer waits for a hung `sessions/new` either.

  Not abandoned: an attempt whose new session has connected, or one in steps 2–5 (moving tracks onto its session, announcing it, pulling). A request in flight there (`tracks/new`, a `Signaling.update` with the new session ID) could land after the next attempt's and undo it. A change (or a return to the foreground) that arrives then is remembered instead: if the attempt fails, the next one skips its backoff wait. Either way the attempt event shows it (`waited` 0, "cut short" in the example's log).
- **Flapping.** The backoff starts over only after the new session has lasted `ReconnectOptions.stablePeriod` (10 s). A session that breaks sooner continues the schedule, so a connection that keeps dropping backs off and eventually gives up instead of re-sessioning in a tight loop.
- **`leave()` during an episode** stops it at the next step: a backoff wait ends at once, a session still connecting is closed when it arrives and never becomes the room's, and nothing is announced.
- **While reconnecting**, `LocalParticipant.publish*` and `room.data.publish`/`subscribe` wait for the episode and then run on the new session. A publish already in flight when the session fails is run again on the new session, once (below).
- **Other participants' reconnections** are M3's path (§4.3): their new `sessionId` in signaling closes the pull on the old session and pulls from the new one at once. Pulls that fail meanwhile back off (`pullRetry`, 8 attempts in 1 minute), and pulls are never attempted on our own dead session (no retry timers while it is unusable; the re-session pulls everything once).
- **Session-bound components.** `Room._replaceSession(next)` is the only place `Room.session` changes: it stops following the old session, follows `next`, and calls `_onSessionReplaced()` (active speaker re-binds its stats reader). It runs when the new session exists, before tracks move onto it. Layer selection needs nothing: the chosen rid is re-applied after every pull.
- **Defaults** (`ReconnectOptions`): enabled; `backoff` = `BackoffOptions()` (≤ 500 ms, ×2, cap 10 s, give up after 2 minutes); `trigger` = `ReconnectTriggerOptions()` (disconnected 5 s, connect 15 s, network-change window 10 s, background 30 s); `stablePeriod` 10 s.
- **Demo and tests.** `Room.debugSimulateConnectionFailure()` fails the current session as a network drop would (`PeerConnectionFailureKind.simulated`, peer connection closed), so the whole path above runs; the example app's call screen has a "simulate network drop" button. `example/integration_test/reconnect_test.dart` drops the publisher, then the subscriber, against a real broker and checks the track is received again each time.
- **Publishing late (M10).** The SFU expires a session whose peer connection never connected, about ten seconds after `sessions/new` (§4.2). A room that joins and publishes only after a permission prompt, Android's screen-capture consent or the iOS broadcast picker used to fail that publish with `SessionGoneException` (seen: a phone waiting about 15 s on consent; a loaded Mac whose first `tracks/new` came 20 s after joining; `sfu_loopback_test` on a loaded Mac). Three measures, combined:
  1. **The peer connection is created while `sessions/new` runs** (§4.2, Connect), so a slow first `createPeerConnection` no longer adds to the session's age.
  2. **Connect early** (`RoomOptions.connectEarly`, default on). At join, while signaling joins, and at the end of a re-session that moved nothing, the room calls `SfuSession.establishConnection()`, so the session connects at once and the SFU keeps it however long the first publish takes. The cost is one more exchange with the broker (two calls: `datachannels/establish`, `renegotiate`) per session and an idle SCTP association. The room is `connecting` after join until the peer connection connects.
  3. **A publish whose session failed under it is retried once** (`Room._onSessionWithRetry`, used by `publishCamera`/`Microphone`/`Screen`/`MediaSource` and `room.data.publish`/`subscribe`). When the operation throws and its session has failed (a 410 on the push: `SfuSessionGone`; or any other failure) or was replaced by a re-session meanwhile, the room makes sure the failure started a re-session (the failures stream may not have delivered it yet; the failure is handled once per session), waits for that episode, and runs the operation once more on the new session, under the same track name and from the same capture. The caller's future completes normally. A second failure, an episode that gives up, automatic reconnection being off, or `leave()` surfaces the error; so does an SFU rejection of the track itself (`SfuTrackException`, `SfuDataChannelException`) or an error on a session that is still usable. Publishes in flight together share one re-session. Other participants see a clean change: the failed push was never announced, the re-session announces the new `sessionId` (with whatever it republished), and the retried track is announced on the new session, so they pull it from there.
     - **The retry is pushed onto a connected session.** The re-session connects its new session while a publish waits to run on it (step 6, even with `connectEarly` off) and ends once it is connected, so the retry is not the session's first negotiation.
     - **Why: the SFU sometimes never serves a track pushed before its session connected.** `late_publish_test` without `connectEarly` failed intermittently on a Pixel ("Bob never pulled Alice's video"): the re-session left the new session unconnected, the retried push was its first negotiation, and every pull of the track answered `not_found_track_error` ("Make sure the publisher peer is connected and sending packets for this track") for as long as the test waited (4 of about 120 runs), while `GET sessions/{id}` listed the track `active` and the publisher's stats showed media sent and RTCP received. A device experiment (`connectEarly: false`, publish at once, a peer pulls) reproduced it in 2 of 300 publishes, where a pull from a brand-new session failed the same way, and about half of the first pulls were answered `not_found_track_error` before a retry succeeded; with the session connected before the push (`connectEarly`), 0 of 300 and no `not_found_track_error` at all. The SFU's side of this isn't documented; the client avoids it by not pushing onto an unconnected session where it can.

  **Decision and why.** Keeping the session alive is the better primary fix: a permission prompt is the common case, and a re-session there shows the user "reconnecting" and churns the session ID in signaling for nothing. The SFU offers only one way to connect a session with nothing to send or receive: the DataChannel transport. `tracks/new` needs a track, a pull needs another session's track, and a placeholder audio push would be an announced-looking SFU track for nothing. partytracks doesn't solve this (no keepalive; it retries a failed push with backoff on the same session, which can't help once the session is gone). The retry stays as the safety net, because connecting early can still lose the race (a session already expired when the early connect goes out, after a very slow peer-connection setup, is replaced right after join) and because any session can fail between its creation and a push. Both are verified on devices with `example/integration_test/late_publish_test.dart` (join, idle 30 s, publish, check frames; once with `connectEarly` and once without, which must re-session). `connectEarly: false` keeps the old lazy behaviour.
- **Open:**
  - **Other pushes onto an unconnected session.** A re-session still republishes the moved tracks before its new session connects (steps 3 and 6), and with `connectEarly: false` the first publish is the session's first negotiation. Both can hit the SFU behaviour above (Publishing late, 3). Connecting the new session before republishing would cover the first; the second is the lazy behaviour `connectEarly: false` asks for.
  - **A pull from a publisher's session that is gone.** Handled since the post-M5 hardening: a `SessionGoneException` from a pull (or a remote DataChannel subscribe) is checked against our own session (`GET sessions/{ownId}`) before failing it (§4.2), so a peer's stale session in signaling makes that pull back off instead of re-sessioning the subscriber again and again. What the real SFU returns in that case (a request-level `session_error` or a per-track error) is still to be confirmed against it; both paths now end in a per-track error.
  - **Mobile background.** The trigger re-sessions after a long background, but keeping a call alive in the background (iOS audio background mode, `beginBackgroundTask`/CallKit, an Android foreground service) is platform setup for M6/M8.
  - The first attempt after a failure waits up to `initialDelay` (jitter). A shorter first delay would recover faster from a lone drop; keep the jitter for synchronized drops.
  - **A network change during an attempt** used to be dropped: it cut a backoff wait short only while the episode was waiting, so an attempt in flight ran to its end (a hung `sessions/new` to the 15 s broker timeout) and the next one still waited its full delay. The checkpoint's real drops showed both: the Windows run, whose broker lost its own path to Cloudflare (Node's fetch gives up after 10 s, so failures came about 11 s apart and recovery about 9 s after the last one), and the Mac run (above). **Done:** the change abandons the attempt, or makes the next one skip its wait (A network change during an attempt, above). Still open: a broker request in steps 2–5 that hangs isn't cut short.

## 9. DataChannels

Implemented (M7) at the session level in `lib/src/data/`, with the operations on `SfuSession`. `Room` exposes it as `room.data`, which maps senders to participants (§4.3). partytracks has no DataChannel support to port; the negotiation follows Cloudflare's DataChannels docs, the OpenAPI schema and Cloudflare's `echo-datachannels` example, and the queueing and lifecycle mirror the track code.

- The SFU forwards DataChannels **from a publisher to its subscribers**.
  - `datachannels/establish` sets up the SCTP transport.
  - `datachannels/new` with `location: "local"` publishes a named channel. With `location: "remote"` plus the publisher's `sessionId`, it subscribes.
  - A subscriber created with `canReply: true` can send back on the publisher's channel. **Only one subscriber can do this**; granting it to another replaces the previous one. For general two-way traffic, both sides publish.
  - Channels are **negotiated**. The SFU returns a channel `id`, and the client calls `createDataChannel(name, negotiated: true, id: id)`. The publisher's and subscriber's IDs can differ.
- **Offer two profiles** (`DataChannelProfile`):
  - **reliable**: ordered, retransmitted (omit `maxRetransmits` and `maxPacketLifeTime`). For keys, clicks, chat and control messages.
  - **unreliable**: `ordered: false`, `maxRetransmits: 0`. For high-rate data such as mouse moves.
  - The SFU requires every subscriber to **mirror the publisher's policy**, in its request and its own channel, so `subscribeDataChannel` takes the profile too. `maxPacketLifeTime` isn't offered: `flutter_webrtc`'s native plugins ignore it.
- **Sender identity comes from the channel's `sessionId`, never from the payload.**
  - The app maps `sessionId` → user through its (server-verified) signaling.
  - The package exposes the remote `sessionId` for each channel, so apps can do this. Remote control depends on it.

**API** (`SfuSession` is in `package:cloudflare_realtime/broker.dart`; the channels, also returned by `Room.data`, are in the main library):

```dart
final input = await session.publishDataChannel('input', profile: DataChannelProfile.unreliable);
await input.whenOpen();
await input.send(bytes);                  // or sendText; StateError unless open
input.bufferedAmount;                     // backpressure
input.bufferedAmountLowThreshold = 64 * 1024;
input.bufferedAmountLow.listen((_) => resume());

final sub = await session.subscribeDataChannel(remoteSessionId, 'input',
    profile: DataChannelProfile.unreliable, canReply: false);
sub.messages.listen((m) { m.fromSessionId; m.isBinary ? m.binary : m.text; });
await sub.setCanReply(true);              // datachannels/update

sub.state; sub.stateChanges;              // SfuDataChannelState: pending/connecting/open/interrupted/failed/closed
await sub.close();                        // datachannels/close
await session.republishDataChannel(input); await session.resubscribeDataChannel(sub, remoteSessionId: newId);
```

- **Negotiation sequence**, run lazily inside the first DataChannel operation on a session, through the session's op queue:
  1. `POST datachannels/establish` with `{"dataChannel": {"location": "remote", "dataChannelName": "server-events"}}` and **no offer**. No local channel has to exist first (the alternative, sending our own offer, needs one to get an `application` m-line).
  2. The SFU answers with `requiresImmediateRenegotiation` and an offer carrying the `application` m-line. Its `server-events` channel (ID 0) is opened in-band by the SFU; the package ignores it.
  3. `setRemoteDescription(offer)`, `createAnswer`, `setLocalDescription`, `PUT renegotiate` (the same path a pull uses).
  4. Then `datachannels/new`; each result's `id` becomes `createDataChannel(name, negotiated: true, id, ordered, maxRetransmits)`. There is no wait for the connection: the channel opens when the SCTP association is up (`connecting` → `open`).

  A failed establish fails that batch and is retried by the next publish or subscribe. Later offers (pushes, closes) carry the `application` m-line automatically.
- **Batching and errors.** As with tracks: publishes and subscribes in one event-loop turn become one `datachannels/new` each (local and remote kept apart, like `tracks/new`); `canReply` updates one `datachannels/update` (the last value per channel wins); closes one `datachannels/close` by `id`. A per-channel error or a missing `id` fails only that channel with `SfuDataChannelException`; a request-level `errorCode` fails the batch with `SfuRequestException`; `SessionGoneException` fails the session (for a subscribe, only after `GET sessions/{ownId}` confirms our session is gone; otherwise just the batch's channels fail, §4.2). If creating the local channel fails, or the channel was closed while its request was in flight, the SFU's `id` is released again with `datachannels/close`, best effort. Names are unique per session, and `server-events` is reserved.
- **Messages.** `DataChannelMessage` carries `binary` or `text`, and `fromSessionId`: the publisher's session for a `RemoteDataChannel`, captured when that underlying channel was opened (so late messages from an old session keep the old ID after a resubscribe). On a `LocalDataChannel`, received messages are replies from the one `canReply` subscriber, which the SFU doesn't identify, so `fromSessionId` is null. `messages` is a broadcast stream that survives moves between sessions.
- **Lifecycle.** A channel outlives its session, like a track publication. When the session fails or closes, channels become `interrupted` and their underlying channels are closed; the Room's re-session moves them with `republishDataChannel` / `resubscribeDataChannel` (§8) (which re-establish on the new session). If the underlying channel closes without `close()` (the SFU or the other end dropped it), the channel becomes `interrupted` too, and its SFU `id` is released. `close()` is immediate and terminal locally; on a dead session it makes no SFU call.
- **Backpressure.** `bufferedAmount` plus an edge-triggered `bufferedAmountLow` stream. Native `flutter_webrtc` reports every buffered-amount change (and fires its low callback on each change below the threshold), so the wrapper detects the crossing itself; on the web the browser's `bufferedamountlow` is used. On native platforms `bufferedAmount` is the last value reported, so it lags slightly.
- **`flutter_webrtc` realities** (1.6.2+hotfix.3):
  - `RTCDataChannelInit.toMap()` drops `maxRetransmits: 0` (it only sends positive values), which would silently make the unreliable profile reliable on native platforms. The wrapper overrides `toMap()`; Android, Darwin and the C++ desktop plugin all apply the key when present.
  - **Web:** `dart_webrtc` drops `maxRetransmits: 0` too and doesn't use `toMap()`, so a browser endpoint of an unreliable channel sends unordered but retransmitted. Needs an upstream fix (still so in `dart_webrtc` 1.8.2, checked in M13: it passes `maxRetransmits` only when it is above 0).
  - Binary messages are requested as `ArrayBuffer` on the web (`binaryType: 'binary'`); the default `Blob` is decoded asynchronously and can reorder messages.
  - **Windows and Android never report a negotiated channel as open.** The Dart channel's state stays null although the channel works (messages flow both ways). The likely cause: the plugin registers its observer only after libwebrtc has created the channel, and a negotiated channel on an already connected SCTP transport opens during creation, so the `open` event is never sent. `getStats()` does report it (`data-channel` with `dataChannelIdentifier` and `state: open`). So on native platforms the wrapper polls the stats while the state is unknown or `connecting` (20 ms doubling to 1 s) and reports `open` once they say so; a platform state event always wins and stops the polling. Found against the real SFU on Windows, where every channel stayed `connecting` and `whenOpen()` never completed. Android (a Pixel on Android 16) behaves the same: its plugin also registers the observer after creation, and the Dart side subscribes to the channel's event stream later still. No platform `open` event arrived there in any run; the first stats probe (20 ms) reported each channel open.
  - **Closing order.** On Windows, `RTCPeerConnection.close()` makes the plugin forget the connection, and `dispose()` then fails to close the channels (`dataChannelClose() peerConnection is null`), leaking their native observers. The wrapper closes its channels (including the SFU's `server-events`) before closing the connection.
- **Not done:** `waitForAck` (hold delivery until the subscriber acks) and a reply-sender identity for `canReply` traffic; neither is needed by the first consumer.

### 9.1 Media state over the SFU (proposal)

**Status: proposed (October 2026), for the owner's review. Nothing here is built.** It came out of an integration review. Today every change to a participant's media state is a `Signaling.update` (§4.3, Announcing): a mute or unmute, a settled layer change of any remote video (`layerDemand`, §6.2), and a change of captured size (§6.3, checked every 3 s). Neither the media nor the SFU carries that state, so it all goes through the app's presence transport. Some apps' signaling is rate-limited, for example presence services that allow a few updates per 30 s. There, quick toggles lag, or the client is throttled or disconnected, and a gallery whose layer demand moves while the user scrolls can use up the budget by itself. This proposal moves that state onto an SFU DataChannel that the package manages, so the app's signaling only has to carry membership.

**Goals.**
- Signaling is updated only when **membership** changes: join and leave, a new `sessionId`, a track published or unpublished, and `metadata`. A typical call then makes 3–6 updates in total, not one per mute or layer change.
- A mute reaches the other participants about as fast as the SFU forwards a packet, with no rate limit to wait for.
- State is **at least as trustworthy as signaling**: a participant can't set another participant's state (Authenticity, below).
- Older clients in the same room keep working. The default stays as it is today until the channel is verified on the real SFU.

**Non-goals.**
- Replacing membership or presence. The SFU has none, and a participant has to be discovered before its channel can be pulled.
- Carrying app data. `metadata` stays in signaling, and app messages stay on `room.data`.
- Making state more private than signaling, or end-to-end encrypted.
- A server component. The proposal adds nothing to the broker contract (§5).

#### What moves, and what stays

| State | Today | Proposed | Why |
|---|---|---|---|
| `participantId`, `sessionId` | signaling | **stays** | Discovery: a channel is pulled by the publisher's `sessionId`, so the session must be known first. It also binds the session to a participant (Authenticity). |
| Track list: `trackName`, `kind`, `source`, the simulcast `rids` and `scaleDownBy` | signaling | **stays** (phase 1) | See "Can the track list move?" below. Changes are rare: a publish, an unpublish, a screen share starting or ending. |
| `TrackInfo.muted` | signaling | **moves** | It is the most frequent state change a person makes. |
| `TrackInfo.simulcast.width` / `height` (captured size, §6.3) | signaling | **moves** | It is re-checked every 3 s and changes when a phone turns or CPU adaptation steps in. The size at publish time stays in the signaled track entry as an initial value. |
| `layerDemand` (§6.2) | signaling | **moves** | It changes with every settled layer choice of every pulled video, and is the largest field. |
| Speaking, audio level | not carried | **not carried** | Every receiver computes it from the audio it pulls (§7). Sending it would add traffic and add nothing. |
| Connection quality (§7.1) | not carried (decided) | **not in v1** | §7.1 kept it out of signaling because of the update rate. The channel removes that objection, so v1 reserves a field for it (Open questions, 7). |
| `metadata` | signaling | **stays** | It is app data, and apps may read it from presence outside the room. |

**Can the track list move?** Technically, yes. Once a participant's `sessionId` is known, the snapshot could list its tracks with `kind` and `source`, and signaling would carry only `{participantId, sessionId, metadata}`. Then a screen share starting or stopping wouldn't touch signaling either. **Decision for phase 1: it stays in signaling**, because:
1. **Media would depend on the channel.** If the state channel fails, a participant's mute icons are wrong but its media still plays. If the track list were on the channel, the participant's media would be gone.
2. **First media would come later.** A pull could start only after the channel has been subscribed, has opened and has delivered a snapshot: one more `datachannels/new` and a sync round trip before the first `tracks/new`. Expect a few hundred milliseconds or more (to be measured).
3. **Mixed rooms.** Older clients find tracks only in signaling, so a new client would have to write the track list there anyway while any of them is present.
4. **The rate doesn't need it.** A call publishes and unpublishes a handful of times. Membership updates (join, re-session) already go out at those moments.

Revisit after phase 1 has run on devices: a `tracks` field in the snapshot can be added in a later version without breaking v1 readers.

#### Topology

- **Each participant publishes one channel**, named `cf-realtime/media-state/1` (the major version is in the name, so two versions can be published side by side during a migration). It uses the reliable profile (`DataChannelProfile.reliable`: ordered, retransmitted), with `canReply: false`.
- **Every other participant subscribes to it**, by the publisher's `sessionId` from signaling. In a room of N, that is N publications and **N×(N−1) subscriptions**. The SFU forwards a channel from one publisher to its subscribers (§9), and one channel can't carry several publishers, so a full mesh is the only way for every receiver to get state from each publisher's own session. It is the same shape as audio, which every participant already pulls from every other.
- **The cost per subscription is small.** All channels share the session's one SCTP association, so a subscription is a `datachannels/new` with no SDP exchange. The transport is already up, because the room connects it at join (`RoomOptions.connectEarly`, §8.1). Subscriptions made in the same event-loop turn are batched, at most 32 per request (§4.2).
- The `cf-realtime/` prefix becomes reserved: `room.data.publish` rejects names that start with it.

Numbers, derived from §4.2's batching and the sizes under Wire format below. **The SFU documents no limit on DataChannels per session, subscribers per channel, or DataChannel message size** (checked 2026-10-04; [cloudflare-sfu.md, Limits](cloudflare-sfu.md#limits)).

| | N = 10 | N = 25 | N = 50 |
|---|---|---|---|
| Subscriptions per participant (+1 publication) | 9 | 24 | 49 |
| Subscriptions in the room | 90 | 600 | 2,450 |
| `datachannels/new` requests for a newcomer (one publish, plus subscriptions in batches of ≤ 32) | 2 | 2 | 3 |
| Extra requests for each existing participant per join | 1 | 1 | 1 |
| DataChannels on one peer connection (own, subscribed and `server-events`) | 11 | 26 | 51 |
| Snapshot size (3 own tracks, demand for N−1 cameras) | ≈ 0.8 KB | ≈ 1.5 KB | ≈ 2.8 KB |
| SFU egress for one mute (≈ 170 B on the wire × (N−1)) | ≈ 1.5 KB | ≈ 4 KB | ≈ 8 KB |
| SFU egress for a full resync (every participant sends a snapshot to every other) | ≈ 70 KB | ≈ 0.9 MB | ≈ 7 MB |
| Heartbeats (≈ 100 B every 20 s × N×(N−1)), per hour for the whole room | ≈ 1.6 MB | ≈ 11 MB | ≈ 44 MB |

- **SFU request rate.** The SFU allows 50 API requests per second per session ([cloudflare-sfu.md, Limits](cloudflare-sfu.md#limits)). Every number above stays well below that, even when the whole room joins at once: each session makes one request per batch of newcomers.
- **The broker** checks every `sessionId` in a `datachannels/new` body against its session store (§5, rule 4). A newcomer's batch at N = 50 names 49 sessions, the same as the newcomer's first batch of audio pulls.
- **Next to the media,** this is negligible. A 4-person call's media egress is about 0.75 GB per participant-hour (§6). The heartbeat overhead at N = 50 is under 1 MB per participant-hour. State changes add about 8 KB each at N = 50: one change per participant every 10 s is about 3 MB per participant-hour.
- **Unknown:** whether libwebrtc m150's SCTP (dcSCTP) still limits a peer connection's streams, as libwebrtc historically did at 1,024, and how many DataChannel subscriptions the SFU allows per session. The scale test (Testing) measures both up to N = 50.
- **Alternatives considered:**
  - **A hub participant that relays everyone's state.** About 2N subscriptions instead of N×(N−1), but the hub could rewrite anyone's state, which loses the authenticity this proposal is for, and it is a single point of failure. Rejected.
  - **An app server that relays state.** That puts a backend in the core package. Rejected; an app can do it in its own signaling.
  - **Carrying state in the media** (RTP header extensions, SEI): `flutter_webrtc` exposes neither, and a muted track sends no RTP. Rejected.
  - **Fewer channels.** Not possible: the SFU's channel fan-out is per publisher. An app channel and the state channel could share one name, but then app traffic would delay state, and state would be mixed with untrusted app payloads. Rejected.

#### Wire format (v1)

JSON text messages on the channel, at most **16 KiB** each. That is the size every WebRTC stack has interoperated with. The SFU's own `a=max-message-size` hasn't been recorded yet; the integration test reads it from the SFU's SDP. JSON over binary: at these rates and sizes a binary format saves nothing that matters, and JSON is easier to debug and evolve, and parses the same on every platform (including Wasm). Field names follow `ParticipantState`'s JSON (§4.4).

```jsonc
// Snapshot: the publisher's full dynamic state as of seq.
{"v":1,"type":"snapshot","seq":12,
 "tracks":{"camera-<uuid>":{"muted":false,"width":720,"height":1280},
           "microphone-<uuid>":{"muted":true}},
 "layerDemand":{"camera-<uuid>":"b","screen-<uuid>":"a"}}
// Delta: only what changed; seq is the previous seq + 1. A null in layerDemand removes the entry.
{"v":1,"type":"delta","seq":13,"tracks":{"microphone-<uuid>":{"muted":false}}}
{"v":1,"type":"delta","seq":14,"layerDemand":{"camera-<uuid>":"c","screen-<uuid>":null}}
// Heartbeat: the current seq, every 20 s while nothing else is sent.
{"v":1,"type":"heartbeat","seq":14}
// Sync request, sent on the requester's own channel: "send me a snapshot".
{"v":1,"type":"sync","sessions":["<publisher sessionId>", "..."]}
```

- **Sequence numbers** count state changes on one channel publication. They start at 0 on each new session (the channel is republished with the session, §8.1), and receivers keep state per `(participantId, sessionId)`, so the reset is unambiguous. Each change increments `seq` and is sent as a delta. A snapshot and a heartbeat carry the current `seq` without incrementing it.
- **Receiving:**
  - A snapshot with `seq` ≥ the last applied replaces the state.
  - A delta with `seq` = last + 1 is applied. One at or below the last is a duplicate and is ignored.
  - A delta that leaves a gap, or a heartbeat ahead of the last applied `seq`, means messages were missed. The receiver keeps what it has and asks for a snapshot.
  - Deltas that arrive before the first snapshot are ignored.

  On a reliable, ordered channel, gaps happen only when a subscription opens after the publisher has already sent messages.
- **Why the publisher needs sync requests.** The SFU doesn't tell a publisher who subscribes to its channel, or when (§9). So a subscriber whose subscription opens sends `sync` naming that publisher's session on **its own** state channel, which every participant pulls. It retries at 0.5, 1, 2 and 4 s, then every 10 s, until a snapshot arrives. The named publishers answer with one snapshot. A snapshot goes to every subscriber, so requests that arrive within 250 ms are answered with one snapshot. The publisher also sends a snapshot whenever its channel opens on a new session.
- **Tolerance:** an unknown `type`, or unknown fields, are ignored. A message that isn't valid JSON, is over 64 KiB, or has an unknown major `v` is dropped. Parsing never throws into the room. A snapshot that would exceed 16 KiB (more than about 300 demand entries, far beyond N = 50) is split into consecutive messages with the same `seq` and `"part"` / `"parts"` fields, and applied once all parts have arrived.
- **Capability:** a participant that publishes the channel announces `"mediaState": {"v": [1]}` at the top level of its `ParticipantState` (the major versions it publishes). Older readers ignore unknown keys (§4.4).

#### Applying the state

The Room keeps signaling's `ParticipantState` per participant, plus an overlay from that participant's channel. It feeds the merged state into the existing diffing (§4.3), layer pausing (§6.2) and ladders (§6.1, §6.3). So the existing events (`TrackMutedEvent`, `ParticipantUpdatedEvent`, …) and the code after the diff stay as they are, whichever path the state came by.

- **The channel wins** for the dynamic fields (`muted`, `width`/`height`, `layerDemand`) once a snapshot from the participant's **current** session has arrived. Signaling's values for those fields are the initial values: they apply before the first snapshot, and for a track that the snapshot doesn't list yet (a publish whose signaling update came first).
- **A track the channel lists before signaling does** (the delta came first) is held by `trackName` and applied when signaling lists the track. Channel state never creates a track: only signaling does.
- **A new `sessionId` in signaling** (the participant re-sessioned) drops the overlay for the old session. The fresh signaling values apply until the new channel's snapshot arrives. Late messages from the old channel are ignored: `RoomDataMessage.fromSessionId` is captured per underlying channel (§9), and it no longer matches.
- **Publishing:** the local participant sends a delta for every dynamic change, at most one message per 100 ms. A change after a quiet 100 ms goes out at once; later changes wait for the end of the window and go out as one delta. Layer demand is already debounced (§6.1, 300 ms) and the size check runs every 3 s, so normal use stays far below that. A heartbeat goes out after 20 s without a message.

#### Authenticity

The claim: **a state message is attributable to the session whose channel carried it, and that session to the participant who announced it.**

1. **The subscriber chooses the source.** It pulls `cf-realtime/media-state/1` from one `sessionId`. The SFU delivers on that subscription only what that session's peer connection sent on that channel. The package records the session per underlying channel (`fromSessionId`, §9). Nothing in the payload names a sender, and nothing in the payload is used to attribute it.
2. **Only the session's owner can send on it.** Sending requires that session's peer connection, which only the client that created it has: the DTLS keys never leave it. The broker's **session binding** (§5, rule 3) stops anyone else from publishing, closing or changing channels on that session through the API.
3. **The session belongs to a participant** through signaling. The Room's `_sessionOwners` maps a session to the participant that announced it, and a session claimed by two participants maps to none (§4.3, `data`). State from an unmapped session is dropped.
4. **Only room members can listen.** The broker's **same-room rule** (§5, rule 4) covers `datachannels/new` subscriptions, so no one outside the room can pull the channel.

**What a malicious participant can do:**
- **Lie about its own state:** say "muted" while sending audio, or name a captured size or layer demand that isn't true. Signaling allows the same today. A false demand can only keep a publisher's layers on, which is also what "not reported" does (§6.2).
- **Flood its own channel.** That costs the app SFU egress, as flooding media does. Receivers drop messages beyond 50 per second per session, and after 5 s of that they unsubscribe from that participant's state, use its signaling state instead, and report a `RoomErrorEvent('mediaState')`.
- **Claim another participant's `sessionId` in signaling,** if the app's signaling doesn't stop it. The session then maps to no one, and its state is dropped, as for `room.data` (§4.3). That doesn't let the attacker write the victim's state, only make the victim's state invisible, which a spoofing signaling transport allows anyway. Apps whose signaling isn't verified by a server can check session ownership against the broker's session store (an app-level step; see Open questions, 8).
- **Reply on someone's state channel.** A participant that calls the broker directly can subscribe with `canReply: true`. Its replies go to the publisher, which ignores everything received on its own state channel. **To verify:** that the SFU forwards a reply only to the publisher, and not to the channel's other subscribers (Open questions, 5).

**What a malicious participant can't do:** write another participant's mute, size or demand. With a shared broadcast channel in the app's signaling, anyone who can send to the channel could do that.

#### Re-sessions (§8)

- **Our re-session:** the state channel is a `room.data`-style publication, so step 3 of §8.1 republishes it on the new session **before** step 4 announces the new `sessionId`. Subscribers that follow the new session therefore find the channel already published. The first message on it is a snapshot with `seq` 0. Step 5 moves our subscriptions to everyone else's channels (the existing `RemoteDataSubscription` logic, §4.3), and each moved subscription sends a sync request when it opens.
- **A peer's re-session:** its new `sessionId` in signaling moves our subscription (a live one is closed and subscribed afresh). Until its snapshot arrives, the fresh signaling values apply (Applying the state).
- **The join window.** At join, the channel is published right after the early connect's `renegotiate` (§8.1; one more `datachannels/new`). The join announcement may reach peers before that request lands, so subscribers retry a failed subscribe with `RoomOptions.pullRetry`, as they do for tracks. **Unknown:** what the SFU answers to a subscription to a channel that isn't published yet: a per-channel error, a pending channel, or a session that opens later (Open questions, 4).

#### Signaling rate limiting on the package side

Separate from the channel, and useful on its own (and needed for the fallback): **`RoomOptions.minAnnounceInterval`** (`Duration?`, default `null`, which is today's behaviour). It spaces out signaling updates whose only changes are dynamic fields, so a burst becomes one update per interval. Updates that change membership-relevant fields (`sessionId`, the track list, `metadata`) go out at once, and carry the current dynamic fields with them. An app whose presence allows 5 updates per 30 s would set about 6 s. The announcer still coalesces as today (§4.3).

#### Options, fallback and mixed rooms

**`RoomOptions.mediaStateTransport`** (`MediaStateTransport`):
- **`signaling` (the default until verified):** today's behaviour. No channel is published or pulled, and no capability is announced.
- **`dataChannel`:** publish the channel, pull everyone's, and announce the capability. A change to dynamic fields **only** goes to signaling while some participant in the room lacks the capability (an older client, or one in `signaling` mode). Such updates are spaced by `minAnnounceInterval`. Every signaling update that happens anyway carries the current dynamic fields, so the signaled values are never older than the last membership change.
- **`both`:** as `dataChannel`, but every dynamic change also goes to signaling (rate-limited the same way). This is for verification, where the two paths can be compared, and for apps that read `muted` from presence outside the room, such as a lobby list. In `dataChannel` mode, those fields in presence are stale between membership changes; the dartdoc says so.

**Mixed rooms:**

| Publisher → subscriber | Older client, or `signaling` mode | `dataChannel` / `both` |
|---|---|---|
| **Older client, or `signaling` mode** | signaling (today) | signaling: no capability is announced, so no channel is pulled |
| **`dataChannel` / `both`** | signaling: the publisher sees a participant without the capability and keeps announcing dynamic changes | channel |

**Fallback:**
- **A participant whose channel never delivers a snapshot within 10 s** after the subscription opened (sync retries included), or whose subscription fails after `pullRetry`, is read from signaling. A `RoomErrorEvent('mediaState')` reports it.
- **If that lasts 30 s,** this client drops its own capability from its state (one signaling update). Its peers then announce dynamic changes in signaling again, which degrades the room to today's behaviour instead of leaving stale mute icons. It announces the capability again once every subscription has a snapshot.
- **A publisher whose channel can't be published** (an SFU rejection, or DataChannels unavailable on the session, §4.2) doesn't announce the capability, and stays on signaling.

`RemoteParticipant.mediaStateSource` (`signaling` / `dataChannel`) shows which path a participant's state currently comes from, for tests, the example app and debugging.

#### Privacy

The channel carries **nothing that signaling doesn't carry today**: track names, `muted`, the captured size and layer demand. It carries no participant IDs (receivers map sessions), no metadata, no device names and no quality. Its audience is the room's members with a session (the broker's same-room rule), which is no wider than the room's presence. As with everything on the SFU, the traffic is encrypted between each client and Cloudflare (DTLS), and is not end-to-end encrypted (§2, Non-goals).

#### Open questions

1. **SFU limits:** DataChannel subscriptions per session, and subscribers per channel. None is documented. Does the "up to 64 tracks per API request" limit also apply to `dataChannels` in one request? The client batches 32, below either.
2. **Billing:** Cloudflare bills SFU egress at $0.05/GB after 1 TB a month ([cloudflare-sfu.md](cloudflare-sfu.md#pricing-for-context)), but the pricing page doesn't say whether DataChannel traffic counts as egress. The numbers above assume it does; they are small either way.
3. **Idle channels:** is a DataChannel that carries nothing subject to the 30 s inactivity garbage collection that media tracks are? If not, the heartbeat could be slower.
4. **Subscribe before publish:** what does the SFU answer, and does a pending subscription open by itself once the channel is published?
5. **`canReply` fan-out:** does the SFU forward a reply only to the publisher? The authenticity argument assumes yes, and the package ignores replies anyway.
6. **The track list:** move it in a later version (Can the track list move?), once phase 1 has measurements?
7. **Connection quality:** share the local rating (§7.1) as an optional v1 field (`"quality"`), now that the rate isn't a problem? It would let apps tell "their uplink" from "my downlink".
8. **Session ownership for apps whose signaling isn't verified by a server:** should the broker contract offer a lookup (session → user) so that such apps can check the `sessionId`s in presence? It would be an optional broker endpoint; the reference brokers' session store already has the data.
9. **When to switch the default** to `dataChannel`. Proposed acceptance: the integration test passes on every platform in M13's list, the scale test passes at N = 25, and the latency is no worse than signaling's on the dev server.

**Estimate:** M (1–2 developer-weeks), mostly tests: a codec, a per-participant state machine, the overlay in the Room, the capability rule and `minAnnounceInterval`. The channel plumbing exists already (`room.data`, §9).

Falls back to GDI when covered, which may show the covering content, or black for GPU-rendered apps | No frames | Composited (no toggle) | **No** (#1952) |

- **Implemented (iOS), end to end (M9; builds and unit tests, device run pending):** the same `ScreenShareSource.start()` / `LocalParticipant.publishScreen()` without a source; the system's broadcast picker is the picker, and the example's "Share screen" goes straight to it. The capture runs in a **Broadcast Upload Extension**, which must be a target of the host app: the package ships its code as templates (`ios/broadcast_extension/`: `SampleHandler.swift`, `BroadcastUploader.swift`, an `Info.plist` and an entitlements file; MIT, written for this package), and the README's "iOS screen share setup" walks through adding it. The templates are not compiled into the plugin: the podspec and `Package.swift` take only `ios/cloudflare_realtime/Sources/`. The example's `BroadcastExtension` target references the template sources, so it builds exactly what ships.
  - **What `flutter_webrtc` 1.6.2 does:** `getDisplayMedia` with `video.deviceId` a plain **string** starting with `broadcast` uses its `FlutterBroadcastScreenCapturer` (a map there crashes it: `-[NSDictionary hasPrefix:]`). It reads the App Group from the app's `Info.plist` `RTCAppGroupIdentifier`, listens on a UNIX socket at `<App Group container>/rtc_SSFD`, and taps an off-screen `RPSystemBroadcastPickerView` (with `preferredExtension` from `RTCScreenSharingExtension`) unless the ID ends in `-manual`. It returns the track at once. Frames arrive as serialized `CFHTTPMessage`s with `Content-Length`, `Buffer-Width`, `Buffer-Height` and `Buffer-Orientation` (a `CGImagePropertyOrientation`, mapped to the frame's rotation) and a JPEG body. It reports neither a cancelled picker nor the broadcast's start or end, and when the extension never connected, stopping the track leaves its socket listening.
  - **This package's native part** (`ScreenBroadcast.swift` in the iOS plugin): `status` checks the setup (both `Info.plist` keys, the App Group container, an embedded `.appex` with extension point `com.apple.broadcast-services-upload` and the bundle ID in `RTCScreenSharingExtension`, and that extension's own `RTCAppGroupIdentifier`) and says whether a broadcast is running; `prepare {frameRate, scale}` writes the settings to the App Group's user defaults; `abandon` removes the socket file; and an event channel forwards the extension's Darwin notifications, `<appGroup>.cloudflare_realtime.broadcast.started` / `.finished`.
  - **A share runs:** `status` (if anything is missing, `start()` returns `false` and `errors` gets a `ScreenShareSetupException` with `problems` and `guidance`; it never waits) → `prepare` → `getDisplayMedia({audio: false, video: {deviceId: 'broadcast'}})` → wait for `started`, then the track is set. A broadcast already running is used at once, with `broadcast-manual` (no picker). If `started` doesn't come within `ScreenShareOptions.broadcastStartTimeout` (60 s), or `finished` comes first, the picker was dismissed or never answered: the capture is released, `abandon` is called so a late broadcast can't reach the abandoned socket, and `start()` returns `false` with nothing on `errors`, like a cancelled browser picker. Turning the share off while waiting ends the wait at once.
  - **Ending:** `finished` while sharing is `ScreenShareEndReason.userStopped` (the red status-bar indicator or Control Center). When the app stops a share, the capture closes the socket, the extension ends the broadcast with a short message ("Screen sharing has stopped."), and the release waits for its `finished` (up to 3 s), so the next share doesn't find a broadcast still running.
  - **The extension** reads the App Group from its own `Info.plist`, posts `started`, connects to the socket (retrying for 5 s; if the app isn't listening, it ends the broadcast with "Start screen sharing from the app."), and sends video frames only: throttled to the frame rate before any work, dropped while the previous frame is still being encoded or written, scaled (Lanczos) by `ScreenShareOptions.broadcastScale` (0.5 by default, even sizes) and encoded as JPEG (quality 0.8) with one cached `CIContext`, to stay well under the extension's ~50 MB memory limit. ReplayKit sends frames only when the screen changes, so a still screen is sent again once a second: otherwise the share would look stalled (`LocalTrackStalledEvent`) and late subscribers would get no picture. It watches the socket for the app closing it, and ends the broadcast then.
  - **Staying alive:** the app keeps running while the user is in other apps only with `UIBackgroundModes: audio` and an active audio session (a published microphone, as in any call). That belongs to the app's setup (README); §4.7 covers background calls in general.
  - **Limits:** `captureAudio` is ignored (`audioTrack` stays `null`): the extension sends video only, and `flutter_webrtc` has no way to add a custom audio source. One share at a time per app (one socket path). The picker's dismissal can't be detected, so a cancelled picker keeps `start()` waiting until the timeout. A broadcast started before the app launched isn't known to the app (the plugin learns of broadcasts from the notifications), so the picker shows again.
- **Implemented (Android), end to end (M9):** the same `ScreenShareSource.start()` / `LocalParticipant.publishScreen()` as on the web, without a source; the example's "Share screen" goes straight to the consent dialog. Native code is in the package's Android plugin (`ScreenCapture.kt`, `ScreenCaptureService.kt`), and its manifest declares the service and the permissions, so the manifest merger brings them into the app (README, "Screen share on Android").
  - **What `flutter_webrtc` 1.6.2 does:** `Helper.requestCapturePermission()` shows the consent dialog (`createScreenCaptureIntent`, from a headless fragment) and keeps the result; the next `getDisplayMedia` uses it to create the projection (`getMediaProjection`) and capture it with its `OrientationAwareScreenCapturer` (a `VirtualDisplay` at the display's size, 30 fps). Called without a kept result, `getDisplayMedia` asks for consent itself and creates the projection immediately. It has **no foreground service** and ignores the projection's `onStop` (its callback is empty). It never captures screen audio.
  - **The order Android 14+ requires:** the `mediaProjection` foreground service must be in the foreground *after* consent (starting it before throws a `SecurityException`) and *before* `getMediaProjection` (which throws without it). So a share runs: `prepare` (the notification permission, below) → `Helper.requestCapturePermission()` → our `startService`, which completes only once the service has called `startForeground(…, FOREGROUND_SERVICE_TYPE_MEDIA_PROJECTION)` (10 s timeout) → `getDisplayMedia` → `watch`.   - **Ending outside the app** is `ScreenShareEndReason.userStopped`, from either the projection's `onStop` (the system's status-bar chip and its "Stop sharing" dialog, or anything else that ends the projection) or the "Stop sharing" action in the service's notification. A denial is fine: the service runs anyway, and Android shows it only in the task manager, not in the drawer. Its channel ("Screen sharing", low importance), texts and icon are resources an app can override.
  - **Release order:** the capture is released first (which stops the projection), then the service.

    - The plugin reports changes only while someone calls `updateSources`. So the picker re-scans every 3 s (configurable), like the `flutter_webrtc` example, and applies added, removed, renamed and new-thumbnail events.

A fix, which builds the list on a worker thread, is proposed upstream ([flutter-webrtc#2223](https://github.com/flutter-webrtc/flutter-webrtc/issues/2223)); until it ships, an app can pin a patched `flutter_webrtc` with `dependency_overrides`. Verified in Chrome 154 (M13, `screen_share_test.dart` with `CF_REALTIME_SCREEN_SHARE_WEB`, Chrome's fake screen accepted by `--use-fake-ui-for-media-stream`): frames sent and decoded through the real SFU, unpublished when stopped, and with `captureAudio` the audio track the browser gave was published as `screenAudio` and pulled.   - **Ending a share** is surfaced on `ended` with a `ScreenShareEndReason`:
    - `stopped`: the app stopped it.
    - `userStopped`: the browser's "Stop sharing" button fired the track's `onEnded`, on Android the system or the notification stopped the share, or on iOS the broadcast finished (above).
    - `sourceClosed`: the shared window or display went away. Native tracks never fire `onEnded`, so while sharing, the desktop source re-scans the source list and ends the share on `onRemoved` for its source, if the removal is real. A re-scan can report a source removed that still exists: `getSources` lists from scratch and reports every source removed and then added again, and a scan can miss a window that is slow to answer (seen on Windows: rapid picker open/close during a share ended it in about 1 run in 4). So an `onAdded` for the same source within `sourceRemovalGrace` (500 ms) cancels the removal; after that the share ends only if the operating system has no geometry for the source (closed, hidden or minimized on Windows, or a platform without geometry). While it still has, the share goes on and the geometry is checked again every `sourceWatchInterval`, since the plugin has dropped the source from its list and won't report it removed a second time. **Why it went away** is `ScreenShareSource.endCause` and `LocalTrackUnpublishedEvent.sourceEndCause` (a `ScreenSourceEndCause`: `closed`, `hidden` or `minimized`), so an app can word its notice ("the window was minimized"). It is read when the share ends (`DesktopCapturerBackend.endCauseOf`): on Windows `IsWindow`, then `IsWindowVisible` (checked before `IsIconic`, since an app closing to the tray may minimize and then hide), then `IsIconic`; on macOS `closed` when the window server no longer lists the window (a minimized or hidden Mac window still has a frame, so its share goes on); a display no longer listed is `closed`; elsewhere `null`. Minimizing or hiding ends a share rather than pausing it: the app shows why, and the user shares again. **The re-scan is skipped while the operating system reports the shared source's geometry** (below; macOS and Windows), since the source then exists, and runs when it doesn't (the window closed, minimized on Windows, or no geometry on that platform), so a closed window still ends the share within one re-scan interval (3 s) of the next geometry read (500 ms). A re-scan (`updateSources` with screens and windows) is expensive: on macOS the plugin lists every window and renders every thumbnail on the main thread, and on a loaded Mac each re-scan held it for 2–7 s in a row while a share ran (`screen_share_stress_test.dart`, 19–21 sources), freezing the app; a 200 s share made 127 re-scans (up to 3.0 s on a quieter Mac), and none since. Reported from a macOS app: a freeze about 105 s after a share started (1 share in 5), during which a hang-up didn't arrive. Not reproduced here (200 s shares, nearly 400 short ones). The package's own main-thread blocks are the re-scans, gone, and `getStats()` calls waiting for libwebrtc's worker thread (§4.2), which now wait in Dart while a description is applied but can still block while the audio device module rebuilds itself after a device-list change. If it recurs, a `sample` of the app's main thread during the freeze will show which plugin call it is in.
  - **Switching sources** releases the old capture before starting the new one. On Windows, stopping any desktop capturer also stops the single loopback-audio capturer.
  - **Windows listing failures** (#1539, #1085) are data, not crashes:
    - `getSources` errors, or a list with no screens, become `ScreenPickerState.error` (`ScreenSourcesException`). The picker retries once at once, and `refresh()` retries again.
    - "source not found!" from `getDisplayMedia` means the plugin's list was stale. The share rebuilds it with `getSources` and retries once, then reports `ScreenSourceNotFoundException`. macOS answers `{error: "No source found for id: …"}` instead of throwing, which `flutter_webrtc` 1.6 misreads as a `TypeError` (a null `streamId`); on macOS that `TypeError` takes the same path.
- **Display and window geometry (desktop).** Apps that map a point in a shared picture to the sharer's desktop (remote pointers, annotation, remote control, click to focus) need to know where the shared display or window is. `ScreenSource.geometry` (a `ScreenGeometry`: `bounds`, `scaleFactor`, `isPrimary`) carries it for each listed source, and `ScreenShareSource.sourceGeometry` / `sourceGeometryChanges` follow the shared source while a share runs: read at the start, then every `geometryWatchInterval` (500 ms), so a window that moves or a display whose arrangement changes is followed. `null` where it isn't known: the web, phones and Linux, a source the OS no longer has, and on Windows a minimized window. `DesktopCapturerBackend.geometryOf(source)` is the seam (fakes answer `null`); the production backend reads the OS through `dart:ffi` (internal `NativeScreenGeometry`, `lib/src/media/screen_geometry*.dart`), with no plugin code, and a failing read is `null`, never an error.
  - **Coordinates are each OS's own desktop coordinates,** the ones its input and window APIs take. macOS: points in Core Graphics' global display space, origin at the primary display's top-left, y down (AppKit's `NSScreen` frames are the same units with y flipped). Windows: physical pixels of the virtual screen as a per-monitor DPI-aware app (Flutter's runner) sees them, origin at the primary monitor's top-left; with mixed scale factors there is no common logical unit, so no conversion is made. Displays left of or above the primary have negative coordinates. A window's `scaleFactor` is that of the display showing most of it (else the nearest); `isPrimary` is `false` for windows.
  - **How `flutter_webrtc` 1.6.2's source IDs map to the OS.** macOS: a screen's ID is its `CGDirectDisplayID` in decimal (its ScreenCaptureKit capturer selects the `SCDisplay` whose `"%u"` of `displayID` equals it; libwebrtc's `ScreenCapturerMac` lists displays by that ID), and a window's is its `CGWindowID` (`kCGWindowNumber`). Windows: a window's ID is its `HWND` in decimal (`flutter_webrtc`'s `loopback_capturer_factory.cc` parses it so), and a screen's is libwebrtc's screen ID, which is **not** a monitor handle: the index of the display device in `EnumDisplayDevicesW(NULL, index)`, counting inactive devices (`GetScreenList`); libwebrtc's wrapper asks for the DXGI capturer, which maps its outputs back to those indices by device name (`GetScreenListFromDeviceNames`). The package matches each active device's name (`\\.\DISPLAY1`) to a monitor from `EnumDisplayMonitors` / `GetMonitorInfoW`.
  - **What is read.** macOS (Core Graphics): `CGGetActiveDisplayList`, `CGDisplayBounds`, the display mode's pixel width over its width for the scale, `CGMainDisplayID` for the primary; a window's `kCGWindowBounds` from `CGWindowListCopyWindowInfo(IncludingWindow, id)`. None of it needs the Screen Recording permission or an entitlement, and it works in the App Sandbox (window bounds are readable without the permission; titles are not, and aren't read). Windows: `rcMonitor` and `MONITORINFOF_PRIMARY` from `GetMonitorInfoW`, `GetDpiForMonitor(MDT_EFFECTIVE_DPI) / 96`, and a window's `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` (the visible frame, without the invisible resize borders), else `GetWindowRect`.
  - **Verified on macOS** (`example/integration_test/screen_geometry_test.dart`, sandboxed example app, one Retina display): the screen's geometry matched Flutter's display list (the `NSScreen` with that `CGDirectDisplayID`: 1728×1117 points at scale 2 = 3456×2234 pixels, primary at 0,0); all 12 listed windows had a frame, the app's own window was the Flutter view's width with a 32-point title bar, and a share of it reported the same frame on `sourceGeometry` and `null` after stopping. Checked outside the sandbox with `NSScreen` and `CGWindowListCopyWindowInfo`: every window source's name was the window server's `kCGWindowName` for that ID, with identical bounds. Several displays (negative origins, mixed scales) are covered by unit tests only. **On Windows** it is built from the Win32 documentation and libwebrtc's source, its mapping is unit-tested with fakes, and `test/media/screen_geometry_native_test.dart` runs the real bindings on the CI's Windows host. The window lookup was checked on Windows 11 hardware through its use in ending a share (2026-10-07, `flutter_webrtc` with the fix from flutter-webrtc#2226): a shared window that was destroyed, closed (`WM_CLOSE`), hidden to the tray (`SW_HIDE`) or minimized ended the share 2.9 to 3.5 s later, and 33 runs of rapid picker open/close during a share (screen, and the app's own window with and without frames) all kept it. Before `IsWindowVisible` was checked, a window hidden to the tray kept its share running on 1×1 frames, which the VP8 encoder then failed to initialize on. Screen bounds and scale against Flutter's display list are not checked on a device yet.
- **macOS Screen Recording permission (TCC).** Capturing needs the user's permission (System Settings → Privacy & Security → Screen & System Audio Recording; "Screen Recording" before macOS 15). There is no entitlement or `Info.plist` key for it (the sandboxed example needs nothing beyond its camera, microphone and network entitlements); macOS prompts on the first capture, and a newly granted permission applies only after the app restarts. A rebuilt, ad-hoc-signed debug app can count as a new app and be asked again. `flutter_webrtc` 1.6 neither asks for it nor reports it: `getDisplayMedia` still returns a live track, and ScreenCaptureKit fails to start in the background (it only logs). So the package watches for symptoms and reports a `ScreenCapturePermissionException` (a `MediaPermissionDeniedException`, `suspected: true`, with `guidance` to show):
  - **in the picker:** `ScreenPickerState.permissionProblem` when a listing has no screens, or every screen's thumbnail is empty or black (`thumbnailLooksBlank`, internal: it reads uncompressed 8-bit TIFF; other formats count as unknown). It clears once a listing looks normal. macOS only.
  - **after sharing:** `LocalTrackStalledEvent` when the share sends no frames (§4.3).
  - Which symptom a denied permission shows (empty, black or wallpaper-only thumbnails; no windows) depends on the macOS version and needs checking on devices; the no-frames check is the reliable one. A native `CGPreflightScreenCaptureAccess()` call would be exact, but the package's plugin has no macOS part yet.
- **Correction to the table:** since `flutter_webrtc` 1.5.0 (#2060), Windows can capture system audio via loopback, with `ScreenShareOptions(captureAudio: true)`. It arrives as `ScreenShareSource.audioTrack`. Whether it's good enough to replace the "No (#1952)" cell needs device testing.
- **Known `flutter_webrtc` issues to plan around:**
  - Windows HDR screens look washed out; WGC capture is requested (#2205).
  - Windows sometimes fails to list sources (#1539, #1085); handled as above.
  - There's no hardware-encoder selection on Windows (#2200).
  - The macOS 14+ system picker exists only in Stream's fork.

## 11. Public API sketch

The room API is implemented (M3, §4.3), with layer selection and active speaker (M4, §6.1, §7), automatic re-sessioning (M5, §8) and typed stats with connection quality (M12, §7.1). Reviewed for the first pub.dev release (M8, [api-review.md](api-review.md)), then cleaned up before 0.1.0 (one style for observable state, one suffix for options, one naming scheme for events, class modifiers, three libraries; [doc/migrating-to-0.1.md](../doc/migrating-to-0.1.md) has the old → new table). It can still change before 1.0.

```dart
import 'package:cloudflare_realtime/cloudflare_realtime.dart';

final rt = CloudflareRealtime(
  broker: BrokerOptions(
    baseUrl: Uri.parse('https://api.example.com/realtime'),
    headers: () async => {'Authorization': 'Bearer ${await getAppJwt()}'},
  ),
);

final room = await rt.join(
  'room-123',
  signaling: mySignaling,             // app-provided Signaling
  participantId: currentUserId,
  metadata: {'displayName': 'Ada'},
  options: const RoomOptions(
    autoSubscribe: AutoSubscribe(audio: true, video: false),
    // Defaults: hide-to-release after 5 s, 500 ms lease grace, 250 ms speaker polls.
    hiddenVideoLinger: Duration(seconds: 5),
    leaseReleaseGrace: Duration(milliseconds: 500),
    activeSpeaker: ActiveSpeakerOptions(),
    reconnect: ReconnectOptions(),     // the default: re-session automatically (§8)
    stats: RoomStatsOptions(),         // stats every 2 s; connection quality on (§7.1)
    videoCodec: VideoCodec.h264,       // M12: null (the default) keeps VP8 (§6, Codec)
    layerPausing: LayerPausingOptions.on,  // M12: pause layers no one pulls (§6.2); off by default
  ),
);

final local = room.localParticipant;
final mic = await local.publishMicrophone();
final cam = await local.publishCamera(encodings: SimulcastPresets.h720);   // the default; [] = no simulcast
final share = await local.publishScreen(source: pickedSource);  // a ScreenSource from ScreenSourcePicker; none on web
                                       // one 15 fps layer (ScreenSharePresets.detail); .motion / .simulcast
await mic.mute(); await mic.unmute();  // announced as TrackInfo.muted; mic.isMuted / mic.mutedChanges
await local.switchCamera();            // front <-> back on phones, next camera elsewhere; same track
await room.setSpeakerphone(false);     // phones: earpiece (a headset first); canSetSpeakerphone, isSpeakerphoneOn

// The phone's own call UI (§4.8): CallKit, Telecom; Dart-only elsewhere.
await SystemCalls.instance.configure(const SystemCallsOptions());
final call = await SystemCalls.instance.reportIncomingCall(id: callUuid, handle: const CallHandle('ada'), displayName: 'Ada');
SystemCalls.instance.events.listen((e) { /* SystemCallAnsweredEvent: join; SystemCallEndedEvent: ... */ });
room.attachSystemCall(call);           // system mute <-> microphone; leave when it ends, end when left
await cam.unpublish();

// Observable state: the value now, and `…Changes`, which replays it and then each change.
room.participants;                     // List<RemoteParticipant> (+ participantsChanges)
room.events;                           // Stream<RoomEvent>: Participant…, Track…, LocalTrack…, Room… events
room.connectionState;                  // connecting/connected/reconnecting/disconnected (+ connectionStateChanges)
room.activeSpeakers;                   // List<String>, loudest first (+ activeSpeakersChanges)
room.dominantSpeaker;                  // String?: who goes on the stage (+ dominantSpeakerChanges)
room.layerReporter;                    // LayerDemandReporter: views report their size here
room.stats;                            // RoomStats?: transport, layers sent, tracks received (§7.1) (+ statsChanges)
await room.getStats();                 // one RoomStats now; raw reports in RoomStats.reports
cam.stats;                             // LocalTrackStats?: per layer rid, size, fps, bitrate, limitation (+ statsChanges)
room.localParticipant.connectionQuality;  // excellent/good/poor/lost/unknown (+ connectionQualityChanges)
room.isAudioPlaybackBlocked;           // web autoplay policy (+ audioPlaybackBlockedChanges); false on native
await room.startAudio();               // from a user gesture: play the blocked remote audio
await room.reconnect();                // re-session now (e.g. a "Reconnect" button after giving up)
room.session;                          // the current SfuSession (broker.dart): replaced by a re-session

final remote = room.participants.first;
remote.microphone?.isMuted;            // camera / microphone / screen / screenAudio, trackPublications
await remote.camera?.subscribe();      // pull on demand; or ParticipantVideoView.remote(remote.camera!)
await remote.camera?.setPreferredLayer(SimulcastLayer.low);   // overrides the automatic layer
await remote.camera?.clearPreferredLayer();                    // back to automatic
remote.camera?.currentRid;             // the rid asked for; layerState / layerStateChanges for debug UIs
remote.camera?.track;                  // RenderableTrack?: track + MediaStream for RTCVideoRenderer (+ trackChanges)
remote.isSpeaking; remote.speakingChanges; remote.audioLevel; remote.audioLevelChanges;
remote.connectionQuality;              // what arrives from them; lost when their media stops (+ connectionQualityChanges)
remote.camera?.stats;                  // RemoteTrackStats?: codec, bitrate, size, fps, loss, jitter, freezes (+ statsChanges)
local.isSpeaking; local.speakingChanges;

ParticipantVideoView.remote(remote.camera!, visible: onScreen);  // subscribes while mounted, picks its layer
ParticipantVideoView.local(cam.mediaSource);                           // self-view, mirrored unless a back camera

final input = await room.data.publish('input', profile: DataChannelProfile.unreliable);
await input.whenOpen();
await input.send(bytes);
final sub = await room.data.subscribe(remote, 'input', profile: DataChannelProfile.unreliable);
sub.messages.listen((msg) { /* msg.participantId, from signaling, never the payload */ });

room.events.listen((event) => switch (event) {   // sealed RoomEvent
      ParticipantJoinedEvent(:final participant) => showToast(participant),
      RoomReconnectFailedEvent() => showReconnectButton(),
      _ => null,
    });

try {
  await local.publishScreen();
} on BrokerException catch (e) {       // sealed, like SfuSessionException and MediaException
  switch (e) {
    case BrokerUnauthorizedException() || BrokerForbiddenException(): /* sign in again */
    case SessionGoneException(): /* the room re-sessions by itself */
    case BrokerNetworkException() || BrokerProtocolException() || BrokerResponseException(): /* retry */
  }
}

await room.leave();

// Debug aid (§4.2): name the platform calls behind a frozen UI.
PlatformCallTimingBinding.ensureInitialized();          // first thing in main()
CloudflareRealtime.debugPlatformCallTiming = const PlatformCallTimingOptions();
CloudflareRealtime.debugPlatformCallTimingEvents;       // Stream<PlatformCallTimingEvent>

// The package's log lines (§4.9): type and code only by default.
CloudflareRealtime.logger = (record) => myLog(record.toString());  // record.error has the full error
CloudflareRealtime.debugLogFullErrors = true;            // the default logger prints error text too
```

- **Style.** partytracks uses Observables deliberately: repair logic (a replaced device or connection) stays inside the library, and consumers just see the new track. **Mirror that with Dart `Stream`s.** No `rxdart` (§12, question 1): where partytracks needs `BehaviorSubject`-style replay of the latest value, the package uses its internal `StateStream<T>` helper (`lib/src/util/`).
- **Observable state** (decided before 0.1.0): a getter `x` for the value now, and a `Stream xChanges` that replays the current value to each new listener, then emits each change. Booleans are `isX` (or `hasX`, `canX`), and their stream drops the `is`: `isMuted` / `mutedChanges`, `isSpeaking` / `speakingChanges`. Streams of things that happen, not of state, keep plain plural names: `events`, `errors`, `messages`, `failures`, `ended`, and the `changes` stream of a participant or publication. The interfaces an app implements (`Signaling.participants`, `NetworkChangeSource.changes`, `AppLifecycleSource.states`) are feeds into the package and keep their names.
- **Options:** every settings class ends in `Options` (`RoomOptions`, `BrokerOptions`, `ActiveSpeakerOptions`, …), and is `final` with a `const` constructor.
- **Class modifiers.** Value types (options, `ParticipantState`, `TrackInfo`, `MediaDevice`, `ScreenSource`, `ScreenGeometry`, the stats, the wire models) are `final`. Events are `final` under a `sealed` root (`RoomEvent`, `SystemCallEvent`), and so are exceptions (`BrokerException`, `SfuSessionException`, `MediaException`), so a `switch` over them is exhaustive. The exceptions outside a family are `final` too: `AudioRouteUnavailableException`, `AudioOutputException` (a refused `Room.setAudioOutputDevice`, with an `AudioOutputFailure` reason; §4.3) and `SystemCallException`. The classes apps mock in tests (`Room`, the participants, the publications, the media sources, `SfuSession`, `SystemCalls`, `CloudflareRealtime`) have no modifier, and the interfaces apps implement (`Signaling`, `BrokerClient`, `MediaBackend`, `VideoRenderer`, `NetworkChangeSource`, `AppLifecycleSource`, `LayerDemandReporter`) are `abstract interface`.
- **Libraries.** `package:cloudflare_realtime/cloudflare_realtime.dart` is what apps use. `package:cloudflare_realtime/broker.dart` holds the plumbing under `Room`: `BrokerClient`, `HttpBrokerClient`, `BrokerHeaders`, the SFU API's wire models, and the low-level `SfuSession` with `LocalTrackPublication`, `RemoteTrackSubscription`, `SfuConnectionState` and `PublishOptions` (apps reach a session through `Room.session`, rarely by name; keeping the session's `LocalTrackPublication` out of the main import also avoids confusing it with the room's `LocalMediaPublication`). `package:cloudflare_realtime/testing.dart` holds the test seams: `MediaBackend` and its platform parts with `FlutterWebrtcMediaBackend`, `VideoRenderer` with `FlutterWebrtcVideoRenderer`, the `CloudflareRealtime` factories (`BrokerClientFactory`, `SfuSessionConnector`, `MediaStreamWrapper`) and `InMemorySignaling`. No symbol is exported twice. What the room API shares with the session layer (`SfuSessionOptions`, `SfuTrackState`, `SendEncoding`, `VideoCodec`, the session failures and exceptions, DataChannels, and the wire enum `SimulcastOrdering` that `LayerSelectionOptions` uses) stays in the main library.

## 12. Open questions

1. ~~`rxdart`, or plain `Stream`/`StreamController`?~~ **Resolved:** plain `Stream`s, plus an internal `StateStream<T>` helper for replay-latest state. This means fewer dependencies for pub.dev consumers, and the replay-latest semantics we need are small.
2. ~~Screen share: simulcast or a single layer?~~ **Decided for the checkpoint (M6): a single layer by default, simulcast as an option.** `publishScreen` sends `ScreenSharePresets.detail` (captured resolution, ≤ 15 fps, ≤ 2.5 Mbps; captured at 15 fps) unless given `encodings`; `ScreenSharePresets.motion` (≤ 30 fps, ≤ 4 Mbps) suits video, and `ScreenSharePresets.simulcast` adds a quarter-size 5 fps layer. Why: a share is usually what everyone watches, on the stage and at full size, so a thumbnail layer mostly costs the sharer's upload and encoder; text needs resolution more than frames, so the frame rate is low and the bits per frame high. The encoder can't be told "this is text": `flutter_webrtc` 1.6 has no `MediaStreamTrack.contentHint` on any platform (and doesn't expose `degradationPreference` through our session wrapper yet; `maintain-resolution` would be the setting for shares). macOS marks desktop capture as a screencast (`videoSourceForScreenCast:YES`), which libwebrtc treats as screen content. **Still to measure on devices:** legibility at 1080p and 4K, and what libwebrtc makes of the simulcast preset's low layer for screencast sources (it may shape screenshare simulcast its own way).
3. Package split: a core package plus separate adapter packages (Supabase, in-memory), or adapters as examples only?
4. ~~Minimum Dart/Flutter SDK for pub.dev?~~ **Resolved (M8): Dart `^3.11.0`, Flutter `>=3.41.0`** (it was `^3.13.0` / `>=3.47.0`). `flutter_webrtc` 1.6 allows Dart 3.3, so the code sets the floor: `TickerMode.valuesOf` (in `SimulcastLayerReporter`) first shipped in Flutter 3.41, and the `TickerMode.of` it replaces is deprecated. Null-aware collection elements need Dart 3.8; private named parameters (Dart 3.12) were rewritten as initializer lists. The Android plugin applies the Kotlin Gradle plugin itself when AGP 9's built-in Kotlin is off (older Flutter app templates use AGP 8), as `flutter_webrtc` does. Checked on Flutter 3.41.0; see [api-review.md](api-review.md#sdk-constraint).
5. Naming and trademark: the package is **unofficial**. Keep the disclaimer in the README and pubspec description.
6. **Publisher-side layer pausing on by default?** (M12, §6.2) Built and unit-tested, and the paused layers work (a new pull of a resumed layer decodes in 0.4–0.6 s), but the SFU often leaves a subscriber that switches **up** with `tracks/update` on a lower layer after the layer was paused (2 of 4 room-level runs on a Pixel 10), and its up-switches are slow (about 6 s) and sometimes stuck even without pausing. So it is **opt-in** (`LayerPausingOptions.on`) for now. To turn it on by default: switch up by pulling the new layer afresh (make before break) when it was paused, or find out from Cloudflare what makes the SFU switch layers. Measure on a constrained uplink and with 4+ participants too.
7. **H.264 by default on phones?** (M12, §6) H.264 now works per room (`RoomOptions.videoCodec`) and hardware-encodes all three layers on a Pixel 10, but every subscriber must decode it, and Windows has crashed decoding it (flutter-webrtc #982). Decide after the Windows re-run (M13): if Windows decodes H.264 safely, phones could prefer it.
